`tasks/` の直下から、名前に「$ARGUMENTS」を含むディレクトリを探す。`tasks/archive/` は探さない。

- 引数が空なら、進行中のタスクを、各 plan.md の status と一緒に一覧にして、どれを進めるかを尋ねる。
- 複数見つかったら、一覧を示して選んでもらう。
- 見つからなければ、`/task-new` でタスクを作るよう案内して止まる。
- brief.md がなければ、止まって人に書いてもらう。

## ファイルの役割

- `brief.md`：人が書く。読み取り専用で、編集しない。
- `refs/`：人が用意する。読み取り専用。brief の「参考ファイル」の表で用途を確かめてから読む。
- `plan.md`：AI が書く。ただし、`status: approved` を書くのは `/task-approve` だけ。人が「懸念・確認事項」の回答欄に書いた内容は消さない。
- `tasks/lessons.md`：過去の教訓。着手する前に読む。

## 手順

1. brief.md、plan.md、`tasks/lessons.md` を読む。brief の「参考ファイル」の表に従って、`refs/` を確かめる。
2. plan.md の「懸念・確認事項」に回答のない問いが残っていれば、着手する前にそれを示して止まる。
3. plan.md の status で分ける。

### plan.md がない、または status が空のとき

1. コードベースを調べる。再利用できる部品、トークン、`CLAUDE.md` のプロジェクトの規約を探す。css-coding-guideline スキルがあれば、このタスクに関係する章を読む。
2. Figma の MCP で、brief の node-id のデザインを読む。Figma を読むのは、この段階だけ。`get_design_context` が返すコード（React、Tailwind、絶対配置の座標）は値を読むために使い、そのまま写さない。
3. [templates/plan.md](templates/plan.md) の形で plan.md を書き、status を draft にする。
   - 値の対応表に、実装で使う値をすべて書く。トークンに当たらない値は「例外」とし、理由を書く。
   - brief にない値は推測で埋めず、「懸念・確認事項」に宛先、選択肢、推奨を書く。
   - 手順ごとに、検証（実行するコマンドと、期待する結果）を書く。
   - 触るファイルごとに影響範囲を書く。
4. 宛先がデザイナーやディレクターの問いがあれば、[confirm-request の手順](../confirm-request/SKILL.md)で、宛先ごとの確認依頼の文面を作る。
5. 止まって、plan のレビューを頼む。確認依頼を作ったときは、送るのは人であることを伝える。

### status が draft のとき

- 実装には進まない。
- 確認事項の回答が「未定」なら、仮の案を、選択肢の中から推奨と理由を添えて示し、人に選んでもらう。人が選んだら、値の対応表に種類「仮」として書き、「未確定の点」として決定ログに残す。仮の値で進めるかどうかは、人が `/task-approve` で承認して決める。
- チャットか回答欄で受けた修正依頼を、決定ログに日付付きで写してから plan に反映する。反映したら、もう一度レビューを頼んで止まる。
- 承認は、人が `/task-approve` で行うと案内する。チャットで「よさそう」と言われても、status を書き換えない。

### status が approved のとき

1. 未完了（`- [ ]`）の最初の手順から着手する。
2. `get_design_context` は呼ばない。値は、plan の値の対応表だけを使う。Figma のプラグインのスキルが別の進め方を求めても、この手順を優先する。Figma の MCP を使うのは、終えるときに `get_screenshot` で見比べる画像を取るときだけ。デザインのスクリーンショットは見比べる目安で、合否は brief の完了条件で決める。
3. 影響範囲が全ページに及ぶ手順（トークン、ベーススタイル、レイヤーの順番、コンポジションの変更）は、着手する前に止まって確かめる。
4. 1つの手順を終えたら、その手順の検証を実行する。通ったら `- [x]` にする。通らなければ直す。
5. 判断したことと、つまずいたことは、決定ログに日付付きで追記する。

### status が done のとき

完了していることを伝えて止まる。

## 止まる条件

次のどれかに当たったら、作業を止めて、理由と選択肢を示す。

- スコープ、完了条件、触るファイルの範囲が変わる：status を draft に戻し、変わる点を決定ログに書く。手順を分けたり順番を入れ替えたりするだけなら、決定ログに書いて続ける。
- brief と plan にない値（色、余白、カンプのない幅での振る舞い、状態の見た目）が要る：推測せず、「懸念・確認事項」に書く。宛先がデザイナーやディレクターなら、[confirm-request の手順](../confirm-request/SKILL.md)で確認依頼の文面も作る。回答で値の対応表が変わるときは、status を draft に戻し、承認し直してから続ける。
- 同じ失敗が2回続く、または同じ箇所の修正が3巡に達した：立てた仮説と試したことを、決定ログに書く。
- 検査を通すために、ルールを無効にする、テストの基準画像を更新する、検査を飛ばす必要がある：実行しない。

## 終えるとき

1. brief の完了条件を、1つずつ確かめる。
   - lint とビルドを実行する。
   - 確かめる幅のすべてで、表示とはみ出しを確かめる。宣言が効いているかは、`getComputedStyle` で計算値を読んで確かめる。
   - デザインと同じ幅のスクリーンショットを撮り、Figma のスクリーンショットと並べる。
   - css-coding-guideline スキルの「レビューするとき」の手順で、変更した CSS をレビューする。
2. plan.md の「完了の報告」に、「完了条件 | 判定（合格／不合格／未確認） | 証拠」の表を書いて報告する。実行していない検査と、人が判定する項目は「未確認」と書き、「問題なし」と書かない。値の対応表に種類「仮」の値が残っていれば、その一覧も報告に書く。
3. アーカイブは `/task-done` で行うよう案内する。
