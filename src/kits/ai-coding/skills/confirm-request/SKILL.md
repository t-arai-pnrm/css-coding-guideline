「$ARGUMENTS」について、意図を確かめる質問を、宛先ごとの確認依頼の文面にする。依頼文は出力するだけで、送らない。送るのは人。

## 質問を集める

- 引数にタスクのスラッグが含まれていれば、`tasks/` の直下（`tasks/archive/` を除く）からタスクを探し、plan.md の「懸念・確認事項」のうち、回答のない問いを集める。
- タスクがなければ、このセッションのやりとりから、確かめたいことを問いの形にまとめる。足りない情報があれば、先に利用者に尋ねる。
- 問いごとに、宛先を決める。見え方（色、余白、カンプのない幅、内容が増減したときの見せ方、状態と動き）はデザイナー、運用と内容（文言、件数、更新の頻度、CMSで編集する範囲）はディレクターに尋ねる。plan.md に「宛先」が書いてあれば、それに従う。

## 依頼文を書く

[templates/request.md](templates/request.md) の形で、宛先ごとに1通ずつ書く。

- 1通に入れる質問は5問まで。超えたら、実装を止めている質問から順に5問を選び、残りは次の便に回すと利用者に伝える。
- 質問ごとに、対象、状況、選択肢、推奨と理由を書く。
  - 対象は、Figma のノードの URL（`node-id` を含むもの）。plan.md のノードの対応表から取る。
  - 状況は、デザインに何が描かれていないか、何と何が食い違っているか。
  - 選択肢は2〜3個にし、選ぶだけで答えられる形にする。
  - 推奨には、実装する側から見た理由を1文で添える。
- 実装の用語（`@container`、`gap`、トークンの名前など）は使わず、見え方の言葉で書く（「置き場所が狭いとき」「見出しと日付の間」）。
- 実装を始めた後なら、Figma のデザインと同じ幅で、いまの画面のスクリーンショットを撮る。タスクがあれば `requests/` に保存し、依頼文にファイル名を書いて、添えて送るよう書く。plan を書く段階では撮らない。
- 書き手は実装者の文面にする。「AI が」とは書かない。
- 末尾に、分からない項目は「未定」と答えてよいことと、その場合は仮の案と進め方をこちらから提案することを書く。仮の形で実装を進めるとは書かない。

## 保存して示す

1. タスクがあれば、`tasks/<slug>/requests/<YYYY-MM-DD>-<宛先>.md` に保存する。タスクがなければ保存しない。
2. チャットに全文を示し、送る前に人が読んで直すよう促す。送るのは人で、AI は送らない。
3. 回答を受け取ったら、plan.md の各問いの「回答」欄に貼るよう案内する。回答が brief の「デザインから読み取れないこと」に当たるときは、人が brief も直すよう案内する。
4. 回答が「未定」の問いは、仮の案を選択肢の中から推奨と理由を添えて示し、人に選んでもらう。選ばれた案は、plan の値の対応表に種類「仮」として書き、承認し直してから実装に使う（`/task-start` の draft の手順）。必要なら、仮の案を相手に伝える文面も作る。
