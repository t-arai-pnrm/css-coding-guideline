ホバーのスタイルは、`&:any-link:hover` や `&:enabled:hover` のように操作できる状態に限り、`@media (any-hover)` の中に書きます。同じ見た目は `:focus-visible` にも指定します。キーボードでフォーカスを移したときはトランジションを掛けず、一度で切り替えます。変化を表すときも `opacity` で透かさず、背景色や文字色を別の色に変えます。

選択中や展開中といった状態は、`.is-active` のような状態クラスを使わず、擬似クラス、HTML要素の属性、ARIA属性、`data-*` 属性の順に検討して、セレクタにします。

文字の選択を止める `user-select: none` は、連打や長押しで文字が選択されて困る操作部品にだけ指定します。`touch-action` も、ドラッグを自分で処理する部品に限り、ページ全体には指定しません。

## タッチ操作の端末でのホバー

`:hover` をメディアクエリの条件なしに書くと、スマートフォンのようなタッチ操作の端末で問題が起きます。タップした要素にホバーのスタイルが当たったまま、ほかの場所をタップするまで残り続けます。リンクによっては、1回目のタップでホバーの表示だけが変わり、2回目でようやく移動することもあります。

```css title="🙅‍♂ Not Recommended: 条件なしのホバーと、画面の幅によるホバーの判定"
/* 🙅‍♂ Not Recommended */
._submit-button {
  &:hover {
    background-color: var(--_background--hocus);
  }
}

._more-link {
  &:hover {
    @media (width >= 768px) {
      color: var(--_color--hocus);
    }
  }
}
```

画面の幅で判定する2つ目の書き方も、問題を解決しません。幅の広いタブレットはタッチで操作しますし、幅の狭いウィンドウをマウスで操作することもあります。画面の幅は、入力の方法を表していないからです。

`@media (hover: hover)` や `@media (hover: hover) and (pointer: fine)` も、よく見かける書き方です。しかし、`hover` が調べるのは「主な入力」がホバーできるかどうかだけです。iPadにトラックパッド付きのキーボードをつないだ場合、主な入力はタッチのままなので、トラックパッドでカーソルを重ねてもホバーのスタイルが当たりません。

## `any-hover` と `:focus-visible` を組み合わせる

ホバーのスタイルは、`@media (any-hover)` の中に書きます。`any-hover` は、使える入力のうち「どれかひとつでも」ホバーできるかを調べるメディア特性です。トラックパッドをつないだタブレットでもホバーが有効になり、つなぐ・外すの変化にも追従します。

ホバーのセレクタは、操作できる状態の要素に絞ります。リンクは `&:any-link:hover`、ボタンやフォームのコントロールは `&:enabled:hover` と書きます。`:any-link` は `href` を持つリンクにだけ当てはまるので、`href` を外した現在のページのリンクは反応しません。`:enabled` は無効にしたボタンを除きます。押せないものが押せそうに見えるのを防ぐためです。`<summary>` と `<label>` には無効の状態がないので、条件を付けずに `&:hover` と書きます。

```css title="🙆‍♂ Recommended: ホバーを操作できる状態に絞って any-hover の中に書き、:focus-visible にも同じ見た目を指定する"
@scope (.scoped.text-link) to (.scoped) {
  :scope {
    --_color: var(--color--accent--600);
    --_color--hocus: var(--color--accent--700);

    color: var(--_color);

    &:focus-visible {
      color: var(--_color--hocus);
    }

    &:any-link:hover {
      @media (any-hover) {
        color: var(--_color--hocus);
      }
    }
  }
}

@scope (.scoped.save-button) to (.scoped) {
  :scope {
    --_background: var(--color--accent--600);
    --_background--hocus: var(--color--accent--700);

    background-color: var(--_background);

    &:focus-visible {
      background-color: var(--_background--hocus);
    }

    &:enabled:hover {
      @media (any-hover) {
        background-color: var(--_background--hocus);
      }
    }
  }
}
```

<Baseline id="interaction" compatKey="css.at-rules.media.any-hover" name="any-hover メディア特性" />

条件は `(any-hover: hover)` と値まで書かずに、`(any-hover)` と書きます。`any-hover` の値は `none` と `hover` の2つだけです。メディア特性を値なしで書くと、値が `none` のときに偽、それ以外のときに真と評価されるので、`(any-hover)` は `(any-hover: hover)` と同じ意味になります。値を書かないほうが短く、「ホバーできる入力があるか」という問いの形がそのまま読み取れます。

ホバーで変える見た目は、`:focus-visible` にも同じように指定します。キーボードで操作するユーザーも、マウスで操作するユーザーと同じ手がかりを得られます。祖先の `overflow` でフォーカスリングの一部が切り取られた場合にも、背景色の変化でフォーカスの位置が分かります。`:focus-visible` のスタイルはメディアクエリの外に書きます。タッチ操作の端末にも、キーボードをつないで使うユーザーはいるからです。

フォーカスリングそのものは、ベーススタイルで二重のリングを定義しています（「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」）。コンポーネントで指定するのは、リングに加える背景色などの変化だけです。リングを `outline: none` で消すことはしません。

リングを描いても、フォーカスした要素が固定ヘッダーの下に隠れていては見えません。WCAG 2.2の達成基準2.4.11「隠されないフォーカス（最低限）」（レベルAA）は、キーボードでフォーカスを受けた要素が、制作者の置いたコンテンツで完全に隠れないことを求めています。本書では、ベーススタイルで `:focus` にも `scroll-margin-block-start` を指定して、この問題を防いでいます（「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」）。スクロールする側に `scroll-padding-block-start` で余白を取る方法は、「[11-7 固定ヘッダー](/layout-practice/sticky-header/)」で説明しています。

なお、タッチスクリーンを持つノートパソコンでは、マウスもあるので `(any-hover)` が当てはまります。この環境では、指でタップしたときにホバーのスタイルが残ります。入力の方法を操作ごとに見分けたい場合は、JavaScriptのポインターイベントを併用するしかありません。

`@media` は、`&:enabled:hover` のようなセレクタの中に書けます。セレクタの層には、@ルールを数えないからです（「[9-4 ネストの書き方](/notation/nesting/)」）。

## キーボード操作とトランジション

ホバーの変化にトランジションを掛けるときは、キーボードでフォーカスを移したときの変化には掛けないようにします。Tabキーで次々とフォーカスを移しているのに、背景色が遅れて変わると、入力と表示がずれて反応が遅く感じられるからです。

```css title="🙆‍♂ Recommended: トランジションを :not(:focus-visible) の中に書く"
._submit-button {
  &:not(:focus-visible) {
    @media (prefers-reduced-motion: no-preference) {
      transition-duration: var(--duration--fast);
      transition-property: background-color;
      transition-timing-function: var(--ease--out-quint);
    }
  }
}
```

`:focus-visible` が当てはまっている間は、トランジションの指定がありません。そのため、フォーカスが来た瞬間に一度で色が変わります。フォーカスが離れるときとホバーのときは、`:not(:focus-visible)` が当てはまるので、なめらかに色が戻ります。トランジションを動きを減らす設定の条件で囲む理由は、「[18-2 動きを減らす設定に対応する](/motion/reduced-motion/)」で説明します。

## ホバーで動く要素の当たり判定

ホバーで位置や大きさが変わる要素を、そのまま `:hover` の対象にすると、ちらつくことがあります。カーソルが縁にあるとき要素が動くと、ホバーが外れて要素がもとの位置に戻り、戻るとまたホバーが当たる、という繰り返しになるからです。

```css title="🙅‍♂ Not Recommended: ホバーを受ける要素自身を動かす"
/* 🙅‍♂ Not Recommended */
._submit-button {
  &:hover {
    translate: 0 -4px;
  }
}
```

ホバーを受ける要素は動かさず、動かすのは子要素（または擬似要素）にします。ホバーを受ける側は、動かない当たり判定として働きます。

```css title="🙆‍♂ Recommended: ホバーを受ける要素は動かさず、子要素を動かす"
@scope (.scoped.lift-button) to (.scoped) {
  :scope {
    --_hocus: --false;
    --_focus-visible: --false;

    display: inline grid;

    &:focus-visible {
      --_hocus: --true;
      --_focus-visible: --true;
    }

    &:enabled:hover {
      @media (any-hover) {
        --_hocus: --true;
      }
    }
  }

  ._face {
    @container style(--_hocus: --true) {
      translate: 0 -4px;
    }

    @container style(--_focus-visible: --false) {
      @media (prefers-reduced-motion: no-preference) {
        transition-duration: var(--duration--fast);
        transition-property: translate;
        transition-timing-function: var(--ease--out-quint);
      }
    }
  }
}
```

ボタンのホバーとフォーカスは、フラグのカスタムプロパティ `--_hocus` で子の `._face` に伝えます。ボタンの状態のセレクタで `--_hocus: --true` を立て、`._face` は `@container style(--_hocus: --true)` で持ち上がります。名前なしの `style()` は親を問い合わせ、カスタムプロパティは継承するので、ボタンで立てたフラグを `._face` から読めます。ボタンにデフォルト値の `--_hocus: --false` を明示しているのは、外側の要素で立てたフラグを継承しないためです。

キーボードでフォーカスしたときは一度で持ち上げるので、トランジションも `--_focus-visible` のフラグで切り替えます。ボタンの `&:not(:focus-visible)` にトランジションを書いても、`transition` は継承しないので、動く `._face` には掛かりません。フラグとスタイルクエリで状態を伝える書き方は、「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」で説明しています。

## 操作する領域の大きさ

指で操作する環境では、操作する領域が小さいと、押し間違いの原因になります。WCAG 2.2の達成基準2.5.8「ターゲットのサイズ（最低限）」（レベルAA）は、ポインターで操作する対象を24×24 CSSピクセル以上にすることを求めています。周囲に十分な間隔がある場合や、文章中のリンクのような場合は例外です。より厳しい達成基準2.5.5「ターゲットのサイズ（強化）」（レベルAAA）は、44×44 CSSピクセルを求めています。

本書では、ボタンやアイコンのような操作する要素に、24px相当の最小の大きさを確保します。タッチ操作ができる環境では、44px相当に広げます。切り替えるのは大きさの値だけで、`min-block-size` と `min-inline-size` の指定は1か所にします。大きさは、ボタンの最小の高さと同じく、文字と一緒に大きくなるように `rem` で書きます（「[6-1 pxとremを使い分ける](/values/px-and-rem/)」）。ただし、`rem` だけで書くと、ブラウザの文字サイズを16pxより小さくしたユーザーの環境では、WCAGが求めるCSSピクセルの下限を下回ります。たとえば文字サイズが12pxなら、`calc(24 / 16 * 1rem)` は18pxです。そこで `max(24px, 24 / 16 * 1rem)` と書き、文字と一緒に大きくなりながら、24pxを下回らないようにします。

```css title="🙆‍♂ Recommended: 最小の大きさをカスタムプロパティで受け、タッチ操作では値だけを変える"
@scope (.scoped.icon-button) to (.scoped) {
  :scope {
    --_hit-size: max(24px, 24 / 16 * 1rem);

    display: inline grid;
    place-content: center;
    min-inline-size: var(--_hit-size);
    min-block-size: var(--_hit-size);

    @media (any-pointer: coarse) {
      --_hit-size: max(44px, 44 / 16 * 1rem);
    }
  }
}
```

条件には、`pointer` ではなく `any-pointer` を使います。使える入力にタッチ操作がひとつでもあれば、広いほうの大きさにするためです。`pointer` と `any-pointer` の違いは、「[13-5 メディアクエリ](/responsive/media-queries/)」で説明しています。

24pxに満たない要素を並べるときは、要素の間隔で例外の条件を満たします。達成基準2.5.8の「十分な間隔」とは、24pxに満たない要素それぞれの中心に直径24pxの円を描いたとき、その円がほかの要素にも、ほかの要素の円にも重ならないことです。たとえば16px四方のアイコンを横に並べるなら、中心どうしを24px以上離す必要があるので、`gap` は8px以上にします。

### 余白を付ける要素

押せる範囲を決めるのは、`<a>` や `<button>` のような操作する要素自身の大きさです。ナビゲーションの `<li>` やリストのような外側の要素に `padding` を付けても、見た目の上では項目が大きくなるだけで、押せるのは文字の部分に限られます。項目の端を押しても反応しないので、ユーザーは押し損じたと感じます。

```css title="🙅‍♂ Not Recommended: 外側の li に padding を付け、押せる範囲を文字だけにする"
/* 🙅‍♂ Not Recommended */
._item {
  padding: 12px 16px;
}
```

`padding` は、操作する要素自身に付けます。`<a>` は初期値でインラインなので、`display: block flow` か `display: inline flow-root` にして、上下の `padding` も押せる範囲と行の高さに含めます（「[7-3 ボックスモデルの基礎](/layout/box-model/)」）。

```css title="🙆‍♂ Recommended: 操作する要素自身に padding を付ける"
@scope (.scoped.global-nav) to (.scoped) {
  ._link {
    display: block flow;
    padding: 12px 16px;
  }
}

@scope (.scoped.option-list) to (.scoped) {
  ._option {
    display: block flex;
    gap: 8px;
    align-items: center;
    padding-block: 8px;
  }
}
```

チェックボックスとその文字も、同じ考え方で扱います。2つ目の例の `._option` は、チェックボックスと文字をまとめて包んだ `<label>` です。チェックボックスと文字の間の `gap` も、上下の `padding` も `<label>` の内側にあるので、どこを押してもチェックが切り替わります。チェックボックスと `<label>` を兄弟に並べて間を空けると、その隙間は押しても何も起きない領域になります。

次のデモでは、押せる範囲に色を付け、外側の要素を破線で囲んでいます。上の例では、破線の内側でも色の付いていない部分を押すと何も起きません。下の例では、破線と色の範囲が一致し、どこを押しても反応します。

### 見た目を変えずに押せる範囲を広げる

ダイアログの閉じるボタンのように、デザインの都合で見た目を小さく保ちたい要素もあります。この場合は、擬似要素を要素の外にはみ出させて、押せる範囲だけを広げます。擬似要素は要素の一部なので、擬似要素を押せば要素を押したことになります。WCAGの「ターゲット」もポインターの操作を受け付ける領域を指すので、擬似要素で広げた範囲を大きさとして数えられます。

```css title="🙆‍♂ Recommended: 擬似要素をはみ出させて、押せる範囲だけを広げる"
@scope (.scoped.close-button) to (.scoped) {
  :scope {
    --_hit-size: max(24px, 24 / 16 * 1rem);

    position: relative;
    display: inline grid;
    place-content: center;

    @media (any-pointer: coarse) {
      --_hit-size: max(44px, 44 / 16 * 1rem);
    }

    &::before {
      content: "";
      position: absolute;
      inset: min(0px, (100% - var(--_hit-size)) / 2);
    }
  }
}
```

`inset` のパーセンテージは、インライン方向の値なら基準のボックスの幅、ブロック方向の値なら高さを基準にします。`(100% - var(--_hit-size)) / 2` は、要素が `--_hit-size` より小さいぶんの半分を負の値で表すので、擬似要素は要素を中心に `--_hit-size` 四方へ広がります。`min()` で0pxを上限にしているのは、要素がもともと `--_hit-size` より大きいときに、擬似要素が要素より小さくならないようにするためです。

広げた範囲が隣の要素に重なると、重なった部分を押したときにどちらが反応するかは、重なりの順序で決まります。ユーザーには、押した要素と違うものが反応したように見えます。擬似要素で広げるのは、周りに広げるだけの余白がある要素に限り、並べるときは広げたあとの大きさで間隔を確かめます。

次のデモでは、2つの閉じるボタンの見た目は同じです。下のボタンは、破線で囲んだ範囲のどこにマウスを重ねても色が変わり、押せる範囲が擬似要素の分だけ広がっていることが分かります。

## サブメニューへ斜めに動かすときの当たり判定

ホバーで横にサブメニューが開くメニューでは、カーソルをサブメニューへ斜めに動かす途中で、隣の項目の上を通ることがあります。すると隣の項目にホバーが移り、開いていたサブメニューが閉じて、隣の項目のサブメニューに切り替わります。サブメニューの中の項目を選ぶには、いったん真横に動かしてから縦に動かすしかありません。

この問題は、項目とサブメニューの間に、カーソルが通っても隣の項目に移らない三角形の領域を置くと防げます。カーソルの位置を頂点の1つとし、サブメニューの項目側の辺の両端を残りの2つの頂点とする三角形です。この領域は「安全な三角形」（safe triangle）と呼ばれます。三角形はホバーを受けている項目の擬似要素として描き、`clip-path: polygon()` で切り抜きます。CSS Maskingの仕様では、`clip-path` で切り抜いた外側はポインターの操作を受けないので、三角形の内側だけが項目の一部として働きます。

```css title="🙆‍♂ Recommended: ホバー中の項目の擬似要素を三角形に切り抜き、サブメニューへの通り道にする"
@scope (.scoped.action-menu) to (.scoped) {
  ._trigger {
    &::before {
      content: "";
      position: fixed;
      inset: var(--_safe-top) var(--_safe-right) var(--_safe-bottom) var(--_safe-left);
      z-index: var(--z--forwards);
      display: none;
      clip-path: polygon(0 var(--_safe-y), 100% 0, 100% 100%);
    }

    &:enabled:hover::before {
      @media (any-hover) {
        display: block flow;
      }
    }
  }
}
```

この例は、サブメニューが右に開く場合です。擬似要素の矩形は、カーソルの位置からサブメニューの左の辺までの範囲で、高さはサブメニューにそろえます。`--_safe-y` は、矩形の上端からカーソルまでの距離です。これらの値は、JavaScriptで `pointermove` のたびに、カーソルの位置とサブメニューの `getBoundingClientRect()` から求めて設定します。画面上の座標から決まる値なので、`inset` は論理プロパティにせず、物理方向の4つの値で受けます。

三角形の擬似要素は、`@media (any-hover)` の中でだけ表示します。タッチ操作ではホバーがなく、斜めの移動も起きないからです。キーボードの操作にも関わりません。サブメニューは、ホバーだけでなくボタンを押したときやキーボードでも開けるようにしておきます。

次のデモは、マウスで操作して確かめます。「ファイル」の左寄りにカーソルを置き、開いたサブメニューの「書き出す」へ斜めに動かしてください。「三角形なし」のメニューでは、途中で「編集」や「表示」のサブメニューに切り替わります。「三角形あり」のメニューでは、色の付いた三角形の中を通るあいだ「ファイル」のサブメニューが開いたままです。

<Demo title="安全な三角形の中を通ると、斜めに動かしてもサブメニューが切り替わらない" html={safeTriangleHtml} css={safeTriangleCss} js={safeTriangleJs} variant="neutral" widths={[]} />

## 連打や長押しで文字が選択される部品

操作部品の中には、素早く2回押すと、中の文字が選択されてしまうものがあります。Chrome 152で確かめたところ、`<label>`、`<summary>`、`role="tab"` を付けた `<div>` は、ダブルクリックで文字の一部が選択されました。`<button>` の文字は選択されませんでした（2026年10月確認）。`<label>` とラジオボタンで作った表示の切り替えや、数量を1ずつ増やす部品のように、続けて押すことの多い部品では、押すたびに文字が反転して見えます。タッチ操作の端末では、長押しで文字の選択が始まることもあります。{/* 要検証: ブラウザ。長押しの挙動は実機で未確認 */}

こうした部品にだけ、`user-select: none` を指定します。Safariは接頭辞なしの `user-select` に対応していないので（2026年10月確認）、`-webkit-user-select` を併記します。接頭辞を書くときは、理由のコメントとStylelintの無効化のコメントを添えます（「[9-7 モダンな記法にそろえる](/notation/modern-syntax/)」）。

```css title="🙆‍♂ Recommended: 連打で文字が選択されて困る操作部品にだけ、user-select: none を指定する"
@scope (.scoped.view-switcher) to (.scoped) {
  label {
    /* Safari は接頭辞なしの user-select に対応していない（2026年10月） */
    /* stylelint-disable-next-line property-no-vendor-prefix */
    -webkit-user-select: none;
    user-select: none;
  }
}
```

<Baseline id="user-select" />

`user-select: none` は、本文の文字や `body` には指定しません。`user-select` は継承しないプロパティですが、初期値の `auto` は、親の値が `none` なら `none` として扱われます（MDN）。そのため、`body` に指定すると、ページのすべての文字が選択できなくなります。文章をコピーして引用や検索に使うユーザーも、選択した文字を読み上げや翻訳の機能に渡すユーザーも困ります。{/* 要確認: 出典なし */}コピーを防ぐ目的でも、開発者ツールやソースの表示で文字は取り出せるので、効果はありません。

## `touch-action` を指定する範囲

`touch-action` は、タッチ操作でブラウザがスクロールや拡大をするかどうかを決めるプロパティです。これを `html` や `body` に `none` で指定すると、ページ全体でスクロールとピンチでの拡大が止まります。`touch-action` も継承しませんが、ブラウザは、触れた要素からスクロールする祖先までの値を重ね合わせて、許す操作を決めるからです（MDN）。拡大して読む必要のあるユーザーが拡大できなくなる点は、`<meta name="viewport">` でズームを止めた場合と同じです（「[17-3 フォーム部品](/interaction/forms/)」）。

```css title="🙅‍♂ Not Recommended: ページ全体のタッチ操作と文字の選択を止める"
/* 🙅‍♂ Not Recommended */
body {
  touch-action: none;
  user-select: none;
}
```

`touch-action` は、ドラッグやスワイプを自分で処理する部品にだけ指定します。たとえば、つまみを横にドラッグして2枚の画像を見比べる部品なら、つまみに `pan-y pinch-zoom` を指定します。横の動きは部品が処理し、縦のスクロールとピンチでの拡大はブラウザに残せます。`none` にするのは、手書きの入力欄のように、すべての指の動きを部品で受け取る場合だけです。{/* 要確認: 出典なし */}

```css title="🙆‍♂ Recommended: 横のドラッグを処理するつまみにだけ、残す操作を明示して指定する"
@scope (.scoped.compare-slider) to (.scoped) {
  ._handle {
    touch-action: pan-y pinch-zoom;
  }
}
```

<Baseline id="touch-action" />

ボタンには、`touch-action` を書き直しません。kiso.cssが、`<button>` や、`role="button"`、`role="tab"` を付けた要素などに `touch-action: manipulation` を指定しています。iOSでダブルタップしたときの拡大を防ぐためです（「[8-1 壊さないリセット](/reset/kiso/)」）。`manipulation` は、スクロールとピンチでの拡大を許し、ダブルタップでの拡大だけを止める値です。

## ホバーの変化を透明度で表す方法

ホバーの表現として手軽なのが、`opacity: 0.7` のように要素を透かす方法です。しかし、この方法はおすすめしません。背景だけでなく文字まで透けるので、コントラストが下がって読みにくくなります。背景に画像や別の色があると、それが透けて見えるのも問題です。

```css title="🙅‍♂ Not Recommended: ホバーを透明度で表し、文字まで薄くする"
/* 🙅‍♂ Not Recommended */
._submit-button {
  &:hover {
    opacity: 0.7;
  }
}
```

もうひとつの問題は、意図が伝わらないことです。コードを読んだ人には、「ホバーしたら暗くしたい」のか「目立たなくしたい」のかが分かりません。デザインで別の色が指定されているなら、その色をそのまま書いたほうが、意図とコードが一致します。

背景色や文字色を変えるときは、状態ごとの値を `--_background--hocus` のような接尾辞を付けた内部プロパティにまとめます。値には、デザインで決まっている色のトークンを使います。専用の色がない場合は、`oklch(from var(--_background) calc(l - 0.1) c h)` のように、相対カラー構文で元の色から明るさだけを変えた色を作ります。接尾辞の付け方は「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で、相対カラー構文は「[15-2 相対カラー構文で派生色を作る](/color-media/relative-color/)」で扱います。

次のデモでは、ボタンとリンクにマウスを重ねたときと、Tabキーでフォーカスを移したときに、同じように色が変わります。無効にしたボタンと、`href` のない現在のページのリンクは反応しません。

<Demo title="ホバーとフォーカスで同じように色が変わり、操作できないものは反応しない" html={hoverHtml} css={hoverCss} />

比較のために、ホバーを `opacity` で表したものが次のデモです。文字まで薄くなり、無効にしたボタンも反応します。Tabキーでフォーカスを移しても、フォーカスリング以外は何も変わりません。

## 状態を表すセレクタ

選択中のタブ、開いているメニュー、現在のページのリンクのような状態は、BEMのModifierのように、JavaScriptでクラスを付け外しして表すことがよくあります。しかし、こうした状態の多くは、アクセシビリティのためにARIA属性でも表す必要があります。クラスと属性の両方を切り替えると、同じ状態を2か所で管理することになります。

```css title="🙅‍♂ Not Recommended: ARIA属性と別に、状態のクラスを付ける"
/* 🙅‍♂ Not Recommended */
._tab.is-active {
  border-color: currentColor;
}
```

本書では、状態を表すのに原則としてクラスを使いません。次の優先順位で、状態を表すセレクタを選びます。

1. 擬似クラス（`:disabled`、`:any-link`、`:checked` など）
2. HTML要素の属性（`target` 属性、`<details>` の `open` 属性など）
3. ARIA属性（`aria-expanded`、`aria-readonly`、`aria-selected` など）
4. `data-*` 属性

最初に検討するのは、擬似クラスです。`:checked`、`:disabled`、`:popover-open`、`:modal`、`:user-invalid` などは、ブラウザが状態を判定して付け外しするので、JavaScriptで管理する必要がありません。`required` 属性と `:required` のように、属性と擬似クラスのどちらでも選べる状態は、擬似クラスで選びます。

擬似クラスがない状態は、HTML要素の属性をセレクタにします。新しいタブで開くリンクを示す `[target="_blank"]` や、開いた `<details>` を示す `[open]` がこれにあたります。これらの属性は、ブラウザの動作を決めるためにHTMLへ書くものです。見た目も同じ属性から決めれば、動作と見た目が食い違いません。

HTMLの属性でも表せない状態は、`aria-selected`、`aria-expanded`、`aria-current`、`aria-pressed` のようなARIA属性をセレクタにします。タブの選択やメニューの展開は、HTMLの要素だけでは表せず、ARIA属性で支援技術に伝える状態です。

```css title="🙆‍♂ Recommended: ARIA属性をそのままセレクタにする"
@scope (.scoped.tab-list) to (.scoped) {
  ._tab {
    border-block-end: 2px solid transparent;

    &[aria-selected="true"] {
      border-color: currentColor;
    }

    &:enabled:not([aria-selected="true"]):hover {
      @media (any-hover) {
        border-color: var(--border--base);
      }
    }
  }
}
```

ARIA属性をセレクタにすれば、支援技術に伝わる状態と見た目の状態が同じ属性から決まるので、両者がずれません。JavaScriptが属性の更新を忘れたら見た目も変わらないので、不具合にもすぐ気づけます。私は2020年ごろから、状態の管理は原則としてARIA属性とdata属性で行うと決めています。

次のデモでは、スクリプトはタブの `aria-selected` 属性を書き換えるだけで、クラスは付け外ししていません。タブを押すか、タブにフォーカスして左右の矢印キーを押すと、`aria-selected="true"` になったタブへ下線が移ります。選択していないタブにマウスを重ねると、薄い色の下線が出ます。

<Demo title='aria-selected="true" のタブに下線が付き、選択を移すと下線も移る' html={tabsHtml} css={tabsCss} js={tabsJs} widths={[]} />

子孫の状態によって祖先の見た目を変えるときは、`label:has(:checked)` や `:has(:focus-visible)` のように `:has()` を使います。状態のクラスを祖先に付けるJavaScriptは要りません。`:has()` の使い方は、第5章「[5-3 :has() で祖先と前の兄弟を選ぶ](/pseudo/has/)」で説明しています。

フォーカスを受けた子に応じて親の見た目を変えるときは、`:focus-within` と `:has(:focus-visible)` を使い分けます。`:focus-within` は、子孫のどれかが `:focus` に当てはまれば当てはまるので、ボタンをマウスでクリックしたときにも親が強調されます（MDN）。子のどれかにフォーカスした時点でグループ全体を強調してよいなら、これで足ります。ブラウザがフォーカスの表示を必要と判断する場合だけ親を強調したいなら、`&:has(:focus-visible)` と書きます。

ただし、`:focus-visible` は入力の手段を判定する擬似クラスではありません。仕様が示す目安では、ボタンをマウスでクリックしたときには当てはまりませんが、テキストの入力欄はクリックやタッチでフォーカスしたときにも当てはまります（Selectors Level 4）。入力欄の多いグループでは、`:has(:focus-visible)` と `:focus-within` の差はほとんどありません。ユーザーがフォーカスの常時表示を選んでいる場合は、クリックでフォーカスした要素も `:focus-visible` に当てはまるとされています。

HTMLの属性とARIA属性のどちらでも表せない状態だけを、`data-*` 属性で表します。たとえば、ページをスクロールしたらヘッダーの高さを縮める場合、縮んでいるかどうかは見た目のためだけにある状態で、支援技術に伝える意味はありません。こうした状態は `data-compact-mode` のような属性で定義し、JavaScriptで付け外しします。支援技術に伝える意味のない値を、ARIA属性にするわけにはいきません。

```css title="🙆‍♂ Recommended: HTMLの属性とARIA属性のどちらでも表せない状態は、data-* 属性で表す"
@scope (.scoped.site-header) to (.scoped) {
  :scope {
    min-block-size: 80px;

    &[data-compact-mode] {
      min-block-size: 56px;
    }
  }
}
```

画面に入ったことを示す `data-revealed` や、ポップオーバーを開いた向きを示す `data-placement="top"` も、同じく見た目のためだけにある状態です。一方、コンポーネントのバリエーションを表す `data-variant` は、状態ではありません。HTMLを書いた時点で決まり、操作によって変わらない値です。BEMのModifierは状態とバリエーションの両方を表していましたが、本書では、状態はこの節の優先順位で、バリエーションは `data-variant` で表します。バリエーションの書き方は、第9章「[9-1 命名規則](/notation/naming/)」で説明しています。

## カード全体をリンクにする

記事の一覧のカードでは、見出しだけでなくカードのどこを押しても記事へ移動させたいことがよくあります。いちばん簡単なのは、カード全体を `<a>` で包む方法です。しかし、この方法ではカードの中身すべてがリンクのテキストになり、スクリーンリーダーは日付やカテゴリーまで続けて読み上げます。カードの中にカテゴリーへのリンクを置きたくても、リンクの中にリンクは入れられません。

そこで、リンクは見出しの `<a>` だけにし、その `::after` をカードいっぱいに広げます。見た目の上ではカードのどこを押してもリンクが反応しますが、リンクのテキストは見出しだけです。

```css title="🙆‍♂ Recommended: 見出しのリンクの ::after をカードいっぱいに広げる"
@scope (.scoped.article-card) to (.scoped) {
  :scope {
    position: relative;
    isolation: isolate;

    &:has(._heading-link:focus-visible) {
      outline: 3px solid CanvasText;
      outline-offset: 3px;
    }
  }

  ._heading-link {
    &::after {
      content: "";
      position: absolute;
      inset: 0;
    }

    /* フォーカスリングはカードの外周に出すので、ベーススタイルの box-shadow を初期値に戻し、outline は色だけを透明にする */
    &:focus-visible {
      box-shadow: initial;
      outline-color: transparent;
    }
  }

  ._category-link {
    position: relative;
    z-index: var(--z--forwards);
  }
}
```

カードに `position: relative` を指定し、`::after` の配置の基準にします。フォーカスリングは、リンクの周りではなく `:has(._heading-link:focus-visible)` でカードの外周に出します。見出しのリンクにフォーカスしたとき、押せる範囲（カード全体）とリングの範囲が一致するからです。カードの中にほかのリンクを置くときは、`position: relative` と `z-index: var(--z--forwards)` で `::after` より手前に重ねます。

リンク自身のリングのうち、ベーススタイルで内側に描いた `box-shadow` は、`initial` で初期値の `none` に戻します。`outline` は `outline: none` で消さずに、色だけを透明にします。強制カラーモードでは `outline` の色がシステムカラーに置き換わるので、リングの形が残ります。私の案件のコードでは `outline: none` で消していましたが、本書のルール（「[8-3 グローバルに書いてはいけないもの](/reset/global-pitfalls/)」の `no-outline-none`）に合わせて、この書き方にしました。

この方法にも弱点があります。`::after` がカードの上に重なるので、カードの中の文章をドラッグして選択できません。以前の私は、この問題を避けるためにJavaScriptでカードのクリックを拾っていました。現在は、実装の手軽さとJavaScriptのない環境でも動くことを優先して、`::after` を広げる方法を使っています。
