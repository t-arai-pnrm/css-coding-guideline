実装を始める前に、デザインカンプからは読み取れないことをデザイナーと確かめておくと、手戻りが減ります。確かめるのは、デザインの共通のルール、カンプのない画面の幅での振る舞い、内容が変わったときの見せ方、状態の変化と動きの4つです。できれば、実装者がデザインをレビューする機会を設け、これらをまとめて話し合います。

カンプをデザイナーとの対話の出発点として扱う考え方は「[3-1 ピクセルではなく意図を再現する](/design-reproduction/intent/)」で説明しました。このページでは、その対話で何を確かめるかを具体的に挙げます。ページの最後に、確かめるときの質問の例を表にまとめています。

## デザインの共通のルール

最初に確かめるのは、デザインの共通のルールが言葉になっているかです。サイト全体で使う色、文字サイズ、余白の値と、それぞれをどういう場面で使うのかが決まっていれば、それをデザイントークンとして実装できます。ルールが決まっていないと、実装者はカンプに出てくる値を1つずつ拾うことになり、似ているが少し違う値が増えていきます。

ルールの一覧がなければ、一覧を用意してもらえないかを頼みます。デザインのファイルの中に、サイト共通の値と使いどころをまとめたページを作ってもらえると、実装者はそこを見ればよくなります。あわせて、ルールから意図的に外している箇所がないかも確かめます。意図的な例外を知らないと、実装者がルールに合わせて直してしまうことがあるからです。

確かめたルールは、CSSのカスタムプロパティとして、トークンのファイルにまとめます。トークンの一覧は、そのまま実装の側から見たデザインのルールの一覧になります。ルールにない値が必要な箇所は、トークンを増やさずに、その場に値を直接書きます。トークンの名前の付け方と、トークンにしない値の扱いは「[10-4 デザイントークン](/components/design-tokens/)」で説明します。

ルールを言葉にしてトークンに置き換える作業は、プロジェクトのデザインの言葉をコードに翻訳する、デザイナーとの最初の共同作業です。この作業を通して、デザイナーと実装者が同じ値を同じ名前で呼べるようになります。プロジェクトに余裕があれば、ルールを文書にしたデザインガイドを作ることも提案します。

## カンプのない画面の幅での振る舞い

カンプは、たいていスマートフォンとPCの2種類か、タブレットを加えた3種類の幅で作られています。しかし、Webページは、その間のすべての幅と、カンプより狭い幅や広い幅でも表示されます。カンプとカンプの間や、カンプの外側の幅での振る舞いは、実装者に「それらしく」任されがちで、食い違いの原因になります。

とくに迷いやすいのがタブレットの幅です。スマートフォンとPCのどちらのレイアウトに近づけるのか、その幅だけの調整を入れるのかは、デザイナーの意図によって変わります。カンプより広い画面で、背景を画面の幅いっぱいに広げるのか、内容の最大幅を広げるのかも、事前に確かめておきたい点です。

仕様書に「ブレイクポイントは768px」のような値が書かれていても、それはカンプの段階の値であり、レイアウトが崩れ始める幅とは限りません。ブレイクポイントは、何を保つか（本文の読みやすさ、画像の縦横比など）と、どこからを崩れとみなすかをすり合わせたうえで、実装したページを見ながら一緒に決めることを提案します。カンプの比率を保ってほしいと頼まれたときの答え方も含めて、「[13-7 カンプの幅で全体を拡大・縮小しない](/responsive/design-comp-pattern/)」で説明します。

幅による切り替えをどこで行うかは、実装の側でも検討が要ります。画面の幅ではなく、部品の置き場所の幅で切り替えるほうが適している場合もあります。切り替えの方法の選び方は「[第13章 レスポンシブデザイン](/responsive/)」で説明します。

## 内容が変わったときの見せ方

カンプは、ちょうどよい量の内容が入った状態で描かれています。しかし、公開して運用が始まると、内容は変わります。文章が極端に長いときや短いとき、1行のつもりの見出しが2行や3行になったとき、並べる要素が1つだけのとき、一覧の項目が1件もないときに、どう見せるかを確かめておきます。

これらが決まっていないと、想定していない内容が入ったときにレイアウトが崩れます。カードのタイトルが長くなったら高さをそろえるのか、内容に合わせて変えるのか。テキストがあふれたら折り返すのか、決まった行数で省略するのか。どちらを選ぶかで、CSSの書き方が変わります。

とくに、一覧の項目がないとき（エンプティステート）の見せ方は、デザインから漏れやすい部分です。何も表示しないと、ユーザーはページが壊れているのか、項目がないのかを区別できません。項目がないことを伝える文言を出すのか、一覧ごと非表示にするのかを、事前に決めておきます。内容の変化に強いレイアウトの書き方は「[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)」で説明します。

## 状態の変化と動き

リンクやボタンのホバーやフォーカス、スクロールに合わせて追従するヘッダー、要素が現れるときの動きは、静止画のカンプでは表しきれず、実装者に任されがちです。しかし、これらもデザインの一部です。ホバーのときの見た目をどうするか、どの要素をどう動かすかを確かめておきます。

動きは、言葉や数値だけでは伝わりにくい部分です。フェードインか下からのスライドインかといった動き方に加えて、速さの変化（イージング）や再生時間の印象は、人によって受け取り方が違います。参考になるサイトを挙げてもらい、実際の動きを見ながらすり合わせると、食い違いを防げます。動かすかどうかの判断と動きの設計は「[第18章 モーション](/motion/)」で説明します。

## 実装者がデザインをレビューする

ここまでの項目をまとめて確かめるために、実装を始める前に、実装者がデザインをレビューする機会を設けることを勧めます。デザイナーが実装の成果物をレビューするのと同じように、実装者も、コードを書く前にデザインをレビューします。

レビューの利点は3つあります。1つ目は手戻りが減ることです。実装の手間が極端に大きいデザインや、特定の幅ですぐに崩れるデザインを、実装を始めてから伝えるのではなく、事前に代わりの案と一緒に相談できます。2つ目は、互いの理解が深まることです。実装者はデザインの意図を知ることができ、デザイナーは自分のデザインの意図を説明する機会になります。3つ目は品質が上がることです。デザイナーがすべての実装の詳細を知っているとは限らないので、カンプからは見えない部分を実装者が指摘することで、デザインをよりよくできます。

レビューで決めた内容は、文書として残します。会議の文字起こしや要約をAIに任せれば、記録を残す手間も小さくなります。レビューは、デザインの欠点を探す場ではありません。デザイナーが考え抜いたデザインを尊重したうえで、一緒にプロダクトをよくするための場として使います。

## 確かめるときの質問の例

次の表は、ここまでの項目を確かめるときの質問の例です。プロジェクトに合わせて言い換えて使ってください。

| 確かめること | 質問の例 |
|---|---|
| デザインの共通のルール | デザインで使っている色、文字サイズ、余白の一覧をいただけますか。トークンとして定義しておくと、実装の正確さと速さが上がります。 |
| デザインの共通のルール | 共通のルールから意図的に外している箇所はありますか。分かっていれば、誤ってルールに合わせてしまうのを防げます。 |
| デザインの共通のルール | サイト共通の値と、それぞれの使いどころをまとめたページをデザインのファイルに作っていただけますか。 |
| カンプのない画面の幅 | タブレットの幅では、どのような表示を想定していますか。参考になるサイトがあれば教えてください。 |
| カンプのない画面の幅 | 1024pxあたりでは、PCとタブレットのどちらのレイアウトが意図に近いですか。この幅だけの調整を入れますか。 |
| カンプのない画面の幅 | ブレイクポイントは、実装したページで崩れ始める幅を一緒に確かめて決めてもよいですか。そのとき、何を優先して保ちますか。 |
| カンプのない画面の幅 | 1440pxより広い画面では、背景を画面の幅いっぱいに広げたり、内容の最大幅を広げたりしますか。 |
| 内容が変わったとき | このカードのタイトルがカンプの倍の長さになったら、カードの高さはそろえますか、内容に合わせて変えますか。 |
| 内容が変わったとき | テキストがあふれたら、すべて表示しますか。それとも3行で省略して「…」を表示しますか。 |
| 内容が変わったとき | この一覧の項目が1件もないときは、一覧ごと非表示にしますか。それとも「現在お知らせはありません」のような案内を出しますか。 |
| 状態の変化と動き | ボタンやリンクのホバーとフォーカスのときの見た目は、どのようなものを想定していますか。 |
| 状態の変化と動き | このアニメーションは、フェードインや下からのスライドインなど、どのような動きを想定していますか。参考になるサイトがあれば教えてください。 |
