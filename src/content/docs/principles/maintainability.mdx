CSSの書き方に迷ったら、コードの短さや共通化のしやすさよりも、ほかの人が読んで安全に直せるかどうかで選びます。そのために本書では、似た記述の重複を恐れず、共通化は同じものが3回現れてから考えます。反対に、必要な理由を説明できない宣言は1つも書きません。

保守しやすさを優先し、共通化を急がない理由を先に述べます。そのあとで、保守の妨げになりやすい不要な記述として、何にでも指定される `width: 100%`、デフォルト値の指定し直し、副作用のあるショートハンドを取り上げます。

## 公開後の運用期間

Webサイトは、公開したときが始まりです。お知らせの追加、ページの増設、デザインの部分的な変更など、公開後の更新と改修の期間のほうがずっと長く続きます。しかも、更新するのは最初に書いた本人とは限りません。スキルの違う人が、時間がたってから触ることを前提に考える必要があります。

CSSは、どれだけ丁寧に組んでも、運用するたびに少しずつ劣化していきます。「ここだけ変えたい」という修正が上書きを呼び、その上書きがさらに次の上書きを呼びます。劣化を完全に止めることはできないので、最初から「崩れにくく、崩れても直しやすい」書き方を選びます。

良いCSSの条件としては「予測しやすい」「再利用しやすい」「保守しやすい」「拡張しやすい」の4つがよく挙げられます。本書はこのうち「保守しやすい」を最も重視します。短く洗練されたコードは書いた本人には気持ちの良いものですが、その短さと引き換えに、読みやすさや変更のしやすさ、不要になったときの捨てやすさを失いがちだからです。

例外は、公開後に更新する予定のない短期のキャンペーンサイトなどです。こうしたサイトなら、記述を切り詰めたコードでもかまいません。ただし、更新しない予定だったサイトに後から改修が入ることもあるので、迷ったら保守しやすいほうを選びます。

## 共通化のタイミング

本書では、似た記述が重複することを許容します。2つのコンポーネントに同じような指定があっても、すぐには共通化しません。共通化を検討するのは、同じものが3回現れてからです。この考え方は「rule of three」と呼ばれます。

共通化を急がないのは、共通化したスタイルは影響範囲が広く、しかもその範囲が見えにくいからです。2か所で使っている共通のスタイルを、片方の都合で変えると、もう片方も一緒に変わります。それを避けるために修飾クラスや上書きを足していくと、共通化したはずのスタイルは分岐だらけになります。

とくに注意したいのが、見た目が似ているだけのものを共通化することです。商品のカードと記事のカードは、どちらも角丸の箱に画像と見出しが入っているかもしれません。しかし、載せる情報も、今後増えていく要素も、変更される理由も違います。

```css title="🙅‍♂ Not Recommended: 見た目が似ているカードを1つにまとめ、修飾クラスで分岐する"
/* 🙅‍♂ Not Recommended */
.card {
  padding: 16px;
  border-radius: 8px;
  background-color: #f5f5f5;
}

.card--product .card__price {
  font-weight: bold;
}

.card--article .card__date {
  font-size: 14px;
}

.card--article.card--featured .card__title {
  font-size: 24px;
}
```

このように1つにまとめると、商品のカードだけを変えたいときにも、記事のカードに影響しないかを毎回確かめる必要があります。どちらかのカードが不要になっても、共通の部分と絡み合っているので、安心して消せません。

```css title="🙆‍♂ Recommended: 別のコンポーネントとして書き、そろえたい値だけをトークンで共有する"
@scope (.scoped.product-card) to (.scoped) {
  :scope {
    padding: 16px;
    border-radius: 8px;
    background-color: var(--background--card);
  }

  ._price {
    font-weight: bold;
  }
}

@scope (.scoped.article-card) to (.scoped) {
  :scope {
    padding: 16px;
    border-radius: 8px;
    background-color: var(--background--card);
  }

  ._date {
    font-size: calc(14 / 16 * 1rem);
  }
}
```

`padding` と `border-radius` は重複していますが、これは意図したものです。それぞれのカードは、相手を気にせず変更したり削除したりできます。「カード類の背景色をまとめて変えたい」といった、そろって変わるべき値だけをトークンで共有します。トークンの設計は「[6-3 デザイントークン](/components/design-tokens/)」で説明します。

共通化の粒度は、大きめから始めます。たとえば「左に画像、右に文章」という配置が何度か出てきたからといって、その配置だけを部品にすると、似た配置を見つけるたびに部品が増えていきます。配置の共通点は部品の境界とは限らず、部品が散らばるほど、どれをどこで使うかを把握できなくなって破綻します。共通化するなら、商品の詳細や記事の一覧のように、役割が名前で言える単位にします。

同じものが3回現れたら、それらが見た目だけでなく役割まで同じかを確かめます。役割まで同じなら、コンポーネントやコンポジションとして切り出します。切り出す単位の考え方は「[6-1 コンポーネントの境界を守る](/components/boundaries/)」で扱います。最適化は、ひととおり書き終えてから行うくらいがちょうど良いと私は考えています。

## 不要な記述をしない

重複は許容しますが、不要な記述は許容しません。余計な宣言があるほど、ベーススタイル、コンポジション、コンポーネントの中の別のルールとぶつかったときに、どの値が勝つかが状況しだいになります。ぶつかった値を打ち消すために詳細度を上げる上書きが増え、修正のたびに手間が大きくなっていきます。

「なんとなく指定してみた」宣言は、設計の判断として共有されず、読む人には意図が分かりません。本書では、宣言ひとつひとつについて「なぜそれが必要か」を説明できる状態にします。以下では、とくによく見かける3種類の不要な記述を取り上げます。

### 何にでも `width: 100%` を指定しない

最もよく見かけるのが、とりあえず `width: 100%` を指定するものです。`div` や `p` のように、ブラウザのデフォルトスタイルで `display: block` になる要素は、`width` が初期値の `auto` のままで親の幅に合わせて広がります。`position: absolute` と `inset: 0` を指定した要素も、その時点で利用できる幅いっぱいに広がります。

`height: 100%` は、親の高さが明示的に指定されているときにしか期待どおりに動きません。親が `min-height` のように最小値だけを決めている場合には成り立たず、flexやgridのアイテムであれば、指定しなくても `stretch` で高さいっぱいに広がります。

```css title="🙅‍♂ Not Recommended: 何にでも width: 100% と height: 100% を指定する"
/* 🙅‍♂ Not Recommended */
.card {
  width: 100%;
}

.card::after {
  position: absolute;
  inset: 0;
  width: 100%;
  height: 100%;
  content: "";
}

.card__body {
  height: 100%;
}
```

これらは無意味なだけでなく、ブラウザ間の挙動の違いによる不具合の原因にもなります。過去には、Safariで `<summary>` の子要素に `width: 100%` を指定すると不自然な改行が起きたり、Firefoxで `height: 100%` を指定したサブグリッドの要素が不自然に詰まったりする事例がありました。`box-sizing` を初期値に戻したときや、左右のマージンが加わったときには、はみ出しの原因にもなります。

`width: 100%` が必要なのは、`display: block` にしても自然には広がらない `<img>` のような置換要素や、`<button>` のようなフォーム部品です。`min(320px, 100%)` のように、はみ出しを防ぐための `100%` も問題ありません。`inline-block` の要素を幅いっぱいに広げたいなら、`width: 100%` を足す前に、外側の表示形式を `block` に変えられないかを検討します。そうすれば、`vertical-align` によって下にできる隙間もなくなります。

子要素を親の高さにそろえたいだけなら、親に `display: block grid` を指定すれば、`stretch` によって子要素が高さいっぱいに広がります。

```css title="🙆‍♂ Recommended: 子要素を親の高さにそろえるなら、親をgridにする"
._card {
  display: block grid;
  min-block-size: calc(240 / 16 * 1rem);
}
```

この方法なら、親が `min-block-size` で最小値だけを決めている場合にも成り立ち、高さの固定を避けられます。Tailwind CSSの `w-full` や `h-full` も同じで、生成AIの出力ではとくに乱用されがちです。生成されたコードにこれらがあったら、1つずつ必要かどうかを確かめます。

### デフォルト値を指定し直さない

ここでいう「デフォルト値」は、CSSの初期値、ブラウザのデフォルトスタイル、リセットCSSの値、ベーススタイルの値をまとめたものです。`margin: 0` や、`div` への `display: block` を場当たり的に書いていたら、設計の一貫性が崩れているサインになりやすいです。最初の要素だけ上のマージンを打ち消したいなら、全体に付けてから打ち消すのではなく、`:not(:first-child)` や `* + *` で「2つ目以降にだけ付ける」設計にします。

ブレイクポイントなどで、いったん変えた値をデフォルト値に戻したいこともあります。その場合も、値を書き写さずに、`revert`、`revert-layer`、`unset`、`initial` のキーワードで戻り先を示します。

```css title="🙅‍♂ Not Recommended: デフォルト値を書き写して戻す"
/* 🙅‍♂ Not Recommended */
.prose ul {
  padding-left: 40px;
  list-style: disc;
}
```

```css title="🙆‍♂ Recommended: 戻り先をキーワードで示す"
._prose :where(ul) {
  padding-inline-start: revert;
  list-style-type: revert;
}
```

`revert` はブラウザのデフォルトスタイルの値に、`revert-layer` は1つ前のカスケードレイヤーの値に戻します。`unset` は継承するプロパティなら親の値を、しないプロパティなら初期値を使い、`initial` は常にCSSの初期値を使います。キーワードで書けば「戻した」という意図が読み取れ、どの段階の値に戻るのかも明確です。ただし、`display` の初期値は要素によらず `inline` なので、`div` に `display: initial` を指定するとインライン要素になります。戻り先の違いは「[2-1 カスケード・詳細度・継承](/cascade/cascade-basics/)」で説明します。

文字の色やフォント、行の高さのように `:root` や `body` で決めた値も、コンポーネントで指定し直さずに継承させます。指定し直すのは、そのコンポーネントで本当に変えたいときだけです。

### 副作用のあるショートハンドを乱用しない

ショートハンドは便利ですが、指定しなかったサブプロパティまで初期値に戻します。そのため、ほかの場所でロングハンドを使って積み上げた設定を、後から意図せずリセットしてしまうことがあります。

```css title="🙅‍♂ Not Recommended: 一部だけ変えたいのにショートハンドを使う"
/* 🙅‍♂ Not Recommended */
.figure {
  max-width: 480px;
  margin: 0 auto;
  background: white;
}
```

`background: white` は、`background-color` だけでなく、`background-image` や `background-size` などもまとめて初期値に戻します。別の場所で設定した背景画像があれば、それも消えます。`margin: 0 auto` は、左右の中央寄せのために、本来触る必要のない上下のマージンまで `0` にします。子要素の間にマージンで余白を入れるレイアウトの中に置くと、その余白を打ち消してしまいます。

```css title="🙆‍♂ Recommended: 変えたいサブプロパティだけをロングハンドで指定する"
._figure {
  max-inline-size: calc(480 / 16 * 1rem);
  margin-inline: auto;
  background-color: oklch(100% 0 0deg);
}
```

次のデモでは、子要素の間に余白を入れた記事の中で、図を中央に寄せています。`margin: 0 auto` のほうでは、図の上の余白が消えています。

<Demo title="margin: 0 auto は、上下の余白の指定まで打ち消す" html={centeringHtml} css={centeringCss} variant="neutral" />

`flex` のように、指定した値から別の値に置き換わるショートハンドにも注意します。`flex: 1` は `flex-grow: 1` と同じではなく、`flex-basis` を `0` にします。「`flex: 1` では何が1なのか分からない」という理由で `flex-grow: 1` に書き換えると、動きが変わります。`font` はさらに影響が大きく、`line-height` や `font-kerning` まで初期値に戻すので、リセットの目的以外では使いません。

すべてのショートハンドが悪いわけではありません。`inset` のように、すべての辺にまとめて値を与える用途では問題になりにくく、`border` も、`border-image` を初期値に戻す点を除けば、線の太さ、種類、色をまとめて決めるだけです。ほかの設定が入り込む余地のない擬似要素なら `background` を使っても困りません。避けるのは、一部だけを変えたいのに、影響範囲の広いショートハンドを使うことです。
