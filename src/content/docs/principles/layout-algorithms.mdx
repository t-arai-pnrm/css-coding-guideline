CSSは、プロパティと値の組を並べたものではなく、ブラウザが要素の大きさと位置を計算するためのアルゴリズムの集まりです。通常フロー、Flexbox、Grid、位置指定といったレイアウトの方式は、それぞれが別のアルゴリズムで、プロパティはそのアルゴリズムへの入力として読まれます。同じ `width: 1000px` が、要素の置かれた方式によって、守られる値にも、縮む出発点にも、無視される値にもなるのはこのためです。

指定が思いどおりに効かないときは、プロパティが壊れていると考える前に、その要素が今どの方式の中にあり、その方式でプロパティがどう働くかを確かめます。各方式の規則は第7章「[レイアウトの仕組み](/layout/)」で説明しているので、この節では、規則を調べるときの見方を示します。

## `width` が効かないと感じる理由

CSSを書き始めて最初に覚える宣言は、たいてい `color: blue` のようなものです。書いた値がそのまま文字の色になるので、CSSを「プロパティに値を書けば、そのとおりに表示される言語」と捉えたくなります。プロパティごとに「この値ならこう表示される」という対応を覚えていけば、CSSを書けるようになると考えるわけです。

ところが、大きさと位置に関わるプロパティでは、この捉え方が通用しません。リンクに `width: 1000px` を書いても、幅は変わりません。横並びのカードで同じ指定をすると、カードは画面の幅に収まるまで縮みます。グリッドの中の要素に `width: 50%` を書くと、親ではなく、要素が置かれたセルの半分の幅になります。

プロパティと値の対応表しか持っていないと、こうした振る舞いは「CSSは予測できない」という印象になります。印象のまま値を足し引きすると、見た目は合っても原因は残ります。効かない `width` に `display: block` を足し、それでも合わなければ `position: absolute` や `!important` を重ねるような修正は、どの宣言がなぜ効いているのかを誰も説明できないコードを残します。

## 方式ごとに別のアルゴリズムがある

ブラウザは、ページを表示するたびに、すべての要素の大きさと位置を計算します。この計算の手順を、レイアウトのアルゴリズムと呼びます。アルゴリズムは並べ方ごとに別のものが用意されていて、主なものに通常フロー、Flexbox、Grid、位置指定（`position: absolute` と `fixed`）があります。この並べ方の区別を、本書の第7章ではレイアウトの方式と呼び、MDNではレイアウトモードと呼んでいます。

要素がどのアルゴリズムで計算されるかは、主に2つの指定で決まります。1つは親の `display` の内側の値で、親が `display: block flex` なら子はFlexboxで、`display: block grid` ならGridで並びます。もう1つは要素自身の `position` で、`absolute` か `fixed` にした要素は、親がどの方式でも、その流れから外れて位置指定のアルゴリズムで置かれます。親が通常のブロックで、要素の `position` も初期値の `static` なら、要素は通常フローで並びます（「[7-1 レイアウトの基礎](/layout/fundamentals/)」）。

プロパティは、こうしたアルゴリズムへの入力です。アルゴリズムは入力を自分の規則で解釈し、使わない入力は無視します。`gap` を通常フローのブロックに書いても子の間が空かないのは、通常フローのアルゴリズムが `gap` を使わないからです。反対に、同じ入力を複数のアルゴリズムが使う場合は、アルゴリズムごとに別の意味として扱われます。

`color: blue` が期待どおりに働いたのは、`color` が方式に左右されないプロパティだからです。文字の色や `font-size` のように、文字と描画に関わるプロパティの多くは、どの方式の中でも同じように働きます。方式によって意味が変わりやすいのは、`width`、`margin`、`z-index` のように、大きさと位置と重なりを決めるプロパティです。

## 同じプロパティが方式ごとに違う意味を持つ

ここでは、よく話題になる `width` で比べます。本書のコードでは論理プロパティの `inline-size` で書きますが、横書きでは `width` と同じ向きの大きさなので、この節では `width` のまま説明します。

通常フローのインライン要素では、`width` は適用されません。`<span>` や `<a>` のような置換要素でないインラインボックスは、行の中を文字と一緒に流れる箱で、幅は中身の文字から決まるからです。リンクに書いた `width: 1000px` が何も変えないのは、行の中に箱を並べる計算が、幅を入力として使わないためです。画像のような置換要素や、`display: inline flow-root` の要素は、インラインでも幅を持てます。

通常フローのブロックでは、`width` は守られる値です。指定がなければブロックは親の幅いっぱいに広がりますが、`width: 1000px` を指定すると、親の幅と関係なく1000pxの幅を保ちます。親の幅が600pxしかなくても縮まず、親からはみ出します。通常フローでは、幅の指定が親の幅と合わないとき、幅ではなく行末側の `margin` の値を計算し直して帳尻を合わせるからです。

横に並べるフレックスアイテムでは、同じ `width` が伸び縮みの出発点になります。`flex-basis` が初期値の `auto` なら、Flexboxのアルゴリズムは `width` の値をアイテムの仮の大きさとして使い、並べて足りなければ `flex-shrink` の比で縮めます。幅600pxのコンテナに `width: 1000px` のアイテムを1つだけ置くと、アイテムは600pxまで縮みます（デフォルトでは、中身の最小幅より小さくはなりません）。通常フローでは守られた値が、Flexboxでは、空間が足りなければ減らされる値になります（「[7-7 Flexboxの基礎](/layout/flexbox-basics/)」）。

`width: 50%` の基準も、方式で変わります。`%` の幅は、包含ブロックという矩形の幅に対する割合です。通常フローのブロックでは、包含ブロックはたいてい親の内容の領域なので、親の幅の半分になります。グリッドアイテムでは、アイテムを置いたグリッドエリアが包含ブロックになるので、`width: 50%` は親ではなく、そのエリア（1つのセルなら、そのセル）の幅の半分です（「[7-8 Gridの基礎](/layout/grid-basics/)」）。

`position: absolute` にすると、要素は通常フローから外れ、位置指定のアルゴリズムで置かれます。`static` の要素では無視される `inset`（`top` や `left` など）が、包含ブロックの辺からの距離として働くようになり、`%` の幅の基準も、`position` が `static` 以外のいちばん近い祖先に変わります。また、幅を指定していない要素は、左右の両方の位置を決めない限り、中身に合わせて縮みます（shrink-to-fit）。親の幅いっぱいに広がる通常フローのブロックとは、逆の振る舞いです（「[7-10 positionの基礎](/layout/positioning/)」）。

重なり順を決める `z-index` も同じで、通常フローの要素では、`position` を `static` 以外にしないと効きません。フレックスアイテムとグリッドアイテムでは、`position` が `static` のままでも効きます。`z-index` を効かせる目的で `position: relative` を足す習慣は、通常フローの規則をFlexboxとGridへ当てはめたものです（ルール [`z-index-on-items-without-position`](/layout-practice/layering/#rule-z-index-on-items-without-position)）。

ここまでの違いをまとめると、次の表のようになります。

| 要素が置かれた方式 | `width: 1000px` | `width: 50%` の基準 | `z-index` |
|---|---|---|---|
| 通常フロー（置換要素でないインライン） | 適用されない | 適用されない | `position` が `static` 以外のときだけ効く |
| 通常フロー（ブロック） | 1000pxのまま。親より広ければはみ出す | 親の内容の領域 | `position` が `static` 以外のときだけ効く |
| Flexbox（横に並べるフレックスアイテム） | 伸び縮みの出発点。足りなければ縮む | フレックスコンテナの内容の領域 | `position` がなくても効く |
| Grid（グリッドアイテム） | 1000pxのまま | アイテムが置かれたグリッドエリア | `position` がなくても効く |
| 位置指定（`absolute`） | 1000pxのまま | `static` 以外のいちばん近い祖先の `padding` の領域 | 効く |

## どの方式の中にいるかを先に確かめる

指定が効かないとき、まず問うのは、「このプロパティは壊れているのか」ではなく、「この要素は今どの方式の中にいて、その方式でこのプロパティはどう働くのか」です。プロパティそのものが壊れていることはめったになく、ほとんどの場合は、方式の規則どおりに振る舞っています（ルール [`identify-layout-mode-first`](/layout/fundamentals/#rule-identify-layout-mode-first)）。

確かめる順番は3段階です。まず親の `display` の内側の値を見て、要素が通常フロー、Flexbox、Gridのどれで並ぶかを確かめます。次に要素自身の `position` と `float` を見て、その流れから外れていないかを確かめます。最後に、そのプロパティがその方式で何を意味するかを、第7章の各節や、MDNのプロパティのページ（冒頭の説明と、公式定義の「適用対象」）で確かめます。

ブラウザの開発者ツールも、この確認に使えます。Chromeの開発者ツールは、正しい宣言でもほかの指定の都合で効いていないものを薄い文字で表示し、横のアイコンにその理由を示します（Chrome 108から）。Firefoxの開発者ツールにも、同じように効いていない宣言を示す機能があり（Firefox 70から）、インライン要素に書いた `width` には、インライン要素には効かないという理由が表示されます。

方式が分かると、直し方も変わります。リンクに幅を持たせたいなら、`width` の値を変えたり宣言を重ねたりせず、リンクを `display: inline flow-root` にして、幅を持てる種類の箱に変えます。フレックスアイテムが縮みすぎるときも、縮む量を決めているのは `width` ではなく `flex-shrink` と最小幅なので、最小幅の指定で守ります（「[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)」）。値を調整するより、その方式の規則に沿って指定を選び直すほうが、原因を取り除けることが多くあります。

## 補足と注意点

方式の規則を、書き始める前にすべて覚える必要はありません。前提として持っておくのは、方式が違えば同じプロパティの意味が変わる、ということです。この前提があれば、効かない指定に出会ったとき、調べる範囲を今の方式の規則へ絞れます。「[1-5 解決策を丸暗記しない](/principles/no-memorizing/)」で取り上げた画像の下の隙間も、画像が通常フローの行の中に置かれていることから生まれる現象です。

1つの要素が、2つの方式に関わることにも注意します。`display: block flex` の要素は、親の通常フローの中ではブロックとして積まれ、自分の子はFlexboxで並べます。要素自身の大きさを調べるときは親の方式を、子の並び方を調べるときは要素自身の `display` の内側の値を見ます。

この見方は、「[1-1 CSSはブラウザへの「提案」である](/principles/browser-suggestion/)」の考え方とつながっています。最終的な大きさと位置を決めるのはブラウザのアルゴリズムで、実装者が書くのは、そのアルゴリズムへの入力です。どのアルゴリズムが入力をどう使うかを知っていれば、固定値で結果を決めつけなくても、意図した範囲に収まる入力を選べます。
