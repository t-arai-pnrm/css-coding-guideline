この章では、本書のすべてのルールの土台になる考え方を扱います。結論を先に書くと、次の3つです。CSSはブラウザへの命令ではなく「提案」として書くこと。コードの短さや共通化よりも、保守しやすさを優先すること。そして、対象のブラウザをはっきり決め、そこから外れる新しい機能はプログレッシブ・エンハンスメントとして使うことです。

以降の章に出てくるルールの多くは、この3つのどれかから導かれています。たとえば「幅を固定しない」はブラウザに計算を任せるためで、「何にでも `width: 100%` を書かない」は余計な記述が保守の妨げになるためです。個々のルールの扱いに迷ったときは、この章の考え方に立ち返って判断してください。

私自身、以前は「デザインカンプを忠実に再現するのは実装者として当たり前」と考えていました。しかし、ユーザーの画面の幅や文字サイズの設定は無数にあり、カンプと同じ見た目を、すべての環境で保証するのは不可能です。今は、限られた環境で見た目を一致させるよりも、どの環境でも破綻しない落としどころを用意するほうが大切だと考えています。

もうひとつの背景は、Webサイトの寿命です。Webサイトは公開したときが始まりで、その後の更新や改修の期間のほうがずっと長く続きます。どれだけ丁寧に組んだCSSも、運用の中で少しずつ劣化していきます。そのため本書では、書いた本人以外が触っても壊れにくいことを何よりも重視しています。

この章は次の3つの節で構成しています。

- [1-1 CSSはブラウザへの「提案」である](/principles/browser-suggestion/)：固定値ではなく制約で考え、計算はブラウザに任せる理由と、ピクセルパーフェクトではなく合格点を目指す考え方
- [1-2 保守しやすさを最優先にする](/principles/maintainability/)：重複を恐れず共通化は3回目から考えることと、`width: 100%`、デフォルト値の指定し直し、副作用のあるショートハンドといった不要な記述をしないこと
- [1-3 ブラウザサポートとプログレッシブ・エンハンスメント](/principles/browser-support/)：Safariを基準にした対象範囲、プログレッシブ・エンハンスメントとして使える機能の見分け方、`@supports` と `scripting` メディア特性の使い方

固定値を避けてブラウザに任せる具体的な方法は、[第8章「レスポンシブデザイン」](/responsive/)で扱います。共通化の単位になるコンポーネントとコンポジションは[第6章「コンポーネントとカスタムプロパティ」](/components/)で、上書きの仕組みは[第2章「カスケードを制御する」](/cascade/)で説明します。想定外の内容に備えるディフェンシブCSSは「[7-3 変化に強いレイアウト](/layout/defensive/)」で、レビューとAIとの協働は「[12-2 レビューとAIとの協働](/operations/review-and-ai/)」で扱います。
