既存のサイトに本書の規約を入れるときは、全体を一度に書き換えず、新しく作るコンポーネントと、変更で手を入れる箇所から適用します。最初に入れるのは、守らないと表示が崩れる仕様上の制約と、Stylelintで検出できるルールです。命名やトークンのような本書の規約は、そのあとで順に足します。

既存のCSSとは、カスケードレイヤーで優先順位を分けて共存させます。既存のCSSを自分で読み込み直せるなら、`@import url("…") layer(vendors);` で `vendors` レイヤーに入れ、新しいCSSを後ろのレイヤーに書きます。読み込み方を変えられないなら、レイヤーを使わずに読み込む順番で分類を保ちます。Stylelintも、新しいCSSを置くディレクトリから適用し、既存のCSSは書き換えたファイルから検査の対象に戻します。

## 何のために段階的に導入するか

段階的に導入する目的は、既存の表示を変えずに、新しく書くCSSだけを本書の規約にそろえることです。全体を一度に書き換えると、変更の差分がサイト全体に広がり、どのページの表示が変わったのかをレビューで確かめきれません。既存のサイトは、運用しながら機能を足していくことが多く、書き換えのためだけに更新を止める期間を取れない場合もあります。

一方で、新しく書くCSSを既存の書き方に合わせ続けると、規約の違う部分はいつまでも減りません。そこで、規約を適用する範囲を「新しく書く部分」と「すでにある部分」で分け、境界をレイヤー、`@scope`、Stylelintの設定で表します。境界がコードに書かれていれば、どのファイルが新しい規約で書かれているのかを、人とAIが同じ方法で判断できます。

## 規約を適用する範囲

規約は、新しく作るコンポーネントから適用します。{/* 要確認: 出典なし */}新しいコンポーネントには既存のコードとの差分がないので、規約に従って書いても、ほかのページの表示は変わりません。ルートに `scoped <名前>` を付け、`@scope (.scoped.<名前>) to (.scoped)` の中に書けば、既存のマークアップの隣に置いても、スタイルの範囲がそのコンポーネントの中に限られます。

次に適用するのは、機能の追加や修正で手を入れるページとコンポーネントです。{/* 要確認: 出典なし */}手を入れる以上、表示の確認とレビューは必要になるので、その機会に書き換えれば、確認の手間を書き換えのためだけに増やさずに済みます。反対に、変更の予定がない箇所は、規約と違っていても書き換えません。表示の確認だけが増え、得られるのは書き方がそろうことだけだからです。

この範囲の決め方は、規約ごとの導入の手順とも一致しています。「[9-3 @scopeとネストの使い分け](/notation/scope-and-nesting/)」でも、新しく作るコンポーネントから `@scope` で書き、既存のコンポーネントは手を入れる機会に書き換える順番を勧めています。

## 先に入れるルール

ルールには、根拠の種類を表す性質があります。CSS・HTML・ブラウザの振る舞いから導かれる「仕様上の制約」、状況で決まる「実装上の判断」、一貫性のために本書が選んだ「本書の規約」の3つです（「[本書の読み方](/introduction/how-to-read/)」）。既存のサイトに入れるときは、仕様上の制約から始めます。{/* 要確認: 出典なし */}守らないと表示や操作が崩れるので、チームの合意を待たずに理由を説明できるうえ、既存のコードで違反を見つけたときに直す理由もはっきりしているからです。

性質とは別に、Stylelintで検出できるかどうかも、入れる順番の目安になります。IDセレクタの禁止や論理プロパティのように設定で検査できるルールは、レビューで指摘しなくても、違反がその場で分かります。{/* 要確認: 出典なし */}置き換え先が1つに決まるルールはエラーに、人が選ぶルールは警告にすると、導入の初期でも作業を止めずに済みます（「[19-1 Stylelintでルールを守る](/operations/stylelint/)」）。

本書の規約は、そのあとに入れます。ただし、既存のCSSと新しいCSSの境界になるレイヤーの割り当てだけは、最初の段階で済ませます（次の見出し）。命名やトークンは、正しいかどうかではなく、チームで同じものを選んだかどうかで価値が決まるので、チームの既存の規約と見比べて、採用するものを決めてから入れます。採用しない規約があってもかまいません。そのときは、採用しないことと、代わりに使う書き方を、プロジェクトの規約の文書に書いておきます。

## 既存のCSSと共存させる

既存のサイトにレイヤーを入れるときに起きやすいのは、新しいCSSだけをレイヤーに入れて、既存のCSSをレイヤーの外に残す書き方です。レイヤーに入っていないスタイルは、詳細度に関係なく、すべてのレイヤーの中のスタイルに勝ちます。この書き方では、新しいコンポーネントのスタイルが、既存のCSSにある `ul li` のような弱いセレクタにも負けます。

```css title="🙅‍♂ Not Recommended: 新しいCSSだけをレイヤーに入れ、既存のCSSに負ける"
/* 🙅‍♂ Not Recommended */
@layer tokens, reset, base, vendors, compositions, pages, components, patterns, utilities;

@import url("./legacy/style.css");
@import url("./components/news-list.css") layer(components);
```

既存のCSSを自分のエントリーポイントから読み込めるなら、既存のCSSも1つのレイヤーに入れます。入れる先は、`vendors` にします。{/* 要確認: 著者の判断。既存のCSSの入れ先を vendors とすること */}`legacy` のような新しい名前を作らないのは、`@layer` と `layer()` に使う名前を先頭で宣言した9つに限っているからです（「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」）。`vendors` は `base` より後ろで、`compositions` と `components` より前にあるので、既存のCSSは新しいベーススタイルには勝ち、新しいコンポーネントには負けます。既存のページの表示を保ったまま、新しいコンポーネントのスタイルだけを優先できます。

```css title="🙆‍♂ Recommended: 既存のCSSを vendors に入れ、新しいコンポーネントを後ろのレイヤーに書く"
@layer tokens, reset, base, vendors, compositions, pages, components, patterns, utilities;

@import url("./tokens/colors.css") layer(tokens);
@import url("./legacy/style.css") layer(vendors);
@import url("./components/news-list.css") layer(components);
```

この例では、kiso.cssのようなリセットと、ベーススタイルをまだ読み込んでいません。既存のCSSが指定していないプロパティには、`reset` と `base` のスタイルがそのまま当たるので、既存のページの表示が変わるからです。{/* 要確認: 出典なし */}リセットとベーススタイルは、既存のページの表示を確かめられる段階で足します。

新しいコンポーネントは、`@scope (.scoped.<名前>) to (.scoped)` の中に書きます。既存のマークアップと同じページに置いても、`._item` のような子要素のセレクタは、このコンポーネントの中の要素にしか当たりません。既存のCSSを書いた人が同じクラス名を使っていても、`scoped` と名前の組み合わせを持つルートの外には届きません。

```css title="🙆‍♂ Recommended: 新しいコンポーネントを @scope で既存のマークアップから切り離す"
@scope (.scoped.news-list) to (.scoped) {
  :scope {
    display: block grid;
    gap: 16px;
  }

  ._item {
    padding-block: 12px;
    border-block-end: 1px solid;
  }
}
```

レイヤーが守るのは、コンポーネントが宣言したプロパティだけです。既存のCSSに `.content li { margin-block-end: 20px; }` のような指定があるとします。新しいコンポーネントをその `.content` の中に置くと、コンポーネントが `margin-block-end` を宣言していない限り、既存の値が当たります。こうした流れ込みは、表示を確かめて、コンポーネントの側で値を宣言して防ぎます。

既存のCSSを読み込み直せない場合もあります。CMSの本体やプラグインのCSS、ほかのチームが管理するテンプレートの `<link>` のように、自分で読み込み方を変えられないCSSです。この場合は、レイヤーを使わず、読み込む順番で9つの分類を保ちます（ルール `no-layers-with-unlayered-css`）。考え方は、19-6「CMSと共存する」で説明します。{/* 19-6 の公開後にリンクする: /operations/cms/ */}既存のCSSが強いセレクタや `!important` で新しいコンポーネントに流れ込み、直せない場合だけ、4-3の例外の書き方（`all: revert-layer !important` で遮断する方法）を使います。

## Stylelintを新しいコードから適用し、例外を記録する

Stylelintは、新しいCSSを置くディレクトリから適用します。既存のCSSを最初から検査すると、違反の数が多すぎて、新しく書いたコードの違反がその中に埋もれます。既存のCSSを置くディレクトリは `ignoreFiles` で検査の対象から外し、新しいディレクトリには本書の設定をすべて適用します。

```js title="stylelint.config.mjs（既存のCSSを検査から外す）"
export default {
  ignoreFiles: ['dist/**', 'node_modules/**', 'src/styles/legacy/**'],
  /* ... */
};
```

既存のCSSを外すのは、エラーを消すためではなく、検査する範囲を「規約で書いたコード」に合わせるためです。そのため、既存のファイルを書き換えたら、新しいディレクトリに移すか、`ignoreFiles` から外して、検査の対象に戻します。{/* 要確認: 出典なし */}`ignoreFiles` に残っているパスの一覧が、そのまま、まだ規約で書かれていないCSSの一覧になります。既存のCSSを当面は書き換えないものの、仕様上の制約に関わるルールだけは検査したい場合は、`overrides` でそのディレクトリに適用するルールを絞る方法もあります。

新しいコードの中で、ルールを守れない箇所が出ることもあります。既存のCSSが付けたクラス名に合わせる必要がある、既存のJavaScriptがIDで要素を探している、などの場合です。このときは、`stylelint-disable-next-line` とルール名で1行・1つのルールに絞り、直前のコメントに理由を書きます（ルール `disable-one-line-with-reason`）。理由に「既存のCSSとの互換のため」と書いておけば、既存のCSSを書き換えたときに、`stylelint-disable` で検索して外せる箇所を見つけられます。

## 規約を入れる順番

本書の規約は、新しいコンポーネントを1つ書くのに必要なものから入れます。{/* 要確認: 出典なし */}最初の段階では、すべてのCSSをいずれかのレイヤーに割り当て、Stylelintの `layer-name-pattern` を有効にします（「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」）。レイヤーの境界が決まらないと、新しいコンポーネントが既存のCSSに勝つかどうかが、ファイルごとに変わってしまうからです。

次に、コンポーネントの書き方をそろえます。命名は、`@scope` を書くのに欠かせないルートの `scoped <名前>` と子要素の `_` から始めます（「[9-1 命名規則](/notation/naming/)」）。カスタムプロパティは、1つのコンポーネントの中で完結する内部プロパティと状態の接尾辞から始め、公開プロパティはコンポーネントを複数の場所に置き始めてから足します（「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」）。

コンポーネントをまたぐ規約は、そのあとに入れます。デザイントークンは、書き写しの違いが起きやすい色と、値の積み増しが起きやすいz-indexから始めます（「[10-4 デザイントークン](/components/design-tokens/)」）。スタイルクエリのフラグは、同じ閾値のコンテナサイズクエリが並んでいるコンポーネントを1つ選んで、幅のフラグに書き換えるところから始めます（「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」）。

この順番は、規約ごとに書いた導入の手順をつないだものです。どの規約も、1つのコンポーネントの中で試せるものを先にし、ほかのコンポーネントやページに影響するものを後にしています。新しい規約を入れたら、プロジェクトの規約の文書に、採用した規約と始めた時期を書き足します。

## 補足と注意点

既存のCSSを `vendors` に入れると、既存のCSSの中にある `!important` の扱いが変わります。`!important` を付けた宣言では、レイヤーの順番が逆になり、前のレイヤーの宣言が後ろのレイヤーに勝ちます。既存のCSSの `!important` は新しいコンポーネントの `!important` より強いので、コンポーネントの側で `!important` を足しても勝てません。既存のCSSをレイヤーへ移す前は、`!important` を使っている箇所を検索し、新しいコンポーネントと重なるプロパティがないかを確かめます。

レイヤーに入れると、既存のCSSどうしの優先順位は変わりませんが、レイヤーの外にあった `<style>` 要素や、別の `<link>` で読み込んでいたCSSとの関係は変わります。既存のCSSを読み込む場所が複数あるときは、すべてを同じエントリーポイントに集めてから、`vendors` に入れます。1つでもレイヤーの外に残ると、そのCSSが新しいコンポーネントに勝ちます。

段階的な導入には、規約の違うコードがしばらく同じリポジトリに並ぶというコストがあります。既存のCSSを修正するときに、どちらの書き方に合わせるかで迷わないように、「`ignoreFiles` に入っているファイルは既存の書き方のまま直す」「新しいディレクトリのファイルは本書の規約で書く」と、ディレクトリで決めておきます。{/* 要確認: 出典なし */}AIにCSSを書かせるときも、どのディレクトリが新しい規約の範囲かを先に伝えます。
