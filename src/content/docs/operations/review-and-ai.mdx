レビューの指摘には、必ず理由と解決策をセットで書きます。指摘には `MUST`、`IMO`、`Q` のラベルを付け、直さなければならないものと、好みの提案と、質問を区別します。レビューを通したコードには、レビュアーも責任を負います。

本書は、人が読む本であると同時に、AIに読ませるドキュメントも兼ねています。ルールから、AI向けのルール集とClaude Codeのスキルを自動で作っています。AIにCSSを書かせるときは、書く前にルール集を読ませ、生成されたコードはStylelintとレビューの両方で確かめます。Stylelintが通っても、ルールを守っているとは限らないからです。

## レビューの指摘に書く内容

「この書き方はダメです」だけでは、レビューになりません。書いた人は、何が問題なのかも、どう直せばよいのかも分からないからです。指摘を受けた人が自分で調べ直すことになり、同じ誤りを別の場所で繰り返しやすくなります。

```md title="🙅‍♂ Not Recommended: 理由も解決策もない指摘"
<!-- 🙅‍♂ Not Recommended -->
width: 100% は要りません。
```

```md title="🙆‍♂ Recommended: 理由と解決策をセットにした指摘"
[MUST] `._panel` の `width: 100%` は削除してください。ブロックレベルの要素は、指定しなくても親の幅いっぱいに広がります。左右に `margin` が付くと、はみ出しの原因にもなります（`no-redundant-width-100`）。
```

理由を書くと、指摘の正しさをレビュイーが自分で確かめられます。本書のルールに当てはまる指摘なら、ルールのIDを添えます。IDは章の構成が変わっても変えないので、ルールの詳しい説明をすぐに引けます。

レビュイーが書いたCSSは、レビューを通した時点で、レビュアーも責任を負います。「書いた人の責任」として見逃した誤りは、後から自分のチームの問題になります。承認するときは、自分が書いたコードと同じ基準で見ます。

## 指摘の深刻度ラベル

指摘には、深刻度のラベルを付けます。`MUST` は、仕様やコーディング規約に反するもの、バグが起きているもの、将来深刻な問題になりそうなもの、使いやすさやアクセシビリティを損なうものです。

`IMO`（in my opinion）は、好みが入りうる提案です。レビューが教義的になりすぎないよう気をつけます。ユーザーやクライアントのメリットになりにくい趣味の指摘は、`IMO` として扱うか、レビューとは別の機会に伝えます。たとえば、私はFlexboxとGridの使い分けについて普段から発信していますが、挙動に問題がなければ、レビューでは基本的に指摘しません。

本書のルールとの関係は次のとおりです。`display` の2値構文や論理プロパティは、本書では「必須」や「推奨」のルールです。しかし、それはプロジェクトで本書の規約を採用していることが前提です。規約として合意したものへの違反は `MUST` ですが、合意していないプロジェクトで同じことを求めるなら、それは `IMO` です。私も、ほかの人が書くコードに、合意のない2値構文を強制はしていません。

`Q` は、意図が読み取れない記述への質問です。たとえば、理由の分からない `position: relative` や `z-index: 3` があっても、誤りと決めつけずに質問します。書いた人にしか分からない事情がある場合もあるからです。答えが「なんとなく」なら、その宣言は消せますし、正当な理由があれば、それをコメントに残してもらいます。

```md title="🙆‍♂ Recommended: 意図が読み取れない記述には質問する"
[Q] `._media` の `position: relative` は、どの要素の配置の基準にするためのものでしょうか。子要素に `position: absolute` が見当たらないので、不要であれば削除できそうです。
```

## 確認する順番

CSSをレビューするときの確認の順番は、私のテンプレートのスキルに次のように定めています。上にあるものほど、プロジェクト全体への影響が大きいものです。

1. 仕様とプロジェクトの規約に従っているか
2. デザイントークンを使っているか（[8-4 デザイントークン](/components/design-tokens/)）
3. 対象のブラウザで動くか（[1-3 ブラウザサポートとプログレッシブ・エンハンスメント](/principles/browser-support/)）
4. 不要な記述や副作用のある上書きがないか（[1-2 保守しやすさを最優先にする](/principles/maintainability/)）
5. グローバルのCSSに重い指定がないか（[6-3 グローバルに書いてはいけないもの](/reset/global-pitfalls/)）
6. 内容の変化に耐えられるか（[10-10 変化に強いレイアウト](/layout/defensive/)）
7. コンポーネントの境界を守っているか（[8-2 コンポーネントの境界を守る](/components/boundaries/)）
8. レスポンシブ対応の手段を正しい順番で選んでいるか（[12-1 検討する順番](/responsive/escalation/)）
9. コメントが「なぜ」を説明しているか（[7-5 コメントの書き方](/notation/comments/)）

インデントやプロパティの並び順は、この一覧に入れていません。整形はツールの仕事で、レビューで指摘するのは、自動化が機能していないときだけです。Stylelintの運用は「[18-1 Stylelintでルールを守る](/operations/stylelint/)」で説明しています。確認の項目をまとめた一覧は、付録D「[レビューのチェックリスト](/appendix/checklist/)」にあります。

指摘の強さは、レビュイーの習熟度に合わせて調整します。たとえば、デフォルト値に戻す `revert` や `unset` の使い分けは、`display` の初期値が `inline` であることのような基礎知識が前提になります。また、余白のトークンのように、レスポンシブの環境では単位の使い分けが絡んで二者択一で片付かないものは、あまり細かく指摘しません。

## AIに読ませるドキュメントとしての本書

本書は、AIのコーディングエージェントに参照させるドキュメントを兼ねています。そのために、ルールはすべて1か所のデータ（YAMLのファイル）で管理しています。各ページの「ガイドライン」、付録A「[ルール一覧](/appendix/rules/)」、AI向けのルール集とスキルは、どれも同じデータから作られます。ルールを変えると、`pnpm gen:ai` でAI向けの配布物も作り直します。

AIが古い書き方や誤った書き方をしがちなルールには、印を付けています。ページのガイドラインでは「AIが生成するコードで誤りやすいルールです」という注意が表示され、AI向けのルール集では、こうしたルールを先頭の「AIが誤りやすいルール」にまとめています。

本文の書き方にも、AIが読むことを前提にした約束があります。各ページは単体で意味が通るように書き、ほかのページに触れるときはリンクと一言の要約を添えます。ブラウザの対応状況のように時間で変わる記述には、確認した年月を書きます。コードを省略するときは `/* ... */` と書き、推奨のコード例はすべてStylelintで検証しています。

Claude Codeを使っている場合は、本書のリポジトリを手元に取得し、その中でスキル（`skills/css-coding-guideline/`）を作り直してから、自分のスキルのディレクトリからシンボリックリンクで参照します。公開URLが決まるまでは、ルール集（`rules.md`）の「詳細」は、各ページの原稿をローカルのファイルの絶対パスで指しています。このパスは、ルール集を生成した人の環境のものです。取得したままのルール集を使うと、スキルの手順にある「詳細を読む」で、存在しないパスを開くことになります。

```sh title="スキルを作り直して登録する"
cd /path/to/css-coding-guideline
pnpm install
pnpm gen:ai
ln -s /path/to/css-coding-guideline/skills/css-coding-guideline ~/.claude/skills/css-coding-guideline
```

`pnpm install` で生成スクリプトが使う依存関係を用意し、`pnpm gen:ai` でルール集とスキルを作り直します。作り直したルール集は、自分が取得したリポジトリの中の原稿を指します。リポジトリを別の場所へ移したときや、更新を取り込んだときも、`pnpm gen:ai` をもう一度実行します。

スキルには、使う場面、基本原則、必須の手順、返答の形式を書いています。手順は、ルール集を読み、関係するページの詳細を読み、書いてから最終確認をする、という流れです。返答の形式では、判断の根拠になったルールのIDを添えるように求めています。`llms.txt` は、公開後に提供する予定です。

ほかのAIツールでは、自分の環境で作り直したルール集（`rules.md`）を、プロジェクトの `AGENTS.md` や `CLAUDE.md` から参照させます。AIへの指示でも、「`no-vw-vh` に従って」のようにルールのIDで伝えると、どのルールのことかが正確に伝わります。

```md title="AGENTS.md（抜粋）"
## CSS

- CSSを書く前とレビューの前に、`/path/to/css-coding-guideline/skills/css-coding-guideline/rules.md` を読む。
- 「AIが誤りやすいルール」は必ず確認する。
- 判断の根拠には、ルールのIDを添える。
```

プロジェクトの事情は、本書のルール集とは別の文書に書きます。私のテンプレートでは、`CLAUDE.md` にコマンド、ディレクトリの構成、検証の手順を書き、CSSの規約は単位、不要な記述、コンポーネントの設計のように、話題ごとのファイルに分けています。CMSの案件では、ネストやモーションの規約を書き足し、「下位の手段を選ぶときは、上位の手段で満たせない理由を説明する」のように、AIに判断の理由を求める書き方もしています。

## AIが誤りやすいパターン

AIが生成するCSSには、よく見かける誤りがあります。本書で「AIが誤りやすい」の印を付けたルールは、大きく5つに分けられます（1〜5つ目）。6〜9つ目は、本書の設計の前提と食い違う考え方を持ち込む誤りです。

1つ目は、古い単位と記法です。`vh` や `vw`、`rgba()`、`display: flex` の1値の構文、`transform: translateX()`、`min-width` のメディアクエリなどです。2つ目は、詳細度で解決しようとする書き方です。上書きが効かない原因を調べずに `!important` を足したり、セレクタを重ねたりします。

3つ目は、不要な指定です。何にでも `width: 100%` を付ける、中央寄せに `margin: 0 auto` を使う、リセットCSSが済ませているリストの `padding: 0` を書き直す、といったものです。Tailwind CSSを使うと、`w-full` や `h-full` がとくに乱用されがちです。4つ目は、アクセシビリティを損なう指定で、`outline: none` や `list-style: none` が代表です。

5つ目は、仕組みの理解が必要な機能の誤用です。名前のないコンテナ、コンテナにした要素そのものを条件にしたクエリ、クエリの条件の中の `var()`、Sassの書き方をまねた `&__title` がこれに当たります。CMSのテーマに `@layer` を持ち込むのも、この仲間です。

6つ目は、「`@scope` はまだ使えない」という古い知識です。AIはこれを理由に、BEMの長いクラス名やCSS Modulesを選びがちです。{/* 要確認: 出典なし */}`@scope` の基本の動作はSafari 17.4で対応していて、機能全体も2026年3月にBaselineの「新たに利用可能」になりました（2026年9月確認）。本書の対象のブラウザはすべて対応しているので、コンポーネントは `@scope` で書きます（`scope-with-donut`）。

<Baseline id="scope" />

7つ目は、Tailwind CSSのユーティリティだけで組み、コンポーネントのクラスを書かない前提を持ち込むことです。{/* 要確認: 出典なし */}本書では、コンポーネントはクラスと `@scope` で作り、ユーティリティは `.-visually-hidden` のような単機能のクラスに限ります（`utility-single-purpose`）。私のテンプレートのAI向けの規約でも、明示的な要求がない限りTailwind CSSやCSS-in-JSは使わないと定めています（`no-unrequested-css-framework`）。

8つ目は、アンカーポジショニングやView Transitionsを「未対応」とみなし、位置の計算や画面の切り替えをJavaScriptで作り直すことです。{/* 要確認: 出典なし */}2026年9月時点で、`anchor-name` は2026年1月に、同じページの中のView Transitionsは2025年10月に、主要なブラウザの最新版がそろいました。本書の対象のSafari 18系でアンカーポジショニングが使えないのは事実です。それでも、未対応の環境向けの表示をCSSで用意すれば、プログレッシブ・エンハンスメントとして使えます（[10-7 positionの基礎](/layout/positioning/)、[17-8 View Transitionsで画面の切り替えをつなぐ](/motion/view-transitions/)）。「未対応」という判断は、対応状況を確かめてから受け入れます（`verify-support-claims`）。

9つ目は、レイヤーを使うプロジェクトで、`@layer` の外にスタイルを書くことです。レイヤーに入っていないスタイルは、詳細度に関係なくすべてのレイヤーに勝つので、決めたレイヤーの順番が崩れます（`no-unlayered-styles`）。5つ目のCMSの場合とは反対の誤りで、どちらもレイヤーの外のCSSが最も強いという仕組みを知らないことから起きます。詳しくは「[2-3 カスケードレイヤーで順位を決める](/cascade/layers/)」で説明しています。

9つの誤りとは別に、レイアウトの手法の選び方にも偏りがあります。AIは、配置をFlexboxで組み、要素を重ねるときは `position: absolute` を選びがちです。学習したコードにその書き方が多いからだと私は考えています。結果として、Gridなら親の1か所で決まる配置が、子要素の幅の計算に散らばります。レイアウトを書かせるときは、先に「配置は `grid-template-areas` で定義し、エリアに名前を付ける」と指示します。エリアの名前が付いた配置は、生成されたコードを読む側にとっても、デザインカンプと見比べやすくなります（[10-8 Gridから考える](/layout/grid-first/)）。

## AIが生成したコードの確認

AIが生成したCSSは、必ずStylelintを実行してから、レビューで確かめます。次のコードは、カードの一覧をAIへ書かせたときにありがちな例として、私が作ったものです。

```css title="🙅‍♂ Not Recommended: AIが生成しがちなカードの一覧"
/* 🙅‍♂ Not Recommended */
.card-list {
  container-type: inline-size;
  display: grid;
  gap: 24px;
  width: 100%;
  margin: 0 auto;
  padding: 0;
  list-style: none;

  &__item {
    transform: translateY(0);
  }

  &__link:focus {
    outline: none;
  }
}

@container (width >= 600px) {
  .card-list {
    grid-template-columns: repeat(3, 1fr) !important;
  }
}
```

本書のStylelintの設定で検査すると、報告されるのは3件だけです（2026年9月、Stylelint 17.15.0で確認）。エラーになるのは、`display: grid` の1値の構文と、セレクタの外へ置いた `@container` です。`width` は、物理プロパティとして警告されます。名前のないコンテナ、コンテナ自身を条件にしたクエリ、`margin: 0 auto`、`&__item`、`translateY()`、`outline: none`、`!important` は、どれも検出されません。

しかも、自動修正を使うと、`width: 100%` は `inline-size: 100%` に書き換わります。不要な宣言が、規約に沿った見た目のまま残るということです。lintが通ったことは、ルールを守っていることの証明にはなりません。lintで検出できないルールこそ、レビューで確かめます。

```css title="🙆‍♂ Recommended: ルールに沿って書き直したカードの一覧"
@scope (.scoped.card-list) to (.scoped) {
  :scope {
    container: --card-list / inline-size;
  }

  ul {
    display: block grid;
    gap: 24px;

    @container --card-list (inline-size >= calc(600 / 16 * 1rem)) {
      grid-template-columns: repeat(3, minmax(0, 1fr));
    }
  }
}
```

```html title="🙆‍♂ Recommended: 書き直したカードの一覧のHTML"
<div class="scoped card-list">
  <ul>
    <li><!-- ... --></li>
  </ul>
</div>
```

書き直したコードでは、ルートをコンテナにし、グリッドにする要素を1段内側の `ul` に分けています。コンテナにした要素は、自分の幅を条件にしたスタイルを受け取れないからです。コンテナには名前を付け、`container` ショートハンドで指定します。条件は `inline-size` とremの式で書きます（`container-name-required`、`container-shorthand`、`container-query-inline-size`）。条件が意図どおりに適用されるので、`!important` も要りません（`no-important-for-specificity`）。

`width: 100%`、`margin: 0 auto`、`padding: 0`、`list-style: none` は、どれも不要なので消しました。ブロックレベルの要素は幅いっぱいに広がり、リストの字下げとマーカーはリセットCSSが消しているからです（`no-redundant-width-100`、`no-redundant-defaults`）。意味のない `translateY(0)` と、フォーカスリングを消す `outline: none` も消しています（`no-outline-none`）。`&__item` のような連結は、素のCSSのネストでは意図どおりに動きません（`no-nesting-concatenation`）。子要素は、`@scope` の中で `li` のようなタイプセレクタで選びます（`type-selector-in-scope`）。

AIと一緒に作業するとき、私は次の流れを守っています。AIには、書く前にルール集を読ませ、書いた後にはlintとビルドを実行させます。エラーを隠すためにルールを無効にしたり、失敗を飛ばしたりすることは禁じています。人のレビューでは、lintで検出できないルール、とくに「AIが誤りやすい」の印が付いたルールを重点的に見ます。

AIの誤りを直したら、同じ誤りを繰り返さないように、プロジェクトの規約の文書に書き足します。私のテンプレートでは、修正を受けるたび、教訓のファイルを決まった形で更新し、次の作業の前に読み直しています。「`max-nesting-depth` に `ignoreAtRules` を使うと検査の穴になる」といった気づきも、規約や作業の記録に残してきました。直した内容が文書に残れば、次の指示でも同じ説明を繰り返さずに済みます。
