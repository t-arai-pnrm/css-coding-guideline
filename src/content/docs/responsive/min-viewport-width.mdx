幅が375px未満の画面では、スクリプトで `<meta name="viewport">` の `content` を `width=375` に書き換え、ビューポートの幅を375pxに固定します。ブラウザは375px幅のレイアウトを画面に収まるように縮小して表示するので、カンプに近い見た目のまま表示されます。CSSは320 CSS pxの幅でも内容が読めて操作できるように書き、見た目をカンプに合わせる調整は375pxまでに限ります。

スクリプトは外部ファイルにせず、`<meta name="viewport">` の直後にインラインで置きます。画面の幅の判定には、ブラウザのウィンドウ全体の幅を表す `window.outerWidth` を使います。ズームを止める指定は加えません。

## 375px未満の画面をCSSで支える手間

スマートフォンの画面の幅は、多くの機種で375px以上です。しかし、それより狭い画面も残っています。Galaxy Foldシリーズのような折りたたみ端末の閉じた状態の画面は300px前後で、iPadのSlide Overのように、ほかのアプリの上に狭いウィンドウでブラウザを開く使い方もあります。{/* 要確認: 出典なし（Slide Overのウィンドウの幅） */}

デザインカンプは、たいてい375pxを最小の幅として作られています。それより狭い幅では、横に並べたボタンが収まらなくなったり、見出しが1文字ずつ折り返したりします。内容がはみ出さず読めることはCSSで保証しますが、それより狭い幅でも見た目をカンプに近づけようとすると、使う人の少ない幅のために、コンポーネントごとに条件と確認の手間が増えます。

一方で、カンプに合わせる調整を375pxで止めると、狭い端末では、読めても見た目の整わないレイアウトが表示されます。見た目を整える手間をかけずに、狭い端末でも375pxを想定したレイアウトを見せる方法が必要です。

境目を375pxにするのは、スマートフォン用のカンプの幅としてよく使われる値だからです。カンプが360pxで作られている案件なら、同じ考え方で360pxを境にします。境目の値は、カンプの最小の幅にそろえておきます。

## スクリプトでビューポートの幅を固定する

`<meta name="viewport">` の `content` に `width=375` を指定すると、ブラウザは端末の幅にかかわらず、375pxの幅でページをレイアウトします。端末の画面のほうが狭ければ、レイアウトした結果を、画面に収まる大きさまで縮小して表示します。たとえば幅320pxの画面では、表示が約0.85倍に縮小されます。{/* 要確認: 出典なし（width の値と初期の拡大率の関係） */}

CSSだけで似たことをするなら、`body` に `min-inline-size: 375px` を指定する方法も考えられます。しかし、この方法では375px幅のレイアウトが画面からはみ出し、横スクロールで見ることになります。ビューポートの幅を固定すれば、はみ出さずに全体が画面に収まります。

ただし、`width=375` を常に指定すると、375pxより広い画面でも375pxでレイアウトされてしまいます。そこで、HTMLには通常どおり `width=device-width,initial-scale=1` を書いておき、画面が375px以下のときだけ、スクリプトで `width=375` に書き換えます。画面の幅が変わったときにも判定し直すので、折りたたみ端末を開いて画面が広がれば、元の指定に戻ります。

## コード例

次のスクリプトを、`<meta name="viewport">` の直後にインラインで置きます。`window.outerWidth` が375を超えていれば `width=device-width,initial-scale=1` を、それ以外なら `width=375` を `content` に設定します。値が変わるときだけ書き換え、ページの読み込み時と `resize` イベントのたびに判定します。幅がちょうど375pxの画面でも `width=375` になりますが、端末の幅と同じなので、表示は変わりません。

```html title="🙆‍♂ Recommended: meta要素の直後にインラインで置き、狭い画面だけビューポートの幅を固定する"
<script>
  (function () {
    "use strict";

    const viewport = document.querySelector('meta[name="viewport"]');
    if (!viewport) return;
    const MIN_WIDTH = 375;
    function onResize() {
      const value =
        window.outerWidth > MIN_WIDTH
          ? "width=device-width,initial-scale=1"
          : `width=${MIN_WIDTH}`;
      if (viewport.getAttribute("content") !== value) {
        viewport.setAttribute("content", value);
      }
    }
    window.addEventListener("resize", onResize);
    onResize();
  })();
</script>
```

判定に `window.outerWidth` を使うのは、ページのレイアウトとは別に、ブラウザのウィンドウ全体の幅を表す値だからです。ただし、ズームしたときの値はブラウザによって違います。MDNによると、ズームするとChromeはデフォルトのピクセルの大きさで数えた値を返すので、`outerWidth` は変わりません。Firefoxはズーム後のCSSのピクセルの値を返すので、デスクトップで大きく拡大すると、`outerWidth` も375を下回ります。

そのため、この判定だけで「端末そのものが狭いこと」と「ズームしていること」を見分けられるわけではありません。デスクトップのブラウザは、通常 `<meta name="viewport">` を反映しないので、`content` が書き換わっても表示は変わらないと考えられます。{/* 要確認: 出典なし（デスクトップのFirefoxが meta viewport を反映しないこと） */} WCAGの達成基準1.4.10（リフロー）が求める幅320 CSS px相当の表示は、スクリプトの判定に頼らず、CSSを320 CSS pxの幅でも崩れないように書いて保証します。

スクリプトは即時に実行する関数で包み、変数がほかのスクリプトの変数と衝突しないようにしています。`resize` イベントのたびに実行しますが、行うのは文字列の比較だけで、`content` を書き換えるのは値が変わるときだけです。そのため、イベントの間引き（デバウンス）は入れていません。

インラインで置くのは、レイアウトシフトを防ぐためです。HTMLの解析中にインラインのスクリプトを見つけると、ブラウザはその場で実行してから続きを読みます。外部ファイルにして読み込みを待つと、その間に375px未満のレイアウトで描画が始まり、あとから固定したときに表示全体が組み直されます。

## 判定にinnerWidthを使わない理由

`window.innerWidth` は、ウィンドウのレイアウトビューポートの幅です。`outerWidth` がブラウザのウィンドウ全体（ツールバーや枠を含む）の幅であるのに対し、`innerWidth` はページを並べる領域の幅を、CSSのピクセルで表します。ページのレイアウトに直接関わるのは `innerWidth` のほうなので、こちらで判定したくなるかもしれません。

しかし、`innerWidth` で判定すると、2つの問題が起きます。1つ目は、一度固定すると元に戻れないことです。`width=375` に書き換えるとレイアウトビューポートの幅は375pxになり、`innerWidth` も375になります。その後に端末を横向きにして画面が広がっても、`innerWidth` は375のままで、条件を満たさないため、固定が解けません。

2つ目は、ズームでも判定が変わることです。ズームすると、CSSのピクセルで数えたウィンドウの幅が狭くなるので、`innerWidth` はどのブラウザでも小さくなります。`outerWidth` は、ページのレイアウトとは別に、ブラウザのウィンドウの大きさを表す値なので、1つ目の問題は起きません。2つ目の問題は、Chromeでは起きませんが、Firefoxでは `outerWidth` もズームで小さくなるので、避けられません。

## 補足と注意点

固定には代償があります。幅320pxの端末では表示全体が約0.85倍になるので、16pxの本文は約13.6pxの大きさで表示されます。375px未満の端末を使っている人にとっては、文字が小さくなります。それでも、横スクロールや重なった要素で内容を読めなくなるよりはよいと考えて、本書はこの方法を選んでいます。

固定した後もズームできるように、`maximum-scale` や `user-scalable=no` は加えません。この2つは、拡大して読む必要のあるユーザーがページを拡大できなくなる指定で、本書では入力欄での拡大を防ぐ目的でも使いません（「[16-3 フォーム部品](/interaction/forms/)」）。縮小された文字は、ピンチで拡大して読めます。

このスクリプトは `content` の値を丸ごと置き換えます。`viewport-fit=cover` や `interactive-widget` を指定するページでは、スクリプトの2つの値にも同じ指定を加えます（「[12-6 セーフエリアに対応する](/responsive/safe-area/)」）。HTMLに書く `content` も、スクリプトの値と同じ書き方（区切りの空白を入れない）にしておくと、読み込み時の不要な書き換えが起きません。コンテンツセキュリティポリシーでインラインのスクリプトを制限しているサイトでは、nonceかハッシュでこのスクリプトを許可します。

動作は、Chromeの開発者ツールのデバイスモードで確かめられます。デバイスモードはモバイルのブラウザと同じく `<meta name="viewport">` を反映するので、幅320pxの端末を選ぶと、375px幅のレイアウトが縮小されて表示されます。{/* 要確認: 出典なし（デバイスモードでの outerWidth の値） */} 縮小された表示で文字が読めるか、ボタンを押せるかは、できれば幅の狭い実機でも確かめます。あわせて、デスクトップのブラウザで400%に拡大し、320 CSS px相当の幅で内容がはみ出さないことも確かめます。

スクリプトは、CSSを狭い幅で崩れないように書く手間を省くものではありません。ズームで表示領域が320 CSS px相当になった場合、スクリプトによる固定は当てにできないので、その幅でも内容がはみ出さず読めるように書いておく必要があります。「[1-1 CSSはブラウザへの「提案」である](/principles/browser-suggestion/)」でデモを320pxの幅で確かめているのは、この幅でも崩れない書き方を示すためです。CSSは狭い幅でも崩れないように書き、見た目をカンプに近づける手間は375pxまでに限り、それより狭い実際の端末はスクリプトで救います。
