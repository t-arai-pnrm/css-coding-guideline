複数の場所に置かれるコンポーネントは、ビューポートではなく、置かれた場所の幅で切り替えます。そのための仕組みがコンテナクエリです。コンテナには必ず `--` で始まる名前を付け、`container` ショートハンドで `inline-size` を指定します。

コンテナにした要素は、幅を中身から決められなくなります。この副作用のため、コンテナにしてはいけない要素があります。この節では、基本の書き方とあわせて、その要素の見分け方を説明します。

## ビューポートの幅では足りない理由

画像と本文を並べたカードを考えます。メインエリアに置いたときは、幅に余裕があるので画像と本文を横に並べたく、サイドバーに置いたときは、幅が狭いので縦に積みたいという要件はよくあります。

メディアクエリでは、この要件を満たせません。メインエリアとサイドバーは同じページにあるので、ビューポートの幅はどちらも同じだからです。結局「サイドバー用」の修飾クラスを作り、置き場所ごとにスタイルを出し分けることになります。

```css title="🙅‍♂ Not Recommended: 置き場所ごとに修飾クラスで出し分ける"
/* 🙅‍♂ Not Recommended */
.media-card {
  display: grid;
}

@media (min-width: 768px) {
  .media-card {
    grid-template-columns: 160px 1fr;
  }

  .media-card--sidebar {
    grid-template-columns: 1fr;
  }
}
```

この方法では、置き場所が増えるたびに修飾クラスも増え、コンポーネントと置き場所が強く結びつきます。カードの配置を決める条件が、カード自身ではなく、カードを置く側の修飾クラスにあるためです。

コンテナクエリを使えば、カードは自分が使える幅だけを条件に配置を決められます。置き場所を知らなくても、どこに置かれても適切に配置されるコンポーネントになります。

コンテナクエリに対応していない環境では、`@container` の中のスタイルが適用されず、クエリの外に書いたスタイルだけが残ります。そのため、基本のスタイルは狭い幅で成り立つように書きます。広い幅でも狭いレイアウトのままになりますが、崩れではなく縮退に収まります。この考え方は、[9-3](/responsive/media-queries/) のモバイルファーストの書き方と同じです。

## 名前付きのコンテナを作る

コンテナクエリは、基準にする要素（コンテナ）の指定と、その幅を判定する条件の2つで書きます。基本の形は、コンポーネントのルートをコンテナにして、中の要素で条件を判定するものです。

```css title="🙆‍♂ Recommended: ルートをコンテナにし、中の要素で判定する"
@scope (.scoped.media-card) to (.scoped) {
  :scope {
    container: --media-card / inline-size;
  }

  ._layout {
    display: block grid;
    gap: 12px;

    @container --media-card (inline-size >= calc(400 / 16 * 1rem)) {
      grid-template-columns: calc(160 / 16 * 1rem) minmax(0, 1fr);
    }
  }
}
```

コンテナには必ず名前を付け、`@container` の条件でもその名前を指定します。名前を省略した `@container` は、いちばん近い祖先のコンテナを参照するので、コンテナが入れ子になると、どのコンテナを参照しているのかがコードから読み取れません。コンポーネントの内部に別のコンテナが足されただけで、判定の基準も変わります。

名前は `--media-card` のように `--` で始めます。近年のCSSでは、`anchor-name` のように、自分で付ける名前に `--` を求めるプロパティが増えています。すべての名前を `--` で始めておけば、プロパティごとに `--` が必要かどうかを覚えずに済み、自分で付けた名前だとすぐに分かります。将来CSSに新しいキーワードが追加されても衝突しません。本書のStylelintの設定では、`container-name-pattern` でこの形を検証しています。

コンテナの指定には、`container-type` を単体で書かず、`container` ショートハンドで名前と種類をまとめて書きます。名前と種類が1つの宣言に入るので、名前の付け忘れが起きません。また、条件には `width` ではなく `inline-size` を使います。物理方向の `width` は書字方向が変わると意味がずれるので、レイアウトの指定を論理プロパティでそろえるのと同じ理由で、書字方向に依存しない `inline-size` を選びます。

AIが生成するコードでは、次のように名前のないコンテナと `width` の条件の組み合わせをよく見かけます。動作はしますが、ここまでに挙げた点がすべて守られていません。

```css title="🙅‍♂ Not Recommended: 名前のないコンテナと width の条件"
/* 🙅‍♂ Not Recommended */
.media-card {
  container-type: inline-size;
}

@container (width >= 400px) {
  .media-card__layout {
    grid-template-columns: 160px 1fr;
  }
}
```

このコードでは、`.media-card` と `.media-card__layout` の間に別のコンテナが入ると、判定の基準がそちらに変わります。条件の値もpxなので、ユーザーが文字サイズを大きくしても切り替わる幅は変わりません。コンテナクエリを書くたびに、コンテナの名前、`container` ショートハンド、`inline-size`、remへの変換式の4点を確認します。

コンテナにした要素は、自分自身の幅を条件にしたスタイルを受け取れません。自分のサイズで自分のスタイルが変わると、判定が循環するからです。そのため、上のコード例のように、ルートをコンテナにして、配置を切り替える要素（`._layout`）を一段内側に置きます。

## 置き場所の幅でラベルを隠すシェアボタン

コンテナクエリで切り替えられるのは、配置だけではありません。アイコンと「この記事をシェアする」のようなラベルを並べたシェアボタンを、本文の下とサイドバーの両方に置く場面を考えます。本文の下では余裕があるのでラベルまで見せ、狭いサイドバーではラベルを隠してアイコンだけにしたいとします。1か所でしか使わないならメディアクエリでも書けますが、幅の違う複数の場所に置くなら、修飾クラスを足すか、置き場所ごとにコンポーネントを複製することになります。

```css title="🙆‍♂ Recommended: 置かれた場所が狭いときだけ、ラベルを視覚的に隠す"
@scope (.scoped.share-button) to (.scoped) {
  :scope {
    container: --share-button / inline-size;
  }

  a {
    position: relative;
    display: block flex;
    column-gap: 1em;
    justify-content: center;
    align-items: center;
    padding-block: 12px;
    padding-inline: 24px;
  }

  ._label {
    /* アイコン 24px・隙間 16px・ラベル 160px と、左右の余白が並ぶ幅 */
    @container --share-button (inline-size < calc((24 + 16 + 160 + 24 * 2) / 16 * 1rem)) {
      position: absolute;
      overflow: clip;
      inline-size: 4px;
      block-size: 4px;
      opacity: 0;
      pointer-events: none;
    }
  }
}
```

```html
<div class="scoped share-button">
  <a href="…" target="_blank" rel="external">
    <svg aria-hidden="true">…</svg>
    <span class="_label">この記事をシェアする</span>
  </a>
</div>
```

ラベルは `display: none` で消さずに、視覚的にだけ隠しています。アイコンのSVGは `aria-hidden="true"` で読み上げの対象から外しているので、ラベルまで消すと、リンクの名前がなくなるからです。隠し方は、ユーティリティの `.-visually-hidden` と同じ考え方です。ユーティリティはHTMLに付けるクラスで、クエリの条件によって付け外しできないので、同じ種類の指定をコンポーネントの中のクエリに書いています。ユーティリティについては「[7-2 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で説明しています。

コンテナにしているのは、リンクを包むルートの `<div>` です。コンテナにした要素には `padding` を指定しないので、余白や背景はリンクの側に指定します。閾値は、アイコン、隙間、ラベル、左右の余白が1行に並ぶ幅を式で書いています。次のデモで幅のボタンを768pxにすると、同じボタンが、本文の側ではラベル付きで、サイドバーではアイコンだけで表示されます。

<Demo title="同じシェアボタンが、置かれた場所の幅に合わせてラベルを隠す" html={shareHtml} css={shareCss} />

コンテナクエリでは、デザイナーとのやり取りが増えやすくなります。メディアクエリなら、切り替わる幅はページで共通なので、画面の幅ごとのカンプで確認できます。コンテナクエリでは、コンポーネントごとに切り替わる幅が違い、その幅はページのカンプからは読み取れません。{/* 要確認: 出典なし */}コンポーネントがどの幅でどう変わるのかは、実装の前にデザイナーと確認しておきます。確認する点は「[1-1 CSSはブラウザへの「提案」である](/principles/browser-suggestion/)」にまとめています。

## コンテナの副作用

`container-type: inline-size` を指定した要素には、インライン方向のサイズの封じ込め（`contain: inline-size`）が暗黙的に適用されます。これは「この要素の幅は、中身の大きさに影響されない」という指定です。中身の幅から自分の幅を決める要素に指定すると、中身が幅に反映されないため、幅が極端に小さく計算されてレイアウトが崩れます。

そのため、インライン要素や、`fit-content` など中身から幅が決まる要素は、コンテナにしません。`flex-grow` や `flex-basis` を指定していないflexアイテムと、`auto` のサイズで配置したgridアイテムも同様です。コンテナにするのは、親から幅を与えられる要素に限ります。

カードを一覧にして並べるときは、カードをgridやflexのアイテムにするだけでなく、その一段内側に注意します。コンテナにした要素は、自分の幅を条件にしたスタイルを受け取れないので、配置を変えたいカード自身をコンテナにすると、カード自身の配置は切り替わりません。一覧側でカードを `<li>` などの要素で包んでそれをコンテナにするか、カードのルート（`:scope`）をコンテナにして、配置を変える要素を一段内側に置きます。

コンテナにした要素には `padding` や `border` も指定しません。クエリの条件やコンテナ単位が基準にするのは、コンテナのコンテンツボックスの幅です。`padding` や `border` があると、要素の幅から、その分を引いた値で判定されるので、閾値やコンテナ単位の値が、見た目の幅とずれます。余白などのレイアウトは子要素に指定し、コンテナは幅の基準に専念させます。

`html`、`body`、ページ全体のレイアウト要素をコンテナにするのも避けます。ページ全体の切り替えはメディアクエリの役割だからです。また、以前の仕様では、コンテナにレイアウトの封じ込め（`contain: layout`）も暗黙的に適用されていました。そのため、コンテナは中にある `position: fixed` や `position: absolute` の要素の包含ブロックになり、スタッキングコンテキストも作っていました。固定したつもりのヘッダーやモーダルが、ビューポートではなくコンテナを基準に配置されていたわけです。

この仕様は制約が強すぎたため、2024年7月にCSSワーキンググループが、コンテナにはレイアウトの封じ込めを適用しないと決めました。ブラウザでは、Chrome 129（2024年9月）、Firefox 133（2024年11月）、Safari 18.4（2025年3月）で修正されています（2026年9月確認）。本書の対象のブラウザ（Safari 18系の最終版以降）では修正後の動作ですが、古い環境では従来の動作が残るので、`position: fixed` の要素を含むページ全体をコンテナにする理由もありません。

ほかにも、いくつか制約があります。`inline-size` や `size` などサイズ系の `container-type` を指定した要素では封じ込めが起こり、`subgrid` が無効になります。そのため、グリッドの親をコンテナにし、サブグリッド側の切り替えには `calc()` で求めた値を使います。`<picture>` の `<source>` にある `media` 属性はコンテナクエリを扱えないので、画像の切り替えはビューポートを基準にするしかありません。`container-type: size` は、インライン方向に加えてブロック方向にも封じ込めが起こり、高さが中身から決まらなくなります。高さを指定していない要素は、中身の高さが反映されず0に潰れるため、原則として使いません。

## コンテナ単位と名前の付け方

コンテナクエリには、コンテナの幅を基準にした単位（`cqi` など）もあります。`cqi` はコンテナのインライン方向のサイズの1%です。ただし、有効なコンテナが見つからないときは、小さいビューポートの単位（`svi`）として計算されます。コンポーネントのスタイルに `cqi` を書いても、置き場所にコンテナがなければ値の意味が変わります。

`cqi` を使うのは、名前付きのコンテナがあると言い切れる子孫の要素だけです。同じコンポーネントの中に `container: --name / inline-size` と、それを参照する `@container --name (…)` があることを確認してから使います。

`cqh` と `cqb` は高さ（横書きのブロック方向）を基準にするので、`container-type: size` のコンテナがないと小さいビューポートの単位として計算されます。`cqmin` と `cqmax` も、`inline-size` のコンテナだけでは片方の軸がビューポートの値になるので、コンテナを基準にするには `size` が要ります。本書は `size` を使わないので、これらの単位を使う場面はほとんどありません。`cqw` は横書きなら `inline-size` のコンテナでも使えますが、物理方向の単位なので、書字方向に追従する `cqi` を選びます。

クラス名にも注意が必要です。`container` プロパティが登場して、「container」はCSSの中で意味を持つ語になりました。`.container` という汎用のラッパーのクラスを作ると、コンテナクエリのコンテナなのか、ただの幅の制限なのかが分からなくなります。`container` プロパティを持つ要素にだけ、`.sidebar-container` のように何のコンテナかが分かる名前を付けます。`:scope` にコンテナを指定する場合は、クラス名は不要です。

想定の最小幅を下回ったときにコンポーネントを `zoom` で縮小して崩れを防ぐ方法もありますが、列数を減らす、折り返す、余白を詰めるといった通常の対応を試したうえでの最後の手段にとどめます。使う場合もコンポーネントのルートに限り、`1` を超えて拡大しません。
