レスポンシブ対応は、「静的 → イントリンシック → コンテナクエリ → メディアクエリ」の順に検討します。上の段階で解決できるなら、下の段階は使いません。クエリを書くのは、要素そのものの性質やブラウザのレイアウト機能では対応しきれなかったときだけです。

この順番を守ると、条件分岐の数が減り、想定していなかった幅や置き場所でも崩れにくいCSSになります。この節では、それぞれの段階が何を指すのかと、順番を守る理由を説明します。

## ブレイクポイントから考え始めると何が起きるか

よくある進め方は、最初に「375px、768px、1024px」のようなブレイクポイントを決め、要素ごとにメディアクエリで見た目を切り替える方法です。デザインカンプの幅がそのままブレイクポイントになるので、一見すると分かりやすく感じます。

```css title="🙅‍♂ Not Recommended: デバイスの幅を基準に列数を切り替える"
/* 🙅‍♂ Not Recommended */
.card-list {
  display: flex;
  flex-wrap: wrap;
}

.card-list__item {
  width: 33.333%;
}

@media (max-width: 1023px) {
  .card-list__item {
    width: 50%;
  }
}

@media (max-width: 767px) {
  .card-list__item {
    width: 100%;
  }
}
```

この書き方にはいくつか問題があります。まず、画面の幅の種類は数え切れないほどあり、決めたブレイクポイントの間の幅では、誰も見た目を確認していません。カンプどおりに見える3つの幅の間で、カードの中身がはみ出したり、不自然な余白ができたりしがちです。

また、メディアクエリが知っているのはビューポートの幅だけです。同じカードの一覧をメインエリアとサイドバーの両方に置くと、ビューポートの幅は同じでも、一覧が使える幅はまったく違います。ビューポートを基準にしている限り、この違いには対応できません。

そもそも、すべての環境で見た目を一致させるピクセルパーフェクトは目指せないものだと私は考えています。ビューポートの大きさ、画面の解像度、ユーザーが設定した文字サイズなど、表示を左右する変数はあまりにも多いからです。CSSはブラウザへの命令書ではなく「提案書」であり、最終的な表示を決めるのはユーザーの環境です。この考え方は「[1-1 CSSはブラウザへの「提案」である](/principles/browser-suggestion/)」で詳しく説明しています。

## 4つの段階

レスポンシブ対応を検討するときは、次の4つの段階を上から順に確認します。上の段階ほどコードが少なく、ブラウザに任せられる部分が大きくなります。

### 段階0：静的

最初に確認するのは、「その要素はそもそもレスポンシブにする必要があるのか」です。タグ、バッジ、ラベル、アイコン、装飾的な区切り線、固定サイズのアバターのように、本質的に大きさが決まっている要素は、画面の幅に合わせて変える必要がありません。

こうした要素に `clamp()` やクエリを足しても見た目はほとんど変わらず、コードの複雑さだけが増えます。アイコンであれば、`1em` を指定して文字サイズに追従させれば十分です。見出しの文字サイズが変われば、隣のアイコンも一緒に大きくなります。

```css title="🙆‍♂ Recommended: アイコンは文字サイズに追従させるだけにする"
._icon {
  inline-size: 1em;
  block-size: 1em;
}
```

すべての要素がレスポンシブである必要はありません。「大きさを変えなくても困らない要素」を最初に見分けておくと、その後の検討の対象がぐっと減ります。

### 段階1：イントリンシック

次に検討するのが、クエリを一切使わずに、要素自体が自然に適応する方法です。「イントリンシック」は「本来備わっている」という意味で、要素の中身やブラウザのレイアウトアルゴリズムが持っている伸び縮みの性質を活かします。

具体的には、`auto` や `fit-content` による自然なサイズ、`flex-wrap: wrap` による折り返し、Gridの `auto-fit` と `minmax()` による列数の自動調整があります。`clamp()`、`min()`、`max()` による流体的なサイズや、`max-inline-size` による上限の指定も、この段階の手段です。

たとえばボタンを横に並べるだけなら、`flex-wrap: wrap` を指定すれば、入りきらないボタンは自動で次の行へ回ります。ボタンの幅は中身の文字数で決まるので、幅の指定やブレイクポイントは要りません。

```css title="🙆‍♂ Recommended: 入りきらない要素は折り返しに任せる"
._actions {
  display: block flex;
  flex-wrap: wrap;
  gap: 8px;
}
```

レイアウトについては、コンポーネントに依存しない配置のパターン（コンポジション）を先に使えないか検討します。要素を並べる、積む、折り返すといった配置は、多くのコンポーネントで共通するからです。詳しくは「[6-2 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で説明します。

### 段階2：コンテナクエリ

イントリンシックな方法では表現できない切り替えが必要なら、コンテナクエリを検討します。たとえば「使える幅が広いときは画像と本文を横に並べる」のような、レイアウトの組み替えです。

コンテナクエリは、ビューポートではなく親要素の幅で条件を判定します。そのため、コンポーネントがどこに置かれても、その場所の幅に合わせて振る舞えます。書き方と注意点は「[8-2 コンテナクエリ](/responsive/container-queries/)」で説明します。

### 段階3：メディアクエリ

最後がメディアクエリです。ページ全体の段組み（1カラムと2カラムの切り替えなど）、モーダルやトーストのようにビューポートに固定される要素、常に画面幅いっぱいに表示されることが保証されたブロック（ヒーローヘッダーなど）は、ビューポートを基準にするのが自然です。

逆に言えば、それ以外の場面でメディアクエリを書きたくなったら、上の段階で解決できないかを疑います。ブレイクポイントの決め方は「[8-3 メディアクエリとブレイクポイント](/responsive/media-queries/)」で説明します。

## どの段階を使うかを見分ける

実際にコードを書くときは、次の問いを上から順に確認すると、使う段階を決めやすくなります。最初に「はい」と答えられた段階を使い、それより下の段階は使いません。

1. その要素の大きさは、画面の幅や置き場所によって変わらなくても困らないか（静的）
2. 折り返し、列数の自動調整、上限と下限の指定だけで、どの幅でも破綻しないか（イントリンシック）
3. 置き場所の幅によって、配置そのものを組み替える必要があるか（コンテナクエリ）
4. ビューポートそのものが判断の基準になるか（メディアクエリ）

迷いやすいのは、2番目と3番目の境目です。私は「幅が変わったときに、要素の並び順や組み合わせまで変わるか」で判断しています。列数が増減するだけならイントリンシックな方法で足り、画像と本文の位置関係が変わるような組み替えならコンテナクエリの出番という印象です。

この問いの順番は、AIにコードを書かせるときにも役立ちます。AIは、レスポンシブ対応を求められると、いきなりメディアクエリで書き始めることが多いからです。生成されたコードにクエリがあったら、1番目と2番目の問いで解決できないかを確認してください。

## クエリを使わないカードの一覧

先ほどのカードの一覧は、イントリンシックな方法で書き直せます。Gridの `repeat()` に `auto-fit` と `minmax()` を組み合わせると、1つの指定で列数がブラウザによって決まります。

```css title="🙆‍♂ Recommended: 列数をブラウザに任せる"
@scope (.scoped.card-list) to (.scoped) {
  :scope {
    display: block grid;
    grid-template-columns: repeat(auto-fit, minmax(min(100%, calc(200 / 16 * 1rem)), 1fr));
    gap: 16px;
  }
}
```

`minmax()` の最小値は、列の最小幅（200px相当）です。ブラウザは、この最小幅を下回らない範囲でできるだけ多くの列を並べ、余った幅は `1fr` で均等に分けます。最小幅は `calc(200 / 16 * 1rem)` とremで指定しています。ユーザーが文字サイズを大きくすると列の最小幅も広がり、窮屈さを感じる前に列数は減ります。

最小幅を `min(100%, …)` で包んでいるのは、一覧自体が200px相当より狭い場所に置かれたときのためです。これがないと、列の最小幅が親の幅を超え、横にはみ出します。次のデモで表示の幅を変えて、列数が変わる様子を確認してください。ブレイクポイントは1つもありません。

## 固定値を避ける

イントリンシックな方法を活かすには、幅と高さを固定しないことが前提になります。幅を `inline-size: 600px` と固定すると、それより狭い場所へ置かれたとき、中身がはみ出します。幅は `max-inline-size` で上限だけを決め、どうしても固定値が必要なときは `min(100%, …)` で、親より大きくならないようにします。

```css title="🙆‍♂ Recommended: 上限だけを決める"
._panel {
  max-inline-size: calc(600 / 16 * 1rem);
}

._thumbnail {
  inline-size: min(100%, 320px);
  aspect-ratio: 4 / 3;
}
```

高さも同じです。`height` を固定すると、内容が増えたときや、ユーザーが文字サイズを大きくしたときに中身があふれます。最低限の高さが必要なら `min-block-size` を、縦横比を保ちたいなら `aspect-ratio` を使います。

どの段階を優先するかは、スタイルを書くレイヤーによっても変わります。ページのレイアウトを書く `pages` レイヤーではメディアクエリを、コンポーネントを書く `components` レイヤーではコンテナクエリを優先します。コンポーネントは、自分がどこに置かれるかを知らないからです。ただし、モーダルやトーストのようにビューポートに固定されるコンポーネントは例外で、メディアクエリを使います。
