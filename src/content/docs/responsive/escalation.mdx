レスポンシブ対応は、「静的 → イントリンシック → コンテナサイズクエリ → メディアクエリ」の順に検討します。上の段階で解決できるなら、下の段階は使いません。クエリを書くのは、要素そのものの性質やブラウザのレイアウト機能では対応しきれなかったときだけです。

クエリが働くのは書いた幅の範囲だけですが、要素の性質やレイアウト機能はブラウザが実際の幅で計算します。そのため、この順番を守ると、想定していなかった幅や置き場所でも崩れにくく、条件分岐も少ないCSSになります。

## ブレイクポイントを先に決める進め方

よくある進め方は、最初に「375px、768px、1024px」のようなブレイクポイントを決め、要素ごとにメディアクエリで見た目を切り替える方法です。デザインカンプの幅がそのままブレイクポイントになるので、一見すると分かりやすい方法です。

```css title="🙅‍♂ Not Recommended: デバイスの幅を基準に列数を切り替える"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.card-list) to (.scoped) {
  :scope {
    display: block grid;
    gap: 16px;

    @media (width >= calc(768 / 16 * 1rem)) {
      grid-template-columns: repeat(2, minmax(0, 1fr));
    }

    @media (width >= calc(1024 / 16 * 1rem)) {
      grid-template-columns: repeat(3, minmax(0, 1fr));
    }
  }
}
```

この書き方には問題が2つあります。1つ目は、画面の幅が数え切れないほどあるのに、確認するのはカンプの3つの幅だけになりやすいことです。その間の幅では、カードの中身がはみ出したり、不自然な余白ができたりしがちです。

2つ目は、メディアクエリで判定できるのはビューポートの幅だけということです。同じカードの一覧をメインエリアとサイドバーの両方に置くと、ビューポートの幅は同じでも、一覧が使える幅はまったく違います。ビューポートを基準にしている限り、この違いには対応できません。

そもそも、すべての環境で見た目を一致させるピクセルパーフェクトは目指せないと私は考えています。ビューポートの大きさ、画面の解像度、ユーザーが設定した文字サイズなど、表示を左右する変数が多すぎるからです。CSSはブラウザへの命令書ではなく「提案書」であり、最終的な表示を決めるのはユーザーの環境です。この考え方は「[1-1 CSSはブラウザへの「提案」である](/principles/browser-suggestion/)」で説明しています。

## 4つの段階

検討する段階は次の4つで、上から順に確認します。上の段階ほどコードが少なく、ブラウザに任せる部分が大きくなります。

### 段階0：静的

最初に確認するのは、「その要素はそもそもレスポンシブにする必要があるのか」です。タグ、バッジ、ラベル、アイコン、装飾的な区切り線、固定サイズのアバターのように、本質的に大きさが決まっている要素は、画面の幅に合わせて変える必要がありません。

こうした要素に `clamp()` やクエリを足しても見た目はほとんど変わらず、コードの複雑さだけが増えます。アイコンであれば、`1em` を指定して文字サイズに追従させれば十分です。見出しの文字サイズが変われば、隣のアイコンも一緒に大きくなります。

```css title="🙆‍♂ Recommended: アイコンは文字サイズに追従させるだけにする"
._icon {
  inline-size: 1em;
  block-size: 1em;
}
```

すべての要素がレスポンシブである必要はありません。大きさを変えなくても困らない要素を最初に見分けておくと、その後に検討する要素が減ります。

### 段階1：イントリンシック

次に検討するのは、クエリを使わず、要素の中身とブラウザのレイアウトアルゴリズムだけで幅に合わせる方法です。「イントリンシック」は「本来備わっている」という意味で、要素とレイアウトアルゴリズムがもともと持つ伸び縮みの性質を使います。

具体的には、`auto` や `fit-content` による自然なサイズ、`flex-wrap: wrap` による折り返し、Gridの `auto-fit` と `minmax()` による列数の自動調整があります。`clamp()`、`min()`、`max()` による流体的なサイズや、`max-inline-size` による上限の指定も、この段階の手段です。読み物のように、要素が縦に流れる内容を複数の段に分けたいときは、CSSの段組み（`column-width`）も使えます。列の幅の下限だけを決めれば、段の数はブラウザが決めます。ただし、要素はブロック方向に順に流れ込み、高さを指定しなくても各段の高さがそろうようにブラウザが切れ目を決めます。どの要素がどの段へ移るかを作者が固定できないので、カードのように行をそろえたい並びには向きません。行や列をそろえたいときは、Gridの `auto-fit` を使います。

たとえばボタンを横に並べるだけなら、`flex-wrap: wrap` を指定すれば、入りきらないボタンは自動で次の行へ折り返されます。ボタンの幅は中身の文字数で決まるので、幅の指定は要らず、ブレイクポイントも不要です。

```css title="🙆‍♂ Recommended: 入りきらない要素は折り返しに任せる"
._actions {
  display: block flex;
  flex-wrap: wrap;
  gap: 8px;
}
```

レイアウトでは、コンポーネントに依存しない配置のパターン（コンポジション）が使えないかを先に検討します。要素を並べる、積む、折り返すといった配置は、多くのコンポーネントで共通するからです。詳しくは「[8-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で説明します。

### 段階2：コンテナサイズクエリ

イントリンシックな方法では表現できない切り替えが必要なら、コンテナサイズクエリを検討します。たとえば「使える幅が広いときは画像と本文を横に並べる」のような、レイアウトの組み替えです。

コンテナサイズクエリは、ビューポートではなく、コンテナにした祖先の要素の幅で条件を判定します。そのため、コンポーネントをどこに置いても、その場所の幅に合わせてスタイルが切り替わります。書き方と注意点は「[12-3 コンテナサイズクエリ](/responsive/container-size-queries/)」で説明します。

### 段階3：メディアクエリ

最後がメディアクエリです。ページ全体の段組み（1カラムと2カラムの切り替えなど）、モーダルやトーストのようにビューポートに固定される要素、常に画面幅いっぱいに表示されることが保証されたブロック（ヒーローヘッダーなど）は、ビューポートを基準にするのが自然です。

それ以外の場面でメディアクエリを書きたくなったら、上の段階で解決できないかを疑います。メディアクエリの書き方は「[12-4 メディアクエリ](/responsive/media-queries/)」で、ブレイクポイントの決め方は「[12-2 ブレイクポイントの決め方](/responsive/breakpoints/)」で説明します。

## 使う段階を決める問い

コードを書くときは、次の問いを上から順に確認します。最初に「はい」と答えられた段階を使い、それより下の段階は使いません。

1. その要素の大きさは、画面の幅や置き場所によって変わらなくても困らないか（静的）
2. 折り返し、列数の自動調整、上限と下限の指定だけで、どの幅でも破綻しないか（イントリンシック）
3. 置き場所の幅によって、配置そのものを組み替える必要があるか（コンテナサイズクエリ）
4. ビューポートそのものが判断の基準になるか（メディアクエリ）

迷いやすいのは、2番目と3番目の境目です。私は「幅が変わったときに、要素の並び順や組み合わせまで変わるか」で判断しています。列数が増減するだけならイントリンシックな方法で足り、画像と本文の位置関係が変わるような組み替えにはコンテナサイズクエリを使います。

どの段階を優先するかは、スタイルを書くレイヤーによっても変わります。ページのレイアウトを書く `pages` レイヤーではメディアクエリを、コンポーネントを書く `components` レイヤーではコンテナサイズクエリを優先します。コンポーネントは置き場所が1つに決まらないので、ビューポートではなく置かれた場所の幅を基準にする必要があるからです。ただし、モーダルやトーストのようにビューポートに固定されるコンポーネントは例外で、メディアクエリを使います。

この問いの順番は、AIにコードを書かせるときにも使えます。AIは、レスポンシブ対応を求められると、いきなりメディアクエリで書き始めることが多いからです。生成されたコードにクエリがあったら、1番目と2番目の問いで解決できないかを確認してください。

## クエリを使わないカードの一覧

先ほどのカードの一覧は、イントリンシックな方法で書き直せます。Gridの `repeat()` に `auto-fit` と `minmax()` を組み合わせると、1つの指定で列数をブラウザが決めます。

```css title="🙆‍♂ Recommended: 列数をブラウザに任せる"
@scope (.scoped.card-list) to (.scoped) {
  :scope {
    display: block grid;
    grid-template-columns: repeat(auto-fit, minmax(min(100%, calc(200 / 16 * 1rem)), 1fr));
    gap: 16px;
  }
}
```

`minmax()` の最小値は、列の最小幅（200px相当）です。ブラウザは、この最小幅を下回らない範囲でできるだけ多くの列を並べ、余った幅は `1fr` で均等に分けます。最小幅は `calc(200 / 16 * 1rem)` とremで指定しているので、ユーザーが文字サイズを大きくすると列の最小幅も広がります。1列に必要な幅が広がる分、列数が減り、カードが窮屈になりません。

最小幅を `min(100%, …)` で包んでいるのは、一覧自体が200px相当より狭い場所に置かれたときのためです。これがないと、列の最小幅が親の幅を超え、横にはみ出します。次のデモで表示の幅を変えると、ブレイクポイントなしで列数が変わります。

<Demo title="auto-fit と minmax() で列数が自動で変わるカードの一覧" html={gridHtml} css={gridCss} />

列の数をブラウザに任せる `repeat()` のキーワードには、`auto-fit` のほかに `auto-fill` もあります。どちらも、最小幅を下回らない範囲で入るだけの列を作ります。違いが出るのは、アイテムの数が入る列の数より少ないときです。`auto-fill` は、アイテムのない空の列をそのまま残すので、アイテムは1列分の幅のまま行の先頭に寄ります。`auto-fit` は、アイテムのない空の列を折りたたみます。折りたたまれた列は幅0の列として扱われ、両側の `gap` も1つ分なくなるので、残ったアイテムが `1fr` で行いっぱいに広がります。アイテムが列の数以上あれば、どちらも同じ見た目になります。

{/* 要確認: 出典なし */}どちらを選ぶかは、アイテムが少ないときにどう見せたいかで決めます。アイテムが1つや2つでも行いっぱいに広げたいなら `auto-fit` を、アイテムの数にかかわらず列の幅をそろえておきたいなら `auto-fill` を使います。検索結果のように件数が変わる一覧で、1件だけのカードが横長に引き伸ばされるのを避けたいときは、`auto-fill` のほうが向いています。

## 幅と高さの固定値

イントリンシックな方法は、幅と高さを固定しないことが前提です。幅を `inline-size: 600px` と固定すると、それより狭い場所に置かれたとき、要素が親からはみ出します。幅は `max-inline-size` で上限だけを決め、どうしても固定値が必要なときは `min(100%, …)` で、親より大きくならないようにします。

```css title="🙆‍♂ Recommended: 上限だけを決める"
._panel {
  max-inline-size: calc(600 / 16 * 1rem);
}

._thumbnail {
  inline-size: min(100%, 320px);
  aspect-ratio: 4 / 3;
}
```

高さも同じです。`height` を固定すると、内容が増えたときや、ユーザーが文字サイズを大きくしたときに、中身が要素からあふれます。最低限の高さが必要なら `min-block-size` を、縦横比を保ちたいなら `aspect-ratio` を使います。
