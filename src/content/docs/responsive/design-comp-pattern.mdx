狭い画面用と広い画面用の2サイズでデザインカンプが用意され、その比率を保った再現を求められる案件があります。こうした案件では、ビューポートの判定を1か所に集めた「画面モード」（`--screen`）と、カンプの寸法をそのまま書ける「比例スケール」（`--px` と `--rem`）を組み合わせると、コードの見通しがよくなります。

ただし、これは「[9-1 検討する順番](/responsive/escalation/)」の原則に対する例外です。どちらもビューポートを基準にする方法なので、置かれた場所の幅に合わせて表示を変えるコンポーネントには向きません。この節では、パターンの書き方と、使ってよい条件を説明します。

## 2サイズのカンプを通常の方法で再現するときの問題

Webサイト制作の現場では、幅375pxと幅1280pxのように、2つの幅のデザインカンプを渡されることがよくあります。カンプの間の幅は、比率を保って拡大・縮小してほしいという要望も珍しくありません。

この要望を通常の方法で実装すると、2つの問題が生じます。1つ目は、すべてのコンポーネントに同じブレイクポイントのメディアクエリが散らばることです。ブレイクポイントを変えるには、そのすべてのファイルを直さなければなりません。

2つ目は、寸法の変換の手間です。カンプの余白や文字サイズをすべて `clamp()` の流体値に変換していくと、式が増え、カンプとの対応が読み取りにくくなります。カンプに「40px」と書いてある値が、コードのどこにあたるのかを探す作業が生じます。

本書は、すべての環境で見た目を一致させるピクセルパーフェクトを目指さない立場です。それでも、カンプの比率を保つことが案件の要件として合意されているなら、その要件に最短で応える書き方を持っておく価値はあります。この節のパターンは原則を捨てるものではなく、要件がはっきりしている場面に限って使う手法です。

## 画面モード（`--screen`）の書き方

1つ目の問題は、ビューポートの判定を `:root` の1か所に集めて解決します。`:root` のメディアクエリで `--screen` というカスタムプロパティの値を決め、各所の分岐はその値を見るスタイルクエリで書きます。

```css title="🙆‍♂ Recommended: 画面モードを :root で決め、各所はスタイルクエリで分岐する"
:root {
  --screen: --compact;

  @media (width >= calc(768 / 16 * 1rem)) {
    --screen: --spacious;
  }
}

._heading {
  font-size: calc(24 * var(--rem));

  @container style(--screen: --spacious) {
    font-size: calc(40 * var(--rem));
  }
}
```

スタイルクエリは、コンテナのカスタムプロパティの値を条件にできるコンテナクエリです。サイズのクエリと違って、すべての要素が最初からスタイルクエリのコンテナになっているので、`container` の指定は要りません。`--screen` は `:root` から継承されるので、どの要素からでも同じ値を参照できます。

この形なら、ブレイクポイントの値は `:root` の1か所にしかありません。各所のコードは「広い画面のモードのとき」という意味で書かれ、具体的な幅を含みません。

モードの名前は `--compact` と `--spacious` のように、デバイスではなく状態を表す名前にします。`--sp` や `--pc` のようなデバイス名は、「[9-3 メディアクエリとブレイクポイント](/responsive/media-queries/)」で説明したのと同じ理由で使いません。名前を `--` で始めるのは、コンテナの名前や `@keyframes` の名前と同じく、自分で付けた名前だとひと目で分かるようにするためです。スタイルクエリの値として使う名前も、この規則にそろえます。

同じ考え方は、ページ全体ではなくコンポーネントの単位でも使えます。コンポーネントのルートでメディアクエリか名前付きのコンテナクエリを使って `--_density` のような値を決め、中の要素はスタイルクエリで分岐します。判定を1か所に集める点は、画面モードと同じです。

<Baseline id="container-style-queries" name="コンテナスタイルクエリ" />

スタイルクエリは、2026年5月にすべての主要なブラウザで使えるようになったばかりの機能です（2026年9月確認）。本書の対象のブラウザ（Safari 18系の最終版以降）では動作しますが、対応していない古いブラウザでは、スタイルクエリの中の指定がすべて無視されます。そのため、`--compact` の表示はクエリの外に基本のスタイルとして書き、`--spacious` との差分だけをスタイルクエリで書きます。こうしておけば、古いブラウザでもコンパクトな表示で内容を読めます。

## 比例スケール（`--px` と `--rem`）の書き方

2つ目の問題は、カンプの寸法をそのまま書ける比例スケールで解決します。画面の幅をカンプの幅で割った比率（`--zoom-scale`）を求め、それを掛けた `--px` と `--rem` を単位のように使います。比率を求める式は、長さどうしの割り算に対応したブラウザでしか計算できません。そのため、`--px` と `--rem` には比率が1のときの値を先に入れ、割り算に対応していることを `@supports` で確かめられたときだけ、比例の式に切り替えます。

```css title="🙆‍♂ Recommended: 画面の幅から比率を求め、単位のように使う"
@property --100svi {
  syntax: "<length>";
  inherits: false;
  initial-value: 0;
}

@property --1rem {
  syntax: "<length>";
  inherits: false;
  initial-value: 0;
}

:root {
  --100svi: 100svi;
  --1rem: 1rem;
  --window-width: calc(var(--100svi) / 1px * min(1, 16px / var(--1rem)));
  --zoom-scale: calc(var(--window-width) / 375);
  --px: 1px;
  --rem: calc(1 / 16 * 1rem);

  @supports (line-height: calc(1px / 1px)) {
    --px: calc(1px * var(--zoom-scale));
    --rem: max(1 / 16 * 1rem, 1 / 16 * 1rem * var(--zoom-scale));
  }

  @media (width >= calc(768 / 16 * 1rem)) {
    --zoom-scale: min(var(--window-width) / 1280, 1680 / 1280);
  }
}
```

式の各部分を説明します。`--window-width` は、画面の幅から単位を外した数値です。長さを長さで割る計算（`100svi / 1px`）で単位を打ち消しています（「[4-3 計算関数で根拠を式に残す](/values/math-functions/)」）。2026年10月の時点で、Firefoxの安定版はこの割り算に対応していません（158で対応する予定）。

割り算に対応していないブラウザでは、`--zoom-scale` を使った式が計算値の時点で無効になります。`--px` と `--rem` に比例の式を直接入れると、それを使った余白や文字サイズの宣言がすべて無効になり、余白のない、デフォルトの文字サイズの表示になります。`@supports` の条件の `calc(1px / 1px)` は、割り算に対応したブラウザでだけ数値として解釈されます。対応していないブラウザでは `--px` と `--rem` が比率1の値のまま残るので、拡大・縮小はしませんが、カンプどおりの寸法で表示されます。

`@property` で型を登録しているのは、`100svi` と `1rem` を `:root` の時点で絶対的な長さに変換し、子孫の要素に同じ値を引き継ぐためです。

`--window-width` の後半の `min(1, 16px / var(--1rem))` は、ユーザーが文字サイズを大きくしているときに、画面を実際より狭いものとして扱うための補正です。たとえば文字サイズを125%（20px）に設定しているユーザーでは、画面の幅を0.8倍として計算するので、`--px` で指定した余白は0.8倍に縮みます。余白を縮めて、大きくなった文字の分の場所を空けています。広い画面のモードでは、比率を1280pxのカンプに対して計算し直し、1680px相当で拡大を止めています。この `@media` は、`--screen` を切り替える `@media` と同じ条件なので、実際のコードでは1つの `@media` の中で `--screen` と `--zoom-scale` をまとめて切り替えます（あとのデモはこの形です）。

使うときは、カンプ上のピクセル値をそのまま掛けます。余白なら `padding: calc(20 * var(--px))`、2つの値の合計なら `calc((60 + 72) * var(--px))` のように、カンプとの対応を式で残せます。

文字サイズには必ず `--rem` を使います。`--rem` は `max()` によって、カンプ上の寸法をremで表した値（`1 / 16 * 1rem`）を下限にしています。そのため、ブラウザの文字サイズの設定を125%や200%にすると、文字はどの画面幅でも、カンプ上の寸法に設定の倍率を掛けた大きさを下回りません。`--rem` が保証するのはこの下限で、文字が設定と同じ割合で大きくなるわけではありません。

幅1600pxの画面で `calc(16 * var(--rem))` を計算すると、文字サイズの設定が16pxなら20px、20pxでも20px、32pxなら32pxになります。設定が16pxのときは、画面がカンプより広いので、比率によってすでに20pxに拡大されています。設定を20pxに上げると、先ほどの補正で比率が1に戻り、下限の20pxと同じ値になります。このように、幅の補正と文字の拡大が打ち消し合う区間では、設定を上げても文字は大きくならない場合があります。

下限を付けずに比率を掛けるだけにすると、この打ち消し合いがどの幅でも起き、文字サイズの設定を変えても文字の大きさが変わらなくなります（2026年9月、Chromeで確認）。文字の拡大は、WCAGの達成基準1.4.4が求める要件でもあり、文字サイズに `--px` を使ってはいけないのも同じ理由です。

ブラウザのズームにも注意が必要です。Chromeでは、`calc(24px / 1rem * 1rem)` のように長さどうしの割り算を含む式で定義した値が、ブラウザのズームで拡大縮小されません（2026年初めに確認）。`--px` と `--rem` の比率も同じ割り算から求めているので、ズームには追従しません。それでも下限が `rem` なので、ズームで表示を拡大した場合も、文字がカンプ上の寸法より小さくなることはありません。

使い回す部品は、`--px` や `--rem` が定義されていないページに置かれることがあるので、`var()` にフォールバックの値を書いておきます。フォールバックには、比率が1のときの値（`1px` と `calc(1 / 16 * 1rem)`）を使います。こうしておけば、比例スケールのないページに置かれても、カンプどおりの寸法で表示されます。このフォールバックが働くのは、変数が定義されていないときだけです。割り算に対応していないブラウザへの備えは、`:root` の `@supports` が受け持ちます。

```css title="🙆‍♂ Recommended: 使い回す部品ではフォールバックを書く"
._cluster {
  gap: calc(16 * var(--px, 1px));
  font-size: calc(14 * var(--rem, calc(1 / 16 * 1rem)));
}
```

## 使ってよい条件と注意点

このパターンを使うのは、2サイズのデザインカンプが用意され、その比率を保って再現することを関係者と合意している案件に限ります。ビューポートを基準にして全体を拡大・縮小する方法なので、「[9-1 検討する順番](/responsive/escalation/)」で説明したイントリンシックな方法やコンテナクエリの利点とは両立しません。サイドバーとメインエリアの両方に置かれる部品や、別のサイトでも使い回すコンポーネントでは、コンテナクエリを使います。

画面モードを使うなら、ビューポートのメディアクエリは `:root` の1か所だけにし、`--screen` と比例スケールの比率をそこでまとめて切り替えます。別の場所にもメディアクエリを書くと、判定が2か所に分かれ、1か所に集めた意味がなくなります。

広い画面のモードへ切り替わった直後の見え方にも注意が必要です。768px相当の幅では1280pxのカンプを0.6倍に縮小して表示するので、余白はカンプの6割になります。一方、文字は `--rem` の下限によってカンプ上の寸法より小さくならないので、この付近では余白に対して文字が大きめに表示されます。これは文字の読みやすさを優先した結果なので、デザイナーとは、この幅での見え方をあらかじめ共有しておきます。

スタイルクエリの条件も、ほかのクエリと同じく、各セレクタの中に書きます。`@scope` の直下に条件のブロックを置き、その中に宣言をじかに書くと、宣言やその後ろのルールは無視されることがあります。条件を各セレクタの中に書くという規約は、「[6-2 ネストとプロパティの並び順](/notation/nesting-and-order/)」で説明します。
