メディアクエリを使うのは、ページ全体の段組み、ビューポートへ固定した要素、常に画面幅いっぱいで表示されるブロックだけです。条件は `min-width` ではなく範囲構文で書き、ブレイクポイントはデバイスの幅ではなく、レイアウトが崩れる幅から決めます。値は `calc(640 / 16 * 1rem)` のように、ピクセル値をremに変換する式で書きます。

この節では、メディアクエリを使う場面と、ブレイクポイントの決め方と書き方を説明します。コンポーネントの中の切り替えは、先に「[9-2 コンテナクエリ](/responsive/container-queries/)」で書けないかを考えます。

## デバイスの幅で決めたブレイクポイントの問題

メディアクエリでよく見かけるのは、次のような書き方です。スマートフォン、タブレット、PCのようなデバイスの分類からブレイクポイントを決め、クラス名にも `sp` や `pc` を使っています。

```css title="🙅‍♂ Not Recommended: デバイスの分類と min-width で書く"
/* 🙅‍♂ Not Recommended */
.sp-only {
  @media screen and (min-width: 768px) {
    display: none;
  }
}

._main {
  @media screen and (min-width: 768px) {
    inline-size: 70%;
  }
}
```

現在、Webサイトが表示される画面の幅は2,000種類以上あると言われます。スマートフォンでも幅はまちまちで、折りたたみ端末もあり、PCのブラウザは好きな幅に変えられます。デバイスの分類は画面の幅の実態と一致せず、`sp` という名前のスタイルが大きなタブレットに当たるといったずれが、時間とともに増えていきます。

`.sp-only` や `.pc-only` のような表示を切り替えるクラスも、同じ理由で使いません。コードには、デバイスの名前ではなく、表示を変える条件を残します。

メディア特性の `device-width` と `device-height`（`device-aspect-ratio` も同様）も使いません。これらが調べるのは端末の画面そのものの大きさで、ブラウザのウィンドウが実際に使える幅ではありません。ウィンドウを狭めたり、分割表示にしたり、ズームしたりしても、`device-width` の値は変わらないため、レイアウトの判断に使えません。MDNも新しいプロジェクトでは避けるよう書いており、代わりに `width` を使います。

`min-width: 768px` と `max-width: 767px` を組み合わせる書き方にも問題があります。幅が767.5pxのように小数になると、どちらの条件にも当てはまらず、どのスタイルも切り替わらない隙間ができます。

## 範囲構文とremで書く

条件は、`>=` や `<` を使う範囲構文で書きます。範囲構文なら、条件を不等式としてそのまま読め、境界の値を含むかどうかも明確です。2つの境界の間は `(640px <= width < 1024px)` のように1つの条件で書けるので、`min-width` と `max-width` を組み合わせたときの隙間も生じません。

```css title="🙆‍♂ Recommended: 範囲構文で書き、閾値をremに変換する"
._layout {
  display: block grid;

  @media (width >= calc(720 / 16 * 1rem)) {
    grid-template-columns: minmax(0, 1fr) calc(240 / 16 * 1rem);
  }
}
```

ブレイクポイントの値はremで指定します。ユーザーがブラウザの文字サイズを大きくすると、同じ画面の幅でも1行に入る文字数が減り、実質的に使える幅が狭くなります。remで指定すれば、閾値の幅も文字サイズに比例して広がるので、文字サイズを大きくしたユーザーには早めに1カラムのレイアウトが適用されます。なお、メディアクエリの中のremは、CSSで `html` に指定した値ではなく、ブラウザの設定の文字サイズを基準に計算されます。メディアクエリの中では `em` も同じ基準で計算されるので、`em` で書いても閾値の挙動は変わりません。MDNは文字サイズの変更に配慮して `em` を勧めていますが、本書は `calc(N / 16 * 1rem)` の式に統一するため、`rem` を選んでいます。

値は `48rem` と書かずに、`calc(768 / 16 * 1rem)` のようにピクセル値からの変換を式で書きます。デザインカンプの値はピクセルで書かれていることが多いので、式にしておけば元の値をそのまま読み取れます。本書のStylelintの設定では、メディアクエリに範囲構文を使っているかを `media-feature-range-notation` で検証しています。

2つの閾値の間だけに当てはめる場合は、下限を含み上限を含まない形（`<=` と `<`）にそろえます。隣り合う範囲の境界の幅は片方の範囲だけに属するため、重複する幅と、どの範囲にも入らない幅は生じません。

```css title="🙆‍♂ Recommended: 2つの閾値の間を1つの条件で書く"
._banner {
  @media (calc(640 / 16 * 1rem) <= width < calc(1024 / 16 * 1rem)) {
    padding-inline: 24px;
  }
}
```

## 基本にするスタイルと広い画面の差分

メディアクエリを使うときは、狭い画面向けのスタイルを基本に書き、広い画面で必要になる差分だけをクエリの中に足します。いわゆるモバイルファーストの書き方で、クエリの条件は `width >=` の形が中心になります。

```css title="🙆‍♂ Recommended: 基本は狭い画面向けに書き、広い画面の差分を足す"
._nav-links {
  display: none;

  @media (width >= calc(768 / 16 * 1rem)) {
    display: block flex;
  }
}
```

狭い画面を基本にするのは、多くの場合、狭い画面のレイアウトのほうが単純だからです。1カラムに積んだ状態を基本にしておけば、広い画面で段組みを足す差分は小さく済みます。広い画面の複雑なレイアウトを基本にすると、狭い画面で打ち消すための指定が増えていきます。

条件付きのアットルールは、上のコード例のように各セレクタの中に書きます。条件のブロックをファイルやスコープの先頭にまとめて置くと、同じ詳細度の元のルールがその後ろに来たとき、後ろのルールが優先され、条件付きの指定が打ち消されてしまうからです。この規約は「[6-2 ネストとプロパティの並び順](/notation/nesting-and-order/)」で詳しく説明します。

## ブレイクポイントを決める幅

ブレイクポイントは、デバイスの幅ではなく「レイアウトが崩れる幅」から決めます。表示の幅を少しずつ狭めていくと、どこかで文字が詰まりすぎたり、要素が重なったり、余白のバランスが崩れたりします。その幅が、切り替えるべき幅です。

「2025年のブレイクポイントはこれで決まり」のような、その年に多い画面の幅から値を選ぶ記事を追いかける必要はありません。画面の幅の流行は毎年変わりますが、レイアウトが崩れる幅は、内容と配置が変わらない限り変わらないからです。この考え方は、メディアクエリとコンテナクエリに共通です。

ただし、Sassの変数やTailwind CSSの設定のように、ブレイクポイントをビルド時に展開される変数として持つフレームワークを使う案件では、独自の値を足さず、フレームワークの変数を使います。案件の中で値がばらばらになるのを避けるためです。

その幅は、できるだけ式で表します。たとえば本文の最小幅を560px、サイドバーを240px、その隙間を32pxとすると、2カラムにできるのは合計の832px以上です。`calc((560 + 240 + 32) / 16 * 1rem)` と書けば、この幅になる理由がコードに残り、サイドバーの幅を変えたときにどこを直せばよいかも分かります。

```css title="🙆‍♂ Recommended: 閾値を成り立つ条件の式で書く"
@scope (.scoped.card-group) to (.scoped) {
  :scope {
    container: --card-group / inline-size;
  }

  ul {
    display: block grid;
    gap: 24px;

    /* 最小幅 160px のカード 4 つと、24px の隙間 3 つが並ぶ幅 */
    @container --card-group (inline-size >= calc(160 / 16 * 1rem * 4 + 24 / 16 * 1rem * 3)) {
      grid-template-columns: repeat(4, minmax(0, 1fr));
    }
  }
}
```

この例では、「最小幅160pxのカードが4つと、24pxの隙間が3つ」並べられる幅を条件にしています。一度しか使わない複雑な式には、何列・何個分なのかをコメントで補足します。一方、根拠のない値を `calc(48rem)` のように包むだけでは、式にした意味がありません。

AIが生成するコードには、クエリの条件を使い回そうとして、条件の中に `var()` を書いてしまう誤りがよく見られます。

```css title="🙅‍♂ Not Recommended: コンテナクエリのサイズの条件に var() を書く"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.card-group) to (.scoped) {
  ul {
    --_column-width: calc(160 / 16 * 1rem);

    @container --card-group (inline-size >= calc(var(--_column-width) * 4)) {
      grid-template-columns: repeat(4, minmax(0, 1fr));
    }
  }
}
```

メディアクエリの条件では、カスタムプロパティを参照できません。条件の構文が `var()` を受け付けないので、その条件は成り立ちません。一方、コンテナクエリのサイズの条件では、現在の仕様の草案が `var()` を認めていて、値は問い合わせるコンテナの計算値で解決されます。ただし、仕様どおりに動くのはFirefoxだけで、ChromeとSafariは仕様のテストの一部にしか通りません（2026年9月、WPTで確認）。

上の例には、もう1つ問題があります。`--_column-width` を定義しているのは `ul` 自身ですが、条件の中の `var()` は、問い合わせるコンテナ（`--card-group`）の値で解決されます。コンテナに同じプロパティがなければ、仕様どおりに動くブラウザでも条件の結果は不明になり、スタイルは適用されません。

そこで本書では、メディアクエリとコンテナクエリのサイズの条件には、リテラルの値を書きます。対象のブラウザでそろって動かないことに加え、閾値がその場に書いてあれば、どの幅で切り替わるのかをすぐに確かめられるからです。{/* 要確認: 出典なし */}プロパティの値の中では、これまでどおり `var()` を使えます。スタイルクエリの `style(--a: var(--b))` のように、カスタムプロパティどうしを比べる条件は、仕様で認められていて主要なブラウザでも動くので、このルールの対象にしません。

<Demo title="本文とサイドバーの段組みを、成り立つ幅でだけ2カラムにする" html={pageHtml} css={pageCss} />

832px相当より狭いときは、サイドバーが本文の下に回ります。このデモのように、ページ全体の骨組みはメディアクエリで、その中に置くコンポーネントはコンテナクエリで切り替えるのが、本書の基本の役割分担です。

この役割分担は、部屋と家具にたとえると整理できます。部屋がページ（ほぼビューポート）で、家具がヘッダーや本文、サイドバーといったランドマークやセクションです。家具の配置や数、大きさは部屋の大きさで決まるので、ページ全体のレイアウト（マクロレイアウト）としてメディアクエリで扱います。家具の上に置くボタンやカードのようなコンポーネントの配置や数、大きさは、置かれた家具の大きさで決まります。こちらは部分のレイアウト（ミクロレイアウト）として、コンテナクエリで扱います。コンテナクエリが使えるようになっても、ページの骨組みを作るメディアクエリが不要になるわけではありません。

## メディアクエリを使う場面

メディアクエリを使ってよいのは、ページ全体の段組みの切り替え、モーダルやトーストのようにビューポートに固定される要素、そして常に画面幅いっぱいに表示され、ほかの場所に置かれることがないと言い切れるブロック（ヒーローヘッダーなど）です。どれも、ビューポートの大きさそのものが判断の基準になります。

モーダルやトーストにメディアクエリを使えるのは、マークアップ上のどこに書かれていても、表示されるときはビューポートを基準に配置されるからです。たとえば画面の下に固定するトーストなら、狭い画面では左右いっぱいに広げ、広い画面では右下に寄せるといった切り替えを、ビューポートの幅で判断するのが自然です。

ヒーローヘッダーのようなブロックは、「ほかの場所に置かれることがない」と言い切れるかどうかが分かれ目です。同じ見た目のブロックを記事の途中にも置く可能性があるなら、コンテナクエリで書いておくほうが安全です。ブロックの幅がビューポートの幅と一致しなくなり、ビューポートを基準にした切り替えが合わなくなるからです。

ビューポート単位（`svi` や `svb`）も、メディアクエリと同じ基準で使い分けます。ページ全体の余白やヒーローの高さのように、ビューポートに対して成り立たせたい値に使い、置き場所が変わるコンポーネントの中では使いません。単位の選び方は「[4-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」で説明します。

## ユーザーの環境を調べるメディア特性

メディアクエリは、画面の幅のほかに、ユーザーの入力手段や設定も調べられます。`prefers-reduced-motion` は動きの扱いを決めるためのもので[第14章「モーション」](/motion/)で、`any-hover` はホバーの扱いを決めるためのもので[第13章「インタラクション」](/interaction/)で説明します。ここでは、幅の代わりに使うことが多い `pointer` と、見落としやすい `prefers-contrast` と `prefers-reduced-transparency` を取り上げます。

操作の手段に合わせて変えたい指定を、画面の幅で判定してはいけません。幅の狭いデスクトップのウィンドウはマウスで操作され、幅の広いタブレットは指で操作されるからです。入力の精度は `pointer` と `any-pointer` で調べます。値は `fine`（マウスやトラックパッドのように精度が高い）、`coarse`（タッチのように精度が低い）、`none` の3つです。

`pointer` は主な入力だけを、`any-pointer` は使える入力のどれかひとつでも条件に当てはまるかを調べます。タッチ操作が主なタブレットにマウスをつなぐと、`pointer` は `coarse` のままですが、`any-pointer` は `coarse` と `fine` の両方に当てはまります。そのため、`pointer: fine` で判定すると、つないだマウスを取りこぼします。ホバーの判定に `any-hover` を選ぶ理由と同じで、本書は `any-pointer` を基本にします。

```css title="🙆‍♂ Recommended: 精度の高い入力があるときだけ、ドラッグ用のつまみを表示する"
._resize-handle {
  display: none;

  @media (any-pointer: fine) {
    display: block flow;
  }
}
```

<Baseline id="interaction" compatKey="css.at-rules.media.any-pointer" name="any-pointer メディア特性" />

`prefers-contrast` は、OSでコントラストを上げる、または下げる設定にしているかを調べます。値は `no-preference`、`more`、`less`、`custom` の4つです。`custom` は強制カラーモードの状態に当たります。ユーザーが選んだ配色で色が上書きされるので、色の指定は要りません。

薄い灰色の境界線や補助テキストで区別や意味を伝えている部品は、`more` のときに色を濃くします。`forced-colors` は配色を上書きするモードですが、`prefers-contrast: more` は配色を上書きせず、コントラストを上げてほしいという希望だけを伝えます。強制カラーモードに対応しただけでは、この設定のユーザーには薄い色が残ります。強制カラーモードの扱いは「[11-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」で説明します。

```css title="🙆‍♂ Recommended: コントラストを上げる設定のときに境界線を濃くする"
._field {
  border: 1px solid oklch(80% 0 0deg);

  @media (prefers-contrast: more) {
    border-color: oklch(40% 0 0deg);
  }
}
```

<Baseline id="prefers-contrast" name="prefers-contrast メディア特性" />

透明度についても、同じ考え方の `prefers-reduced-transparency` があります。OSで透明度を下げる設定（macOSとiOSの「透明度を下げる」、Windowsの「透明効果」をオフにする設定）にしているかを調べ、値は `no-preference` と `reduce` の2つです。半透明の背景や `backdrop-filter` のすりガラスの上に文字を置いた部品は、背景の写真や色によって文字が読みにくくなります。`reduce` のときは、背景を不透明にします。

```css title="🙆‍♂ Recommended: 透明度を下げる設定のときに背景を不透明にする"
._overlay {
  background-color: oklch(from var(--color--neutral--50) l c h / 70%);
  backdrop-filter: blur(12px);

  @media (prefers-reduced-transparency: reduce) {
    background-color: var(--color--neutral--50);
    backdrop-filter: initial;
  }
}
```

<Baseline id="prefers-reduced-transparency" name="prefers-reduced-transparency メディア特性" />

2026年10月の時点で、`prefers-reduced-transparency` に対応しているのはChrome系のブラウザだけです。対応していない環境では条件が成り立たず、半透明のまま表示されます。そのため、この指定に頼って読みやすさを確保するのではなく、半透明の状態でも文字と背景のコントラストが足りる色を選んだうえで、設定に応じてさらに読みやすくする指定として書きます。
