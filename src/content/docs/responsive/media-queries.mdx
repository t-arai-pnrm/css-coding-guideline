メディアクエリを使うのは、ページ全体の段組み、ビューポートへ固定した要素、常に画面幅いっぱいで表示されるブロックだけです。条件は `min-width` ではなく範囲構文で書き、ブレイクポイントはデバイスの幅ではなく、レイアウトが崩れる幅から決めます。値は `calc(640 / 16 * 1rem)` のように、ピクセル値をremに変換する式で書きます。

この節では、メディアクエリを使う場面と、ブレイクポイントの決め方と書き方を説明します。コンポーネントの中の切り替えには、先に「[8-2 コンテナクエリ](/responsive/container-queries/)」を検討してください。

## デバイスの幅で決めたブレイクポイントの問題

メディアクエリでよく見かけるのは、次のような書き方です。スマートフォン、タブレット、PCのようなデバイスの分類からブレイクポイントを決め、クラス名にも `sp` や `pc` を使っています。

```css title="🙅‍♂ Not Recommended: デバイスの分類と min-width で書く"
/* 🙅‍♂ Not Recommended */
.sp-only {
  display: block;
}

@media screen and (min-width: 768px) {
  .sp-only {
    display: none;
  }

  .l-main {
    width: 70%;
  }
}
```

現在、Webサイトが表示される画面の幅は2,000種類以上あると言われます。スマートフォンでも幅はまちまちで、折りたたみ端末もあり、PCのブラウザは好きな幅に変えられます。デバイスの分類は画面の幅の実態と一致せず、`sp` という名前のスタイルが大きなタブレットに当たるといったずれが、時間とともに増えていきます。

`.sp-only` や `.pc-only` のような表示を切り替えるクラスも、同じ理由で使いません。デバイスの名前ではなく「どういう条件で表示を変えるのか」をコードに残すことが大切です。

また、`min-width: 768px` と `max-width: 767px` を組み合わせる書き方には、小数の幅（767.5pxなど）でどちらにも当てはまらない隙間ができる問題もあります。条件の書き方そのものも見直す必要があります。

## 範囲構文とremで書く

条件は、`>=` や `<` を使う範囲構文で書きます。範囲構文なら、条件を不等式としてそのまま読めて、境界の値を含むかどうかも明確です。2つの境界の間は `(640px <= width < 1024px)` のように1つの条件で書けるので、`min-width` と `max-width` の隙間の問題も起きません。

```css title="🙆‍♂ Recommended: 範囲構文で書き、閾値をremに変換する"
._layout {
  display: block grid;

  @media (width >= calc(720 / 16 * 1rem)) {
    grid-template-columns: minmax(0, 1fr) calc(240 / 16 * 1rem);
  }
}
```

ブレイクポイントの値はremで指定します。ユーザーがブラウザの文字サイズを大きくしていると、同じ画面の幅でも1行に入る文字数が減り、実質的に使える幅が狭くなります。remで指定すれば、文字サイズを大きくしたユーザーには、早めに1カラムのレイアウトが適用されます。なお、メディアクエリの中のremは、CSSで `html` に指定した値ではなく、ブラウザの設定の文字サイズを基準に計算されます。

値は `48rem` と書かずに、`calc(768 / 16 * 1rem)` のようにピクセル値からの変換を式で書きます。デザインカンプの値はピクセルで書かれていることが多いので、式にしておけば元の値をそのまま読み取れます。本書のStylelintの設定では、メディアクエリに範囲構文を使っているかを `media-feature-range-notation` で検証しています。

2つの閾値の間だけに当てはめたい場合も、範囲構文なら1つの条件で書けます。下限を含み、上限を含まない形（`<=` と `<`）にそろえておくと、隣り合う範囲の境界で重なりや隙間が生まれません。

```css title="🙆‍♂ Recommended: 2つの閾値の間を1つの条件で書く"
._banner {
  @media (calc(640 / 16 * 1rem) <= width < calc(1024 / 16 * 1rem)) {
    padding-inline: 24px;
  }
}
```

## 狭い画面を基本に書く

メディアクエリを使うときは、狭い画面向けのスタイルを基本に書き、広い画面で必要になる差分だけをクエリの中に足します。いわゆるモバイルファーストの書き方です。クエリの条件も、`width >=` の形が中心になります。

```css title="🙆‍♂ Recommended: 基本は狭い画面向けに書き、広い画面の差分を足す"
._nav-links {
  display: none;

  @media (width >= calc(768 / 16 * 1rem)) {
    display: block flex;
  }
}
```

狭い画面を基本にするのは、多くの場合、狭い画面のレイアウトのほうが単純だからです。1カラムに積んだ状態を基本にしておけば、広い画面で段組みを足す差分は小さく済みます。反対に、広い画面の複雑なレイアウトを基本にすると、狭い画面で打ち消すための指定が増えていきます。

また、条件付きのアットルールは、上のコード例のように各セレクタの中に書きます。条件のブロックをファイルやスコープの先頭にまとめて置くと、同じ詳細度の元のルールが後ろに来たとき、上書きが効かなくなるからです。この規約は「[5-2 ネストとプロパティの並び順](/notation/nesting-and-order/)」で詳しく説明します。

## ブレイクポイントは内容から決める

ブレイクポイントは、デバイスの幅ではなく「レイアウトが崩れる幅」から決めます。表示の幅を少しずつ狭めていくと、どこかで文字の詰まりすぎ、要素の重なり、余白のバランスの崩れといった変化が起きます。その幅が、切り替えるべき幅です。

その幅は、できるだけ式で表します。たとえば本文の最小幅を560px、サイドバーを240px、その隙間を32pxとすると、2カラムにできるのは合計の832px以上です。`calc((560 + 240 + 32) / 16 * 1rem)` と書けば、「なぜこの幅なのか」がコードに残り、サイドバーの幅を変えたときにもどこを直せばよいかが分かります。

```css title="🙆‍♂ Recommended: 閾値を成り立つ条件の式で書く"
@scope (.scoped.card-group) to (.scoped) {
  :scope {
    container: --card-group / inline-size;
  }

  ._list {
    display: block grid;
    gap: 24px;

    /* 最小幅 160px のカード 4 つと、24px の隙間 3 つが並ぶ幅 */
    @container --card-group (inline-size >= calc(160 / 16 * 1rem * 4 + 24 / 16 * 1rem * 3)) {
      grid-template-columns: repeat(4, minmax(0, 1fr));
    }
  }
}
```

この例では、「最小幅160pxのカードが4つと、24pxの隙間が3つ」並べられる幅を条件にしています。閾値の考え方は、メディアクエリとコンテナクエリで変わりません。一度しか使わない複雑な式には、何列・何個分なのかをコメントで補足します。反対に、根拠のない値を `calc(48rem)` のように包むだけでは意味がありません。

ここで、AIが生成するコードで特によく見かける誤りがあります。クエリの条件を使い回すつもりで、条件の中に `var()` を書いてしまう例です。

```css title="🙅‍♂ Not Recommended: クエリの条件に var() を書く"
/* 🙅‍♂ Not Recommended */
._list {
  --_column-width: calc(160 / 16 * 1rem);

  @container --card-group (inline-size >= calc(var(--_column-width) * 4)) {
    grid-template-columns: repeat(4, minmax(0, 1fr));
  }
}
```

カスタムプロパティはプロパティの値を置き換える仕組みで、クエリの条件からは参照できません。この条件は無効になり、スタイルは適用されません。クエリの条件に必要な値は、最終的にリテラルの値で書きます。プロパティの値の中では、これまでどおり `var()` を使ってかまいません。

## ビューポートに関わるものだけに使う

メディアクエリを使ってよいのは、ページ全体の段組みの切り替え、モーダルやトーストのようにビューポートに固定される要素、そして常に画面幅いっぱいに表示され、ほかの場所に置かれることがないと言い切れるブロック（ヒーローヘッダーなど）です。どれも、ビューポートの大きさそのものが判断の基準になるものです。

モーダルやトーストがメディアクエリを使ってよいのは、どこに書かれていても、表示されるときはビューポートを基準に配置されるからです。たとえば画面の下に固定するトーストなら、狭い画面では左右いっぱいに広げ、広い画面では右下に寄せるといった切り替えを、ビューポートの幅で判断するのが自然です。

ヒーローヘッダーのようなブロックは、「ほかの場所に置かれることがない」と言い切れるかどうかが分かれ目です。同じ見た目のブロックを記事の途中にも置く可能性があるなら、ビューポートではなくコンテナクエリで書いておくほうが安全です。

なお、`prefers-reduced-motion` や `any-hover` のように、ユーザーの環境や設定を調べるメディアクエリは、この節の対象外です。これらはレイアウトの切り替えではなく、動きやホバーの扱いを決めるためのもので、[第11章「インタラクションとモーション」](/interaction/)で扱います。

ビューポート単位（`svi` や `svb`）も、メディアクエリと対で考えます。ページ全体の余白やヒーローの高さのように、ビューポートに対して成り立たせたい値に使い、置き場所が変わるコンポーネントの中では使いません。単位の選び方は「[3-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」で説明します。
