クラス名は5種類に分け、先頭の記号と名前の種類で見分けます。コンポーネントのルートは `class="scoped <名前>"`、コンポーネントの子要素は `._main-link` のように `_` で始め、ユーティリティは `.-visually-hidden` のように `-` で始めます。`.cluster` のようなコンポジション（配置のパターン）と、`.section-heading` のようなパターン（静的な見た目の断片）には、接頭辞を付けません。コンポジションには配置の名前を、パターンには役割の名前を付けて区別します。

どの種類でも、名前は見た目ではなく役割で付けます。`container` や `button` のように、HTMLやCSSで意味が決まっている語は、別の意味で使いません。また、`@keyframes` の名前やグリッドのエリア名のように、自分で付けて値として使う名前は `--` で始めます。

カスタムプロパティの名前の付け方は、第7章の「[7-4 公開プロパティと内部プロパティ](/components/custom-properties/)」で扱います。

## ページ全体で共有される名前の問題

CSSのクラス名は、ページ全体で共有される1つの名前空間に属します。別々のコンポーネントで同じ `.title` という名前を使うと、片方のために書いたスタイルがもう片方にも当たります。この衝突を避けるために広く使われてきたのが、BEMのように、コンポーネントの名前を子要素の名前の先頭に付ける方法です。

```css title="🙅‍♂ Not Recommended: 衝突を避けるためにコンポーネント名を繰り返す"
/* 🙅‍♂ Not Recommended */
.media-card__image {
  aspect-ratio: 16 / 9;
}

.media-card__title {
  font-size: 1.125rem;
}

.media-card--featured .media-card__title {
  font-size: 1.5rem;
}
```

この書き方で衝突は防げますが、代わりに名前が長くなります。子要素の名前に繰り返し現れる `media-card` は、衝突を避けるためだけの情報です。HTMLの `class` 属性も長くなり、どれがどの要素の名前なのかを読み取りにくくなります。

バリエーションを修飾子（`--featured`）で表すと、別の問題も起きます。修飾子の付いたルートから子要素を選ぶと、クラスが2つになるので、セレクタの詳細度が上がります。後から上書きするには、さらに詳細度の高いセレクタが必要です。名前で衝突を避ける方法には、名前の長さと詳細度の積み上がりという2つの問題があります。

## 5種類のクラス名

本書では、衝突を名前で避けるのではなく、`@scope` でスタイルの届く範囲を閉じ込めて防ぎます。範囲が閉じていれば、子要素の名前は `._main-link` のように短くてかまいません。そのうえで、クラス名を次の5種類に分け、先頭の記号と名前の種類で見分けられるようにします。

| 種類 | 書き方 | 例 |
|---|---|---|
| コンポーネントのルート | `scoped <名前>` | `scoped media-card` |
| コンポーネントの子要素 | `_` で始める | `._main-link`、`._nav-links` |
| ユーティリティ | `-` で始め、段階や種類は `--` で続ける | `.-visually-hidden`、`.-fluid-text--md` |
| コンポジション | 接頭辞を付けず、配置の名前にする | `.cluster`、`.switcher` |
| パターン | 接頭辞を付けず、役割の名前にする | `.section-heading`、`.icon` |

ルートの `scoped` は、そこからコンポーネントが始まるという目印です。`@scope (.scoped.media-card) to (.scoped)` と書くと、スタイルは `media-card` のルートから、内側にある次の `scoped` の要素（別のコンポーネントのルート）の手前までに届きます。`@scope` の書き方は、第2章の「[2-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で説明します。

`scoped` の後ろに続く名前は、kebab-caseを基本にします。PHPのテンプレートのように、ファイル名がkebab-caseの環境と、そのまま対応させられるからです。一方、Astroのようにコンポーネントの名前がPascalCaseの環境では、`scoped MediaCard` のようにコンポーネント名に合わせてもかまいません。どちらの場合も、ルートの名前からコンポーネントのファイルをたどれることが大切です。ページ固有のスタイルは、`scoped page-about` のように `page-` を付けたルートにまとめます（「[2-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」）。

子要素の `_` は、「このコンポーネントの中だけで意味を持つ名前」という印です。内部用のカスタムプロパティを `--_` で始めるのと同じ考え方で、外から触れるものではないことを示します。ただし、子要素のすべてにクラスを付けるわけではありません。スコープの中の要素は `ul` や `a` のようなタイプセレクタで選び、子要素のクラスは、同じ種類の要素を役割で区別するときと、意味を持たない `div` と `span` に役割を示すときだけ付けます。そのときは、`._main-link` と `._sub-link` のように、役割と要素の役割の語を組み合わせて名付けます。`._list` や `._link` のように要素の種類を言い換えただけの名前は付けません（「[7-1 コンポーネントの境界を守る](/components/boundaries/)」）。

ユーティリティの `-` は、どのコンポーネントからでも使える単機能のクラスであることを示します。`.-fluid-text--md` のように、段階や種類は `--` で続けます。コンポジションは、`.cluster`（折り返して並べる）や `.switcher`（幅に応じて横並びと縦積みを切り替える）のように、配置のパターンの名前をそのまま使います。パターンは、`.section-heading`（セクションの見出し）や `.icon`（文字に添えるアイコン）のように、繰り返し使う静的な見た目の断片に付けるクラスです。

コンポジションとパターンは、どちらも接頭辞を付けないので、記号では見分けられません。そこで、名前の種類で区別します。コンポジションは `stack`、`cluster`、`switcher`、`sidebar` のように、子をどう並べるかを表す配置の名前にします。パターンは `section-heading` や `icon` のように、その要素がページの中で何であるかを表す役割の名前にします。`class="cluster"` は子の並び方を、`class="section-heading"` は要素自身の見た目を決めるクラスだと、名前から読み取れます。何をユーティリティ、コンポジション、パターンにするかは、第7章の「[7-2 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で扱います。

```html title="🙆‍♂ Recommended: クラス名の種類を組み合わせたHTML"
<section class="scoped news-section">
  <h2 class="section-heading">お知らせ</h2>
  <p class="_lead">店舗からのお知らせです。</p>
  <ul class="stack">
    <li>
      <article class="scoped news-card">
        <h3>営業時間の変更について</h3>
      </article>
    </li>
  </ul>
  <p class="_note -text-center">掲載から1年が過ぎたお知らせは削除します。</p>
</section>
```

このHTMLは、`class` 属性を見るだけで読み解けます。`_lead` と `_note` は `news-section` の子要素、`-text-center` はユーティリティ、`stack` はコンポジション、`section-heading` はパターンです。`stack` と `section-heading` はどちらも接頭辞がありませんが、配置の名前と役割の名前なので取り違えません。2つの `p` は役割が違うので子要素のクラスで区別し、1つしかない `h2` と `ul` には子要素のクラスを付けていません。`scoped news-card` から先は別のコンポーネントなので、`news-section` のスタイルは届きません。`news-card` の中に `news-section` と同じ名前の子要素や同じ種類の要素があっても衝突しません。

## 階層を名前に映さない

HTMLの入れ子が深くなっても、子要素のクラス名は平らなままにします。コンポーネントの直下にある要素も、その下の下にある要素も、同じ `._kebab` の形で付け、親の名前を連結して階層を表しません。孫にあたる要素には、その要素の役割を名前にします。

```html title="🙅‍♂ Not Recommended: 階層を名前につなげる"
<!-- 🙅‍♂ Not Recommended -->
<article class="scoped news-card">
  <ul class="_tags">
    <li class="_tags-item">
      <a class="_tags-item-link" href="/tags/notice/">お知らせ</a>
    </li>
  </ul>
</article>
```

```html title="🙆‍♂ Recommended: 孫にあたる要素にも、役割の名前を平らに付ける"
<article class="scoped news-card">
  <ul class="_tags">
    <li class="_tag">
      <a class="_tag-link" href="/tags/notice/">お知らせ</a>
    </li>
  </ul>
</article>
```

階層を名前に写すと、名前が要素の位置を表してしまいます。`<li>` を別の要素に替えたり、リンクを1つ外側に出したりしたときに、HTMLの構造に合わせてクラス名も、CSSのセレクタも変えなければなりません。役割の名前なら、構造が変わっても名前は変わりません。セレクタも、`._tag-link` のように1つのクラスで選べるので、詳細度は上がりません。

## BEMの名前を書き直す

冒頭のBEMの例を、本書の命名で書き直します。子要素の名前は短くなり、バリエーションはクラス名の修飾子ではなく、`data-variant` 属性で表しています。

```html title="🙆‍♂ Recommended: ルートにだけコンポーネント名を付ける"
<article class="scoped media-card" data-variant="featured">
  <div class="_image"></div>
  <h2 class="_title">記事のタイトル</h2>
</article>
```

```css title="🙆‍♂ Recommended: 子要素は短い名前で、スコープの中に書く"
@scope (.scoped.media-card) to (.scoped) {
  :scope {
    display: block grid;
    gap: 12px;

    &[data-variant="featured"] {
      padding: 16px;
      border: 1px solid oklch(85% 0 0deg);
    }
  }

  ._image {
    aspect-ratio: 16 / 9;
    border-radius: 8px;
  }

  ._title {
    font-size: calc(18 / 16 * 1rem);
  }
}
```

`._title` のスタイルは `media-card` のスコープの中にしか当たらないので、ほかのコンポーネントに同じ名前の子要素があっても問題ありません。`@scope` の括弧の中のセレクタは詳細度に加わらないので、`._image` と `._title` は `0.1.0` です。`:scope` も擬似クラスと同じ `0.1.0` で、その中の `&[data-variant="featured"]` は、`&` が `:scope` を指すため、属性セレクタの分を足した `0.2.0` になります。バリエーションや状態を属性で表す書き方は、「[12-1 状態とフォーカスを表す](/interaction/states-and-focus/)」で扱います。

AIに名前を付けさせると、`.media-card__title` のようなBEMの名前や、`.card-title` のようにコンポーネント名を繰り返した名前が出てくることがよくあります。`@scope` の中に書くコードでは、子要素の名前からコンポーネント名を取り除き、`_` で始まる短い名前に直してください。

BEMなどの命名規則と、本書の命名が分かれるところもあります。BEMに基づく設計の記事には、レイアウトのためのブロックに `l-` のような接頭辞を付けず、通常のブロックと同じに扱うものがあります。何がレイアウトなのかの線引きが人によって違い、接頭辞で見分けられても利点が少ないからです。また、修飾クラスは単独でスタイルを持たせず、必ずブロックと一緒に宣言する、という考え方もあります。単独で使えるクラスは、どこに付けても同じ効果があるとは限らないからです。

本書では、配置のパターンを `.cluster` のようなコンポジションとして分けます。コンポジションは配置だけを書くと決めているので、線引きは「見た目を持つか」で判断でき、接頭辞は付けません。また、単独でスタイルを持つクラスは、どこに付けても同じ意味を持つユーティリティと、静的な見た目だけを持つパターンに限ります。コンポーネントのバリエーションは、クラスの修飾子ではなく属性で表します。この対比は、命名の規則が違うだけで、名前から役割と影響範囲を読み取れるようにするという目的は同じです。

## 見た目の名前と役割の名前

名前は、見た目ではなく役割で付けます。`._red-text` や `._big-title` のような見た目の名前は、デザインが変わった時点で実態とずれます。赤かった文字が青になれば、`._red-text` という名前は実態と食い違います。`._notice` や `._heading` のように役割で名前を付けておけば、見た目を変えても名前を変えずに済みます。

```html title="🙅‍♂ Not Recommended: 見た目や汎用の語で名前を付ける"
<!-- 🙅‍♂ Not Recommended -->
<div class="scoped contact-section">
  <div class="_wrapper">
    <p class="_red-text">受付は平日のみです。</p>
    <a class="_button" href="/contact/">お問い合わせ</a>
  </div>
</div>
```

同じ理由で、HTMLやCSSで意味が決まっている語を、別の意味で使いません。上の例の `<a>` は見た目がボタンでも、役割はページを移動するリンクなので、名前には `_contact-link` のように `link` の語を使います。`button` は `<button>` 要素のための名前です。`container` はCSSの `container` プロパティを持つ要素に、`columns` は段組み（マルチカラム）のレイアウトに使う語なので、ただの入れ物やFlexboxの横並びには使いません。`.container` のクラスについては、「[9-2 コンテナクエリ](/responsive/container-queries/)」でも説明しています。

`wrapper`、`block`、`module`、`widget` のような総称も避けます。何のための要素なのかが名前から分からず、責務の境界もあいまいになるからです。内容の幅を制限して中央に寄せる要素は `_inner`、外側との余白や配置を調整する要素は `_outer` のように、責務を表す名前を付けます。

```html title="🙆‍♂ Recommended: 役割と責務で名前を付ける"
<div class="scoped contact-section">
  <div class="_inner">
    <p class="_notice">受付は平日のみです。</p>
    <a class="_contact-link" href="/contact/">お問い合わせ</a>
  </div>
</div>
```

この例では、名前の付け方を示すために `p` と `a` にもクラスを付けています。実際のコンポーネントで、ほかに同じ種類の要素がなければ、クラスを付けずにタイプセレクタで選びます。

見た目の名前を付けてよいのは、ユーティリティだけです。ユーティリティは1つのことしかしないので、`.-text-center` のように、その効果をそのまま名前にするのがいちばん分かりやすいからです。コンポーネントや、繰り返し使う静的な部品（パターン）には、`section-heading` や `status-badge` のように役割の名前を付けます。`big-title` や `blue-link` のような名前は付けません。

名前に迷ったときは、そのコンポーネントや要素が何なのかを、日本語で1文に書いてみます。その文に出てくる特徴的な語が、名前の候補になります。「商品の画像と価格と購入ボタンをまとめたもの」なら `product-detail`、「記事の一覧」なら `article-list` です。`text-box` や `center-box` のように、見た目や配置だけを表す名前は、何のための部品なのかが分からないので避けます。

名前は省略しません。`._desc` や `._ttl` のように文字数を削っても、節約できるのはわずかなバイト数で、読む人には意味を推測する負担が残ります。`nav` のように、HTMLの要素名として広く通じている語はそのまま使ってかまいません。

## 自分で付ける名前の `--`

`@keyframes` の名前、グリッドの線とエリアの名前、アンカーの名前、スタイルクエリで比べる値のように、自分で付けて値として使う名前は `--` で始めます。コンテナの名前も同じ規則で、「[9-2 コンテナクエリ](/responsive/container-queries/)」で扱っています。

```css title="🙆‍♂ Recommended: 自分で付ける名前を -- で始める"
@keyframes --fade-in {
  from {
    opacity: 0;
  }
}

@scope (.scoped.media-card) to (.scoped) {
  :scope {
    display: block grid;
    reading-flow: grid-rows;
    grid-template-areas:
      "--image"
      "--body";
  }

  ._image {
    grid-area: --image;
  }

  ._body {
    grid-area: --body;
  }
}
```

理由は4つあります。1つ目は、近年のCSSで、自分で付ける名前に `--` を求めるプロパティが増えていることです。`anchor-name` やスクロール連動アニメーションのタイムラインの名前は、`--` で始めないと無効になります。2つ目は、すべての名前を `--` で始めておけば、「このプロパティでは `--` が必要か」を個別に覚えなくて済むことです。

3つ目は、将来CSSに新しいキーワードが追加されても、自分で付けた名前と衝突しにくいことです。CSSのキーワードは `--` で始まらないので、`--` を付けておけば見分けられます。4つ目は、コードを読んだときに、自分で付けた名前だとすぐに分かることです。`fadeIn` や `image` のような名前は、CSSのキーワードと見た目の区別がつきません。

```css title="🙅‍♂ Not Recommended: キーワードと見分けにくい名前"
/* 🙅‍♂ Not Recommended */
@keyframes fadeIn {
  from {
    opacity: 0;
  }
}

._layout {
  grid-template-areas:
    "image"
    "body";
}
```

グリッドのエリアの名前は、そのエリアに置く子要素のクラス名とそろえます。`._image` を置くエリアは `--image` です。こうしておくと、`grid-template-areas` の図と、各要素の `grid-area` の対応をすぐに読み取れます。グリッドのエリアの使い方は、「[8-6 Gridから考える](/layout/grid-first/)」で扱います。

`--` を付けるのは、値として書く名前だけです。`@layer` のレイヤー名のように、プロパティの値として使わない名前には付けません。`@keyframes` の名前をコンポーネントごとにどう分けるかといった設計は、「[12-2 モーションを実装する](/interaction/motion/)」で説明します。本書のStylelintの設定では、`@keyframes` の名前を `keyframes-name-pattern` で検証しています。
