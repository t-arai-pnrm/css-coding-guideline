背景色から文字色を黒か白に決めるときは、相対カラー構文と `sign()` を組み合わせ、`color: oklch(from var(--_background) sign(0.7 - l) 0 h);` と書きます。背景の明度が0.7より低ければ白に、0.7以上なら黒になります。この書き方は、不透明で、選ばれる文字色とのコントラスト比を確認済みの背景色に使います。閾値の0.7は読みやすさを優先した本書の方針で、WCAGのAAへの適合を保証する値ではありません。

同じことをする `contrast-color()` という関数もありますが、本書の対象のブラウザのうちSafari 18系は対応していません。また、いまの `contrast-color()` はWCAG 2.xのコントラスト比のアルゴリズムで黒か白を選ぶので、中間の明度の色では読みにくいほうを選ぶことがあります。そのため、文字色は `sign()` で決めます。一方、画像の上に文字を載せるときに、画像が表示されなかった場合に備えて敷く背景色は、`background-color: contrast-color(currentColor);` で文字色から決めます。こちらは、未対応の環境では背景色が付かないだけで済むからです。

## 背景色ごとに文字色を指定すると起きること

ボタンやバッジのように、色のバリエーションを持つ部品を考えます。バリエーションを足すたびに、背景色と文字色の組み合わせを1つずつ決めることになります。

```css title="🙅‍♂ Not Recommended: バリエーションごとに文字色を指定する"
/* 🙅‍♂ Not Recommended */
._badge {
  &[data-variant="info"] {
    background-color: var(--color--accent--600);
    color: oklch(100% 0 0deg);
  }

  &[data-variant="warning"] {
    background-color: var(--color--warning--400);
    color: oklch(0% 0 0deg);
  }
}
```

このコードでは、背景色を変えるたびに文字色も見直す必要があります。`--color--warning--400` を少し暗い段階に替えたら、黒い文字のままでよいのか、白にすべきかを、誰かが判断しなければなりません。ダークモードで背景色の段階が替わる場合も同じで、配色ごとに文字色の組み合わせが増えます。

背景色がCSSの外から来る場合は、さらに困ります。CMSで編集者がラベルの色を選べる場合、選べる色を確認済みの候補に限っていても、どの候補が使われるかはCSSを書く時点では分かりません。この節で扱うのは、コントラスト比を確認済みの限られた背景色について、文字色を背景色から自動で決める書き方です。どのような色が来ても読みやすさを保証する方法ではありません。

## sign() で黒か白を選ぶ

`sign()` は、中の値が正なら1を、負なら-1を、0なら0を返す関数です。これを相対カラー構文の明度の位置に書くと、元の色の明度によって、明度が1か、0以下の色を作れます。

```css title="🙆‍♂ Recommended: 背景色の明度から、文字色を黒か白に決める"
@scope (.scoped.badge) to (.scoped) {
  :scope {
    --_background: var(--badge--background, var(--color--accent--600));

    background-color: var(--_background);
    color: oklch(from var(--_background) sign(0.7 - l) 0 h);
  }
}
```

背景の明度が0.7より低いと、`0.7 - l` が正になり、明度は1、つまり白になります。0.7以上なら明度は0か-1になります。`oklch()` の明度は0より小さくならないので、-1は0に切り詰められ、どちらも黒になります。彩度を0にしているので色相は見た目に影響せず、元の色の `h` をそのまま渡しています。

バリエーションの側では、`--badge--background` に背景色を渡すだけです。文字色は背景色から決まるので、色を1つ選べばバリエーションが1つ増えます。CMSから来る色を `style` 属性で渡す場合も、同じ式で文字色が決まります。ただし、編集者やユーザーが任意の色を選べると、選ばれた文字色がコントラスト比の基準に届かない色も来ます。選べる色を、コントラスト比を確認済みの候補に限っておきます。{/* 要確認: 出典なし */}

`sign()` は、2025年6月にすべての主要なブラウザで使えるようになりました（2026年10月確認）。なお、`sign()` を相対カラー構文の中で使う書き方は、Chrome 153でだけ確認しています。

## 閾値を0.7にする理由

閾値は、どの明度から黒い文字にするかの境目です。0.7は読みやすさを優先した本書の方針で、WCAG 2.xのコントラスト比の高いほうを選ぶ値ではありません。コントラスト比の高いほうを選ぶなら、無彩色の背景では、白とのコントラスト比と黒とのコントラスト比が等しくなる明度0.56あたりが閾値になります。本書はこれより上の0.7に置き、中間の明度の色では白を選びます。

0.56にしないのは、中間の明度では、WCAG 2.xのコントラスト比が実際の読みやすさと一致しないことがあるからです。明度0.57の青（`oklch(57% 0.16 255deg)`）では、コントラスト比は白が約4.5:1、黒が約4.7:1で、比の高い黒が選ばれます。しかし、MDNは、この明度に近い青の背景に黒い文字を置くと、小さな文字では読みにくいと注意しています。この例は0.7という数値の根拠ではありません。中間の明度の色では白い文字のほうを読みやすく感じることが多いという本書の判断から、閾値を0.56より上に置いています。どの色相や文字サイズでも0.7が最適とは限らないので、使う背景色ごとに表示を確かめます。

その代わり、0.7で白が選ばれる色の一部は、通常の大きさの文字の基準（4.5:1）に届きません。本書のルールでは、文字と背景のコントラスト比はWCAG 2.1のAAを満たす必要があります。そこで、文字を載せる背景のトークンを選ぶ段階で、選ばれる文字色とのコントラスト比を確かめ、基準に届かない色を除きます。無彩色の背景では、次のようになります。

| 背景の明度（無彩色） | 選ばれる文字色 | コントラスト比 | 背景のトークンに |
|---|---|---|---|
| 0.55 | 白 | 約4.9:1 | 使える |
| 0.6 | 白 | 約3.9:1 | 使わない |
| 0.65 | 白 | 約3.2:1 | 使わない |
| 0.69 | 白 | 約2.8:1 | 使わない |
| 0.7 | 黒 | 約7.9:1 | 使える |
| 0.75 | 黒 | 約9.4:1 | 使える |

明度がおよそ0.57から0.7までの色は、白が選ばれて基準を下回るので、背景のトークンに使いません。この範囲が使えないのは色そのものの性質ではなく、本書の閾値で白が選ばれるからです。明度0.69の灰色でも、黒を選べばコントラスト比は約7.6:1あります。閾値は前の段落の理由で0.7のままにし、白が基準に届かないこの範囲を背景のトークンから除いています。有彩色では範囲の境目が色相によって少し動くので、実際のトークンごとに確かめます。

`sign()` は、黒と白のうちどちらかを選ぶだけで、選んだ色が基準を満たすことまでは保証しません。最後は、実際の背景色と文字色の組み合わせでコントラスト比を確かめます。コントラストの基準と確かめ方は「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」で説明しています。知覚にもとづくコントラストのモデルであるAPCAで0.7を比べた結果は、ページの最後の「[閾値をAPCAで比べる](#閾値をapcaで比べる)」にまとめています。

## contrast-color() と sign() の使い分け

`contrast-color()` は、色を渡すと、白か黒のうちその色とのコントラストが高いほうを返す関数です。`color: contrast-color(var(--_background));` と書けば、上の `sign()` の式と同じように、背景色から文字色が決まります。どちらを使うかは、対応していない環境で何が起きるかと、選ばれる色を調整する必要があるかで決めます。

```css title="🙅‍♂ Not Recommended: Safari 18系に対応する間に、contrast-color() で文字色を決める"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.badge) to (.scoped) {
  :scope {
    --_background: var(--badge--background, var(--color--accent--600));

    background-color: var(--_background);
    color: contrast-color(var(--_background));
  }
}
```

この書き方を勧めない理由は2つあります。1つ目は、Safari 18系で文字が読めなくなることです。`contrast-color()` に対応していない環境では `color` の宣言が無効になり、文字色は親から継承した色のままになります。本文の濃い文字色を継承すれば、濃い背景のバッジの上で文字が背景に溶け込みます。文字色は内容を読むための指定なので、未対応の環境で欠けてはいけません。

2つ目は、いまの `contrast-color()` の計算方法です。主要なブラウザは、WCAG 2.xのコントラスト比で黒か白を選んでいます。上で見た明度0.57の青のように、中間の明度の色では比の差がわずかで、読みにくいほうの黒を選ぶことがあります。閾値を変える手段も、黒と白以外の色を返させる手段もありません。Safari 18系を対象から外したあとも、閾値を自分で決めたい場合や、後で説明するように黒と白の代わりに色味のある色を使いたい場合は、`sign()` で書きます。

一方、画像の上に文字を載せる部品で、画像が表示されなかった場合に備える背景色には、`contrast-color()` を使います。文字色は先に決まっているので、その文字色と対比する背景色を `contrast-color(currentColor)` で求めます。

```css title="🙆‍♂ Recommended: 画像が表示されなかった場合の背景色を、文字色から決める"
@scope (.scoped.image-banner) to (.scoped) {
  :scope {
    display: block grid;
    grid-template-areas: "--pile";
    background-color: contrast-color(currentColor);
    color: var(--image-banner--foreground, oklch(100% 0 0deg));

    & > img,
    & > ._body {
      grid-area: --pile;
    }
  }
}
```

`currentColor` は、その要素の `color` の値です。白い文字なら黒い背景が、濃い文字なら白い背景が敷かれるので、画像に合わせて文字色を変えても、背景色を書き直す必要がありません。画像が表示されれば、背景色は画像に隠れて見えません。画像と本文をグリッドの同じエリアに重ねる方法と、写真を `<img>` で置く理由は、「[16-1 画像の配置と読み込み](/decoration/images/)」で説明しています。

この用途で `contrast-color()` を使えるのは、2つの理由がなくなるからです。Safari 18系では宣言が無効になって背景色が付きませんが、困るのは画像を読み込めなかったときだけで、画像が表示されれば見た目は対応した環境と変わりません。対応した環境だけで表示を改善するプログレッシブ・エンハンスメントとして扱えます。また、画像の上の文字には、画像のどの部分とも対比するよう白や黒に近い色を選びます。WCAG 2.xの計算が読みにくいほうを選ぶ中間の明度の色は、ふつう渡されません。{/* 要確認: 出典なし */}

`contrast-color()` は、2026年4月にすべての主要なブラウザで使えるようになりました。ただし、Safariが対応したのはバージョン26からで、本書の対象のブラウザ（Safari 18系の最終版以降）には未対応の環境が残ります（2026年10月確認）。

## 1つの色から配色を組み立てる

同じ式を使うと、文字色から背景色を作ることもできます。トーストのように色のバリエーションを持つ部品では、バリエーションごとに書き換える色を1つにできます。

```css title="🙆‍♂ Recommended: 文字色だけを受け取り、背景色は文字色から作る"
@scope (.scoped.toast) to (.scoped) {
  :scope {
    --_foreground: var(--toast--foreground, var(--foreground--base));
    --_contrast-color: oklch(from var(--_foreground) sign(0.7 - l) 0 h);

    padding: 1em;
    border: 1px solid;
    border-radius: 4px;
    background-color: color-mix(in oklab, var(--_foreground), var(--_contrast-color) 90%);
    color: var(--_foreground);

    &[data-variant="success"] {
      --_foreground: var(--color--accent--600);
    }

    &[data-variant="error"] {
      --_foreground: var(--color--error--600);
    }
  }
}
```

`--_contrast-color` が、文字色と対比する黒か白です。背景色は、その黒か白に文字色を10%だけ混ぜて作ります。枠線は `currentColor` なので文字色と同じです。バリエーションのルールでは、`--_foreground` だけを書き換えます。

文字、枠線、背景の3色がすべて `--_foreground` から決まるので、色を1つ選べばバリエーションが1つ増えます。暗い文字色なら淡い背景に、明るい文字色なら暗い背景になるので、ダークモードで明るい段階の色を渡しても、文字と背景の明暗が逆転することはありません。ただし、背景に文字色を混ぜるとコントラスト比は下がるので、バリエーションの色ごとに確かめます。

## sign() で書くときの注意

この式は、背景色が不透明であることを前提にしています。半透明の背景色では、下にある色と重なった色が実際の背景になり、元の色の明度とは違う明るさに見えます。半透明の背景に文字を載せるときは、重なったあとの色で確かめます。

選べるのは、黒と白の2色だけです。ブランドの濃い色や、少しだけ色味のある白を文字色にしたい場合は、`sign()` の結果を明度の段階に置き換える必要があります。たとえば `calc(0.2 + 0.75 * max(sign(0.7 - l), 0))` のように書けば、明度0.2と0.95の間で切り替えられます。{/* 要確認: 出典なし */}ただし、式が長くなるので、決まった組み合わせが少ないなら、トークンで組み合わせを決めたほうが読みやすくなります。

文字以外の要素にも、同じ式を使えます。アイコンや枠線のように、背景の上に描く部品の色を決めるときも、背景色から黒か白を選べます。非テキストのコントラスト比の基準は、文字とは異なり3:1です。

## 閾値をAPCAで比べる

採用した0.7を、知覚にもとづくコントラストのモデルであるAPCAでも比べてみました。この比較は0.7を決めた根拠ではなく、決めた後に確かめたものです。計算にはAPCAのバージョン0.0.98G-4gの定数を使い、背景をOKLCHの色、文字を白（`#fff`）と黒（`#000`）として、コントラスト値（Lc）の絶対値を比べました。

無彩色の背景では、白い文字と黒い文字のLcの絶対値が等しくなるのは明度0.72あたりです。有彩色では色相によって少し動き、彩度0.12の色ではおよそ0.70から0.73の間でした。明度0.57の青では、Lcの絶対値は白が約76、黒が約33で、WCAG 2.xのコントラスト比とは逆に、白のほうが大きくなります。0.7は、WCAG 2.xの交点の0.56よりも、APCAの交点の近くにあります。{/* 要確認: 出典なし（0.7 の採用経緯は著者の資料にない）。Lc と交点は 2026年10月6日に APCA 0.0.98G-4g の定数で再計算し、本文の値と一致した。計算スクリプトは本文に添付していない */}

ほかの資料では、0.6前後のような別の閾値を見かけることもあります。閾値は、0.56に近いほどWCAG 2.xのコントラスト比に、0.72に近いほどAPCAの評価に従います。その間の値は、両者の中間で白と黒を切り替えるものです。APCAはまだWCAGの基準として採用されていないので、本書は、WCAG 2.1のAAを満たすかどうかを背景のトークンを選ぶ段階で確かめ、黒と白を切り替える明度はAPCAの交点の近くにしています。
