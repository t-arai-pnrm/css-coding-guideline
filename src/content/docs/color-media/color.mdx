色は `oklch()` で定義し、透過させた色や明度を変えた色は、元の色から相対カラー構文や `color-mix()` で作ります。派生させた色のためにトークンやRGBの値を増やさないので、元の色を1か所直せば、そこから作った色もすべて追従します。

ダークモードに対応するときは、セマンティクスのトークンの値を `light-dark()` で書き、`<meta name="color-scheme">` で両方の配色に対応することを宣言します。配色の切り替えはトークンの側で済ませ、コンポーネントには書きません。サイトの中でテーマを選べるようにする場合も、このメタ要素の `content` を書き換えるだけで済みます。

## 16進数の色で起きること

色を16進数で指定してトークンにまとめたCSSを考えます。ボタンの背景を少し透過させたいときや、少し暗い色がほしいときに困ります。16進数のトークンからは不透明度を変えられないので、RGBの値を別のトークンとして用意することになります。

```css title="🙅‍♂ Not Recommended: 透過させるためだけに RGB の値を別に持つ"
/* 🙅‍♂ Not Recommended */
:root {
  --color-primary: #e4a153;
  --color-primary-rgb: 228 161 83;
  --color-primary-dark: #c9853a;
}

.button--ghost {
  background-color: rgb(var(--color-primary-rgb) / 20%);
}

.button--strong {
  background-color: var(--color-primary-dark);
}
```

このコードでは、1つの色を表すトークンが3つあります。ブランドの色を変えるときは3つとも書き換える必要があり、1つでも直し忘れると、元の色と派生させた色がずれます。`--color-primary-dark` のような「少し暗い色」は誰かが目で見て選んだ値で、元の色との関係がコードに残っていません。

HSLで書けば明るさを数値で調整できるように見えますが、HSLの明度は、人の目に見える明るさと一致しません。同じ明度50%でも、黄色は明るく、青は暗く見えます。色相を変えただけで明るさがそろわなくなるので、段階的なパレットを作るのには向きません。

## oklch() で色を定義する

色は `oklch()` で定義します。`oklch()` は、明度（L）、彩度（C）、色相（H）の3つの値で色を表します。明度は見た目の明るさに近くなるように設計されているので、色相が違っても、明度が同じならおおむね同じ明るさに見えます。

```css title="🙆‍♂ Recommended: 明度の段階を oklch() でそろえる"
:root {
  --color--neutral--100: oklch(97% 0 0deg);
  --color--neutral--500: oklch(55.6% 0 0deg);
  --color--neutral--900: oklch(20.5% 0 0deg);
  --color--accent--300: oklch(80% 0.1 250deg);
  --color--accent--500: oklch(60% 0.16 250deg);
  --color--accent--700: oklch(45% 0.14 250deg);
}
```

私のテンプレートでは、グレーとアクセントカラーを、それぞれ50から950までの11段階で定義しています。グレーは彩度を0にして、明度だけを変えています。アクセントカラーは色相を250deg（青）に固定し、中間の段階ほど彩度が高くなるように、山なりに値を変えています。

`oklch()` を選ぶいちばんの理由は、値がそのまま色の性質を表していることです。`#c9853a` という値を見ても、元の色より暗いのかどうかは分かりません。`oklch(52% 0.16 250deg)` なら明度52%の青だと読み取れ、「もう少し明るく」という調整も明度の数値を上げるだけです。

彩度の上限は色相と明度によって変わり、画面で表示できる範囲を超えた値も指定できます。範囲を超えた色は、ブラウザが表示できる色に置き換えて描画します。デザインツールから受け取った色を変換するときは、彩度が上がりすぎていないかを確かめてください。

色の関数をスペースで区切ることや、色相に `deg` を付けることは、「[5-3 モダンな記法にそろえる](/notation/modern-syntax/)」で説明しています。色のトークンをプリミティブとセマンティクスの2層で持つ設計は、「[6-3 デザイントークン](/components/design-tokens/)」で扱います。

## 相対カラー構文で派生色を作る

透過させた色や明度を変えた色は、元の色から相対カラー構文で作ります。`oklch(from 元の色 l c h)` と書くと、元の色を分解した明度・彩度・色相の値が `l`、`c`、`h` に入ります。変えたい値だけを書き換えれば、ほかの値は元の色のままです。

```css title="🙆‍♂ Recommended: 元の色から、不透明度や明度を変えた色を作る"
._divider {
  border-block-end: 1px solid oklch(from var(--color--accent--500) l c h / 10%);
}

._tag {
  background-color: oklch(from var(--color--accent--500) calc(l - 0.15) c h);
}
```

1つ目は、アクセントカラーの不透明度を10%にした区切り線です。2つ目は、明度だけを0.15下げた、少し暗いアクセントカラーです。どちらも元の色のトークンを参照しているので、アクセントカラーを変えれば、区切り線とタグの色も一緒に変わります。

相対カラー構文の中の `l` は、パーセントではなく0から1までの数値として扱われます。計算するときは、`calc(l - 0.15)` のように数値で書きます（2026年9月、Chrome 153で確認）。

WordPressの案件では、theme.jsonのパレットの色を元に、`oklch(from …)` で細い罫線の色をトークンにしました。編集画面でパレットの色が変わっても、罫線はその色の薄い版であり続けます。

Safariが対応したのはバージョン18なので、本書の対象のブラウザ（Safari 18系の最終版以降）では問題なく使えます（2026年9月確認）。

### 背景の明るさから文字色を選ぶ

相対カラー構文と `sign()` を組み合わせると、背景色の明度から、文字色を黒か白に自動で決められます。

```css title="🙆‍♂ Recommended: 背景の明度から、黒か白の文字色を決める"
._badge {
  --_background: var(--color--accent--500);

  background-color: var(--_background);
  color: oklch(from var(--_background) sign(0.6 - l) 0 0deg);
}
```

`sign()` は、中の値が正なら1を、負なら-1を、0なら0を返す関数です。背景の明度が0.6より低いと明度が1になり、文字は白になります。0.6以上なら明度は0以下になり、0に切り詰められて黒になります。背景色を変えるたびに、文字色を選び直す必要がありません。

閾値は、白と黒のうちコントラスト比の高いほうが選ばれる値にします。無彩色の場合、白い文字と黒い文字のコントラスト比が等しくなるのは、明度0.56あたりです。閾値を0.7にすると、明度0.6から0.7の背景に白い文字が乗り、コントラスト比が4.5:1を下回ります（明度0.7では約2.7:1）。0.6でも境目のすぐ近くの色では基準にわずかに届かないことがあるので、最後は実際の組み合わせで確かめます。コントラストの確認は「[10-2 強制カラーモードとコントラスト](/color-media/forced-colors/)」で扱います。

背景色から文字色を決める `contrast-color()` という関数もありますが、Safariが対応したのはバージョン26で、本書の対象のブラウザでは使えません（2026年9月確認）。`sign()` は、2025年6月にすべての主要なブラウザで使えるようになりました。なお、`sign()` を相対カラー構文の中で使う書き方は、Chrome 153でだけ確認しています。

## color-mix() で2つの色を混ぜる

`color-mix()` は、2つの色を指定した割合で混ぜる関数です。相対カラー構文が1つの色の成分を書き換えるのに対して、`color-mix()` は2つの色の間の色を作ります。背景色と文字色を少しだけ混ぜた枠線や、`currentColor` を半透明にした下線のように、2つの色の関係で決まる色に向いています。

```css title="🙆‍♂ Recommended: 2つの色の間の色を作る"
._card {
  border: 1px solid color-mix(in oklab, var(--background--base), var(--foreground--base) 15%);
}

._link {
  text-decoration-color: color-mix(in oklab, currentColor 60%, transparent);
}
```

1つ目は、背景色に文字色を15%混ぜた枠線の色です。ライトモードでは背景より少し暗く、ダークモードでは少し明るい線になり、どちらの配色でも背景からわずかに浮きます。2つ目は、文字色に透明を混ぜて、不透明度を60%にした下線の色です。`currentColor` の不透明度を変えたいときも、`transparent` と混ぜれば簡単に書けます。

補間の色空間には `oklab` を指定します。以前の私は `in srgb` と書いていましたが、いまのテンプレートでは `in oklab` にそろえています。`srgb` で混ぜると、中間の色がくすんで見えることがあります。

ホバーのときに背景色を少し暗くしたい場合も、`opacity` を下げるのではなく、`color-mix()` で黒を混ぜます。`opacity` を下げると、文字まで一緒に透けてしまうからです。ホバーの表し方は「[11-1 状態とフォーカスを表す](/interaction/states-and-focus/)」で説明します。

### 相対カラー構文と color-mix() の使い分け

同じ色をどちらでも作れる場面は多くあります。不透明度が10%の色なら、`oklch(from X l c h / 10%)` と `color-mix(in oklab, X 10%, transparent)` のどちらの書き方でも作れます。

私は、1つの色の成分を変えるときは相対カラー構文を、2つの色の間を取るときは `color-mix()` を使います。「アクセントカラーの薄い版」なら元の色は1つなので相対カラー構文、「背景と文字の中間」なら2つの色が必要なので `color-mix()` という具合です。書き方を決めておくと、コードを読むときに、どの色から作った色なのかをすぐに追えます。

## light-dark() でダークモードに対応する

ダークモードの色は、セマンティクスのトークンに `light-dark()` で両方の値を持たせます。`light-dark(ライトの色, ダークの色)` と書くと、要素に適用されている配色に合わせて、どちらか一方の値になります。

```css title="🙆‍♂ Recommended: セマンティクスのトークンに、両方の配色の値を持たせる"
:root {
  --background--base: light-dark(var(--color--neutral--100), var(--color--neutral--900));
  --background--surface: light-dark(var(--color--neutral--200), var(--color--neutral--800));
  --foreground--base: light-dark(var(--color--neutral--950), var(--color--neutral--50));
  --foreground--muted: light-dark(var(--color--neutral--600), var(--color--neutral--400));
  --border--base: light-dark(var(--color--neutral--300), var(--color--neutral--700));
}
```

コンポーネントは、これらのセマンティクスのトークンを参照するだけです。配色による切り替えはトークンの側で済んでいるので、コンポーネントに `prefers-color-scheme` のメディアクエリを書く必要はありません。ダークモードの色を調整するときも、見直すのはトークンの定義だけです。

```css title="🙅‍♂ Not Recommended: コンポーネントごとにダークモードの色を書く"
/* 🙅‍♂ Not Recommended */
.card {
  background-color: #f5f5f5;
  color: #1c1c1c;
}

@media (prefers-color-scheme: dark) {
  .card {
    background-color: #2a2a2a;
    color: #f5f5f5;
  }
}
```

コンポーネントごとにメディアクエリを書くと、ダークモードの色がサイトのあちこちに散らばります。ダーク用の値を書き忘れたコンポーネントだけが明るいまま残る、といった不具合も起きがちです。AIにダークモードへの対応を頼むと、この形のコードが出てくることが多いので注意してください。

### meta 要素で配色を宣言する

`light-dark()` を使うには、ページが両方の配色に対応していることを宣言する必要があります。宣言がないと、OSがダークモードでも `light-dark()` は常にライトの値になります（2026年9月、Chrome 153で確認）。私のテンプレートでは、CSSの `color-scheme` プロパティではなく、HTMLのメタ要素で宣言しています。

```html
<meta name="color-scheme" content="light dark" />
```

メタ要素で宣言すると、スクロールバーやフォームの部品といったブラウザの部品も、ページと同じ配色で描画されます。CSSを読み込む前から配色が決まるので、読み込みの途中で背景が白く光ることも防げます。

反対に、ダークモードに対応していないサイトでは、この宣言を書きません。色を指定していない部分だけが暗い配色になり、文字を読めなくなることがあるからです。詳しくは「[4-3 グローバルに書いてはいけないもの](/reset/global-pitfalls/)」で説明しています。

## テーマを手動で切り替える

OSの設定とは別に、サイトの中でテーマを選べるようにする場合も、メタ要素の `content` を書き換えます。私のテンプレートでは「ライト」「ダーク」「OSの設定に合わせる」の3つを選べるようにし、それぞれ `light only`、`dark only`、`light dark` を設定しています。選んだ値はlocalStorageに保存し、次にページを開いたときに読み戻します。

```html
<meta name="color-scheme" content="light dark" />
<script>
  (() => {
    try {
      const stored = localStorage.getItem('color-scheme');
      const meta = document.querySelector('meta[name="color-scheme"]');
      if (stored && meta) meta.content = stored;
    } catch {
      // Cookie を無効にしている環境では、localStorage にアクセスすると例外が発生する
    }
  })();
</script>
```

このスクリプトは `<head>` の中に直接書き、ページの描画より前に実行します。外部のファイルにして後から読み込むと、保存したテーマに切り替わるまでの一瞬、OSの配色で表示されてしまいます。localStorageは、Cookieを無効にしている環境では例外を投げるので、必ず `try` で囲みます。

`only` を付けた値は、ページがその配色にしか対応していないことを表します。ブラウザが独自にページを暗くする機能を持っていても、`only` があれば、ページの配色はそのまま保たれます。

以前の私は、`<html>` の `data-theme` 属性とメタ要素の両方を書き換えていました。いまはメタ要素だけを書き換え、色はすべて `light-dark()` に任せています。CSSの側でテーマの属性を参照しないので、切り替えの仕組みが1か所にまとまります。

### 色以外のスタイルを配色で変える

画像の明るさや影の強さのように、色以外のスタイルを配色で変えたい場合もあります。テンプレートでは、メタ要素の値から `--color-scheme` というカスタムプロパティを決めておき、スタイルクエリで分岐できるようにしています。

```css title="🙆‍♂ Recommended: meta 要素の値から、いまの配色をカスタムプロパティにする"
:root {
  &:has(meta[name="color-scheme"][content="light only"]) {
    --color-scheme: --light;
  }

  &:has(meta[name="color-scheme"][content="dark only"]) {
    --color-scheme: --dark;
  }

  &:has(meta[name="color-scheme"][content="light dark"]) {
    --color-scheme: --light;

    @media (prefers-color-scheme: dark) {
      --color-scheme: --dark;
    }
  }
}
```

使う側では、`@container style(--color-scheme: --dark)` のように条件を書きます。値を `--` で始めるのは、自分で付けた名前だと分かるようにするためです。スタイルクエリは2026年5月にすべての主要なブラウザで使えるようになったので、本書の対象のブラウザでは問題なく動作します（2026年9月確認）。ただし、色の切り替えは `light-dark()` で足りるので、このフラグを使う場面は多くありません。

テーマを切り替える瞬間には、View Transitionで画面を上から塗り替えるアニメーションを付けています。切り替えの処理は、`types` に `theme-toggle` を指定して `document.startViewTransition()` に渡します。CSSの側では、`:active-view-transition-type(theme-toggle)` でアニメーションを定義します。動きを減らす設定をしているユーザーには、アニメーションを付けません。View Transitionsの書き方は「[11-5 View Transitionsで画面の切り替えをつなぐ](/interaction/view-transitions/)」で扱います。

## 案件でのダークモード

WordPressの案件では、ダークモードに対応せず、パレットの色を固定していることがほとんどです。デザインがライトの配色しか用意していないなら、無理に対応する必要はありません。

ダークモードに対応するなら、すべての色をセマンティクスのトークンで管理していることが前提になります。16進数の色がコンポーネントに直接書かれていると、その部分だけが切り替わりません。CMSで編集者が本文の文字に色を付けられる場合は、その色がダークモードの背景で読めるかどうかまでは保証できません。
