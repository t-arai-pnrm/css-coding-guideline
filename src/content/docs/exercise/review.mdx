## 組み上げたページを確かめる

最初は内容です。組み上げたトップページには、カンプどおりの内容しか入っていないので、内容の変化は、各節の後半のデモで確かめます。21-4の記事リストには、カンプの2倍の長さの見出し、画像のない記事、長い英単語の `Internationalization` が入っています。21-9のよくある質問には表と箇条書きの回答が、21-10の料金プランには長さの違う説明と項目が入っています。どれも、幅を320pxにしても横スクロールは出ず、部品の子が部品からはみ出しません（「[21-4 記事リストを作る](/exercise/article-list/)」）。

次は幅です。トップページを1280pxで見ると、ヘッダーにナビゲーションが1行で並び、帯の中身はどれも1080pxの幅にそろいます。制作の流れは横に、強みのカードは3列に並びます。768px以下では、ヘッダーがメニューのボタンに切り替わり、制作の流れは縦に並びます。フッターは、会社の情報の下にリンクのまとまりが回ります。強みのカードは、768pxではまだ3列で、約736px（カードの閾値648pxに、ガターとページの余白の88pxを足した幅）を下回ると1列になります。

拡大では、1280×900pxの画面でズームを200%にすると、ページから見た大きさは幅640px、高さ450px以下になり、768px以下と同じ形になります。高さも600px相当に満たないので、ヘッダーは留まらず、ページと一緒にスクロールします。メニューのボタンで開いたドロワーは、閉じるボタンとお問い合わせのボタンが画面に収まり、ナビゲーションの部分だけが中でスクロールします（「[21-7 ドロワーメニューを作る](/exercise/drawer/)」）。文字サイズの設定を200%に上げたときは、制作の流れの閾値と強みのカードの列の最小幅をremで書いているので、切り替わる幅も文字と同じ割合で大きくなります。ヘッダーは、文字が大きくなった分だけナビゲーションの並びが長くなり、1行に収まらなくなった時点で切り替わります。1280pxの画面でも、ヘッダーはメニューのボタンに、制作の流れは縦の並びに切り替わり、横にはみ出しません（「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」）。高さが900pxの画面では、ヘッダーを留める条件の600px相当が1200pxになるので、ヘッダーは留まらず、ページと一緒にスクロールします。文字が大きいほど、留めたヘッダーが本文を読める範囲を狭めるので、これも意図した切り替えです（「[21-6 固定ヘッダーを作る](/exercise/sticky-header/)」）。よくある質問の表は、幅320pxでは回答の幅に収まらなくなり、金額の数字の途中で折り返さずに、表の枠の中で横にスクロールします（「[21-9 よくある質問を作る](/exercise/faq/)」）。

ルートの `font-size` を変えた表示も確かめます。開発者ツールで `:root` に `font-size: 200%` を指定すると、remで書いた文字と寸法、コンテナサイズクエリの閾値がまとめて2倍になります。幅320px、768px、1024px、1280pxのどれでも横にはみ出さず、部品は、ブラウザの設定で文字を大きくしたときと同じ形に切り替わりました。ただし、メディアクエリの中のremは、ルートの `font-size` ではなく、ブラウザの設定の文字サイズを基準にします。ヘッダーを留める条件は600pxのままなので、ヘッダーは留まり続け、幅320pxでは2行に折り返して197pxの高さになります。ブラウザの設定で文字を大きくしたときは、この条件も1200pxに広がり、ヘッダーは留まりません。メディアクエリで決まる表示は、ブラウザの設定を変えた確認のほうで判断します（「[19-3 表示と操作を確かめる](/operations/verification/#拡大と文字サイズを200にする)」）。

キーボードでは、`Tab` キーで移動すると、ヘッダーのロゴ、ナビゲーション、お問い合わせのボタンの順にフォーカスが移り、ヒーローのボタンへ続きます。狭い幅では、ナビゲーションの代わりにメニューのボタンにフォーカスが移り、ドロワーを開くと、フォーカスはドロワーの中だけを移ります。ページ内リンクで移動したときは、見出しがヘッダーの下に隠れません（「[21-6 固定ヘッダーを作る](/exercise/sticky-header/)」）。

表示の設定では、まず動きを減らす設定を見ます。ドロワーの開閉、よくある質問の開閉、スクロールに合わせた表示は、どれも動きを減らす設定ではフェードだけになるか、動かなくなるように書いています（「[21-13 スクロールに合わせて表示する](/exercise/scroll-reveal/)」）。ホバーとフォーカスの状態は、背景の色だけでなく、下線、矢印の移動、フォーカスリングでも示しているので、グレースケールでも見分けられます。

強制カラーモードでは、`background-color` がシステムカラーに置き換わるので（「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」）、紺の帯、ヒーロー、フッター、おすすめのプランの紺の面は、ほかの面と同じ背景になります。おすすめのプランは「おすすめ」の文字でも示していて、紺の面は飾りなので、面が消えても情報は失われません（「[21-10 料金プランを作る](/exercise/pricing/)」）。一方、よくある質問の絞り込みのボタンと記事一覧のカテゴリーのリンクは、選んだ項目を塗りで示しています。塗りが消えると、どれを選んでいるかを見分けられなくなります。そこで、強制カラーモードのときだけ、選んだ項目に下線を引いています（「[21-4 記事リストを作る](/exercise/article-list/#今いるカテゴリーを-aria-current-で示す)」）。

この範囲では、組み上げたページの部品とページのCSSに直す箇所はありませんでした。ただし、Chromeだけで確かめた結果です。公開前には、動きを減らす設定とグレースケールを、その設定を有効にしたブラウザで確かめます。ここまでのすべての項目も、Safari（iOSを含む）とFirefoxで確かめ直します（「[1-2 ブラウザサポートとプログレッシブ・エンハンスメント](/principles/browser-support/)」）。

## 自分でレビューする

次の見出しからの解説を読む前に、このプルリクエストを自分でレビューしてください。コードは配布版のHTMLとCSSで読み、表示は幅を変えて、操作はポインターと `Tab` キーで確かめます。読み進める順番は、19-2の段階（規約から始まり、コメントで終わる9つの段階）に従います（「[19-2 レビューの進め方](/operations/review/#確認する順番)」）。

見つけた問題ごとに、根拠、修正案、ラベルを書きます。根拠には、どのルールや仕様に反しているかと、どの表示や操作で問題が現れるかを書きます。ラベルは、直さなければならない指摘の `MUST`、好みが入りうる提案の `IMO`、質問の `Q` のどれかです（「[19-2 レビューの進め方](/operations/review/#指摘の深刻度ラベル)」）。

手元で試すときは、配布版の[index.html](/exercise-files/review/index.html)（サンプル一式のZIPでは `exercise/review/index.html`）を開きます。同じディレクトリの `notice-card.css`、`notice-section.css`、`page-top.css`、`compositions.css` が、プルリクエストのCSSです。書き終えたら、次の見出しからの解説と見比べ、見落とした誤りと、ラベルの付け方の違いを確かめます。

## 表示と操作に現れる症状

幅を320pxにすると、カードとカードの間が、一覧の `gap` の16pxにカードの `margin-block-end` の24pxが足されて、40px空きます。タグの色は、一覧から赤を渡しているはずなのに、デフォルトのティールのままです。見出しは、ページのCSS（`page-top.css`）の `!important` で15pxに固定されています。画像が明るくなるのはマウスでホバーしたときだけで、キーボードでフォーカスしても変わりません。

3件目のカードの5つのタグは、折り返さずに縮み、「重/要」「Infrastruc/ture」のように単語の途中で改行されます。はみ出す代わりに縮んで現れるのは、デモの土台のCSSがすべての要素の `min-inline-size` を0にしているからです。

解説も、19-2の順番で進めます。5つの誤りは、規約、上書き、内容の変化、境界の段階で見つかります。残りの1つは、カードのCSSだけでは見つからず、値を渡すテンプレートとの照合か、画面を起点にした調査が要ります。

## コンテナとホバーの書き方

規約の段階では、2つの誤りが見つかります。1つ目（誤り2）は、カードのコンテナです。ルートに `container-type: inline-size` を単体で書き、`._body` で、名前のない `@container (width >= 300px)` を問い合わせています。名前のないクエリはいちばん近い祖先のコンテナを参照するので、コンテナが入れ子になると、参照先がコードから読み取れなくなります。条件は書字方向に依存しない `inline-size` で、閾値は文字サイズの設定に追従するremの式で書きます（「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」）。

```css title="🙆‍♂ Recommended: ルートを名前付きのコンテナにし、フラグを宣言する要素だけがクエリを書く"
@scope (.scoped.notice-card) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
    display: block grid;
    gap: 12px;
  }

  ._body {
    --_density: --compact;

    display: block grid;
    gap: 8px;

    @container --scoped (inline-size >= calc(300 / 16 * 1rem)) {
      --_density: --spacious;

      gap: 12px;
    }
  }
}
```

直した形では、`._body` がフラグ `--_density` を宣言し、コンテナサイズクエリはこのルールにだけ書きます（「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」）。300pxという値の根拠は、コードから読み取れないので、`Q` のラベルで尋ねます。列の最小幅などから決めた値なら、その条件を式に書いてもらいます（「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」）。

2つ目（誤り3）は、ホバーです。カードのスコープの外に `.notice-card:hover img { filter: brightness(1.08); }` と書いています。カードのどこにポインターを置いても画像が明るくなりますが、押せるのは見出しのリンクだけです。ホバーを `@media (any-hover)` の中に書いておらず、キーボードでフォーカスしたときの変化もありません（「[17-1 ホバーとフォーカスを表す](/interaction/states-and-focus/)」）。スコープの外にあるので、カードの中に別のコンポーネントを入れると、その中の画像まで選びます。

```css title="🙆‍♂ Recommended: 見出しのリンクのホバーとフォーカスで --_has-hocus を立て、画像はフラグで切り替える"
@scope (.scoped.notice-card) to (.scoped) {
  :scope {
    --_has-hocus: --false;

    &:has(h3 a:any-link:hover) {
      @media (any-hover) {
        --_has-hocus: --true;
      }
    }

    &:has(h3 a:focus-visible) {
      --_has-hocus: --true;
    }
  }

  img {
    /* ... */

    @container style(--_has-hocus: --true) {
      filter: brightness(1.08);
    }
  }
}
```

状態の判定はルートの1か所にまとまり、画像はフラグを読むだけです。記事リストで、行全体を押せるようにしたときと同じ形です（「[21-4 記事リストを作る](/exercise/article-list/#見出しのリンクを行いっぱいに広げる)」）。

## ページのCSSからの上書き

不要な記述や副作用のある上書きの段階では、トップページのCSS（`page-top.css`）が目に留まります（誤り4）。`pages` のレイヤーに、`.page-top .notice-card h3` を選ぶルールがあります。ページがお知らせのカードの内部を選び、見出しの大きさを `font-size: calc(15 / 16 * 1rem) !important` で上書きしています。カードの見出しを直す人は、カードのファイルを読んでも、15pxになる理由を見つけられません（「[10-2 コンポーネントの境界を守る](/components/boundaries/)」）。

`!important` が要ったのは、本書のレイヤーの順番では `pages` が `components` より前にあり、ページの宣言は詳細度に関わらずカードの宣言に負けるからです。重要な宣言ではレイヤーの順位が逆になるので勝てますが、ページからカードの内部を変えているという問題はそのまま残ります（「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」）。

見出しの大きさは、カードのCSSで決めます。狭い列でtitleの役割（18px）では大きすぎることが理由なら、カードが置かれた幅で文字の役割を切り替えます。誤り2を直したときに `._body` で宣言した `--_density` を、見出しが読みます。狭い列ではsubtitle（16px）、広い列ではtitleにします（「[14-5 文字の役割と色](/typography/text-roles/)」）。

```css title="🙆‍♂ Recommended: 見出しの大きさはカードが幅のフラグで決め、ページからは選ばない"
@scope (.scoped.notice-card) to (.scoped) {
  h3 {
    font-size: calc(var(--text--subtitle--font-size) / 16 * 1rem);
    line-height: var(--text--subtitle--leading);

    @container style(--_density: --spacious) {
      font-size: calc(var(--text--title--font-size) / 16 * 1rem);
      line-height: var(--text--title--leading);
    }
  }
}
```

ただし、15pxにした理由がほかにあるかは、コードからは分かりません。この指摘には、理由を尋ねる質問を添えます（後述の指摘の見本）。

## タグの並びと内容の変化

内容の変化の段階では、タグの並び（誤り6）を見ます。`._tags` は `display: block flex` と `gap` だけで、`flex-wrap` がありません。タグの数は記事ごとに変わるので、入りきらなくなったときに折り返す指定が要ります（「[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)」）。

直すときは、`flex-wrap: wrap` を足すより、記事のカードと同じ `cluster` コンポジションを使います。タグの `ul` を `<ul class="_tags | cluster">` にし、カードは間隔だけを公開プロパティで渡します（「[12-3 cluster：子を横に並べ、入りきらなければ折り返す](/compositions/cluster/)」）。配布版の `review` の `compositions.css` には、ほかの節で使っている `cluster` も入っています。`display: flex` の1値の構文はStylelintでも見つかるので、レビューの前にlintを通してもらいます。

```css title="🙆‍♂ Recommended: タグの並びは cluster に任せ、カードは間隔だけを渡す"
@scope (.scoped.notice-card) to (.scoped) {
  ._tags {
    --cluster--row-gap: 4px;
    --cluster--column-gap: 12px;

    font-size: calc(var(--text--caption--font-size) / 16 * 1rem);
    line-height: var(--text--caption--leading);
  }
}
```

この誤りは、表示が崩れているので `MUST` です。ただし、本書の規約を採用していないプロジェクトなら、`MUST` で求めるのは折り返すことまでで、`cluster` に替えるのは `IMO` の提案です。

## カードのルートの外側の余白

コンポーネントの境界の段階では、カードのルートの `margin-block-end: 24px`（誤り1）を見ます。カードとカードの間隔は一覧の `gap` が持っているので、ルートの余白がそこに足され、320pxでは40px空いています。カードを別の場所に置けば、置く側がこの余白を打ち消すことになります（「[10-2 コンポーネントの境界を守る](/components/boundaries/)」）。

ルートの余白は消します。24pxの間隔がデザインで必要なら、一覧のテンプレートで `ul` の `style` 属性の `--grid--gap` を24pxにします。記事のカードでも、カードに幅と外側の余白を書かず、一覧のグリッドに任せています（「[21-3 カード一覧とサイドバーを作る](/exercise/card-grid/#カードの幅と外側の余白は並べるグリッドが決める)」）。

## 色が変わらない原因をたどる

最後の誤り（誤り5）は、カードのCSS（`notice-card.css`）だけでは見つかりません。カードのCSSは `:scope` で `--notice-card--accent` を正しく受けていて、誤りは一覧のテンプレートの側にあるからです。見つけるには、値を渡すテンプレートとカードの名前を照らし合わせるか、表示を起点に原因をたどる必要があります。ここでは表示から始めます。画面で、赤を渡したはずのタグがティールのままだと気付いたら、「[19-4 表示の崩れを開発者ツールで調べる](/operations/devtools/#宣言が効かない)」の「宣言が効かない」の手順で原因をたどります。

開発者ツールでタグのリンクを選ぶと、`color: var(--_accent)` には取り消し線がなく、宣言は勝っています。宣言が勝っていても表示が思った色と違うので、参照しているカスタムプロパティの値を確かめます。タグの色はデフォルトのティールなので、`--_accent` には、`var()` のフォールバックに書いたトークンの色が使われています。つまり、`--notice-card--accent` がカードまで届いていません。そこで、値を渡しているはずの祖先の `li` をElementsパネルで選び、`style` 属性を読むと、宣言されていたのは綴りの違う `--notice-card--acent` でした。

テンプレートの名前を `--notice-card--accent` に直します。あわせて、カードのファイルの先頭に、公開プロパティを `@prop` で並べた説明ブロックを足してもらいます。ドロワーに置くナビゲーションでも、公開プロパティを足したときに同じ一覧を書きました（「[21-7 ドロワーメニューを作る](/exercise/drawer/#同じナビゲーションを縦に並べる)」）。

```css title="🙆‍♂ Recommended: 公開プロパティを説明ブロックの @prop に並べ、使う側が名前を照らし合わせられるようにする"
/**
 * お知らせのカード。
 *
 * @prop {color} --notice-card--accent [var(--foreground--accent)] - タグの色
 */
@scope (.scoped.notice-card) to (.scoped) {
  :scope {
    --_accent: var(--notice-card--accent, var(--foreground--accent));

    /* ... */
  }

  ._tags {
    /* ... */
  }

  ._tag-link {
    color: var(--_accent);
  }
}
```

説明ブロックに公開プロパティの名前が並んでいれば、レビュアーはテンプレートの差分をその名前と照らし合わせられます。そうすれば、綴りの誤りは、画面で確かめる前のコードレビューの段階でも見つかります。

## 指摘の見本

指摘には、ラベル、理由、解決策をセットで書き、当てはまるルールのIDを添えます（「[19-2 レビューの進め方](/operations/review/#レビューの指摘に書く内容)」）。誤り4と誤り5の指摘を、見本として示します。

```md title="🙆‍♂ Recommended: 境界を越えた上書きに、理由と解決策を書き、意図を尋ねる"
[MUST] トップページのCSSの `.page-top .notice-card h3 { font-size: … !important; }` は削除してください。ページがお知らせのカードの内部を選んでいるので、カードの見出しを直す人は、カードのファイルだけでは15pxになる理由を見つけられません（`no-other-component-internals`）。`!important` は、`pages` のレイヤーで負けていた宣言の順位を逆にしているだけです（`no-important-for-specificity`）。見出しの大きさはカードのCSSで決め、狭い列で大きすぎることが理由なら、`--_density` が `--spacious` のときだけtitleの役割（18px）にしてください（`density-via-style-query`）。

[Q] 15pxにしたのは、どの幅で見出しが大きすぎたからでしょうか。トップページに置いたときだけ小さくしたい事情があれば、カードの公開プロパティにするかを相談させてください。
```

```md title="🙆‍♂ Recommended: 画面で見つけた誤りに、たどった手順と解決策を書く"
[MUST] お知らせの一覧のテンプレートで `li` に渡している `--notice-card--acent` は、`--notice-card--accent` の綴りの誤りです。カードはこの名前を読まないので、タグの色が赤ではなく、デフォルトのティールのままです。開発者ツールでタグのリンクを選ぶと、`--_accent` がフォールバックの `--foreground--accent` になっていました。テンプレートの名前を直してください。あわせて、カードのCSSの先頭に `@prop` の説明ブロックを足し、公開プロパティの名前を照らし合わせられるようにしてください（`prop-tag-for-public-properties`）。
```

1つ目は、`MUST` の指摘に `Q` を添えています。15pxにした理由によって、カードの中で幅から切り替えるか、公開プロパティにするかが変わるからです。2つ目は、原因をたどった手順を書いているので、レビュイーが同じ手順で確かめられます。

## 直した箇所と直さずに済んだ箇所

組み上げたトップページは、確かめた範囲では直さずに済みました。

プルリクエストで直すのは、お知らせのカードの `notice-card.css`、トップページの `page-top.css`（上書きの削除）、一覧のテンプレート（公開プロパティの名前と `cluster` のクラス）です。一覧の `notice-section.css` と `grid` コンポジションは直さずに済みます。6つの誤りは、この章の部品が守ってきた規約と1つずつ対応します。誤り1から3は、外側の余白を持たないこと、名前付きのコンテナとフラグ、`--_has-hocus` で伝えるホバーとフォーカスに当たります。誤り4から6は、置く側から内部を選ばないこと、`@prop` の一覧、`cluster` で並べるタグに当たります。

これで演習は終わりです。章の概要の「[この章で判断できるようになること](/exercise/#この章で判断できるようになること)」に戻り、要件の変更を受け持つのが部品、コンポジション、置く側のページのどれかを見分けられるようになったかを振り返ってください。この節のレビューで見た項目は、付録D「[レビューのチェックリスト](/appendix/checklist/)」に、19-2の順番で並んでいます。

## 判断の問い

### 問い1

誤り5の綴りの誤り（`--notice-card--acent`）は、Stylelintで見つけられますか。見つけられないなら、何で防ぎますか。

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えと解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

見つけられません。どのカスタムプロパティを宣言しても構文としては正しく、しかもこの宣言はCSSのファイルではなく、テンプレートの `style` 属性にあるからです。防ぐのは、レビューと、画面での確認です。カードのファイルの先頭に `@prop` で公開プロパティを並べておけば、レビュアーはテンプレートの名前と照らし合わせられます（「[9-10 コメントの書き方](/notation/comments/)」）。

</details>

### 問い2

誤り4の指摘に、トップページの担当者から「お知らせの見出しは、どこに置いても15pxにしたい」と返事が来ました。どこに書きますか。

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えと解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

カードのCSSの `h3` に書きます。どこに置いても同じ大きさなら、それはカード自身の文字の階層の決定で、置き場所の判断ではないからです。幅のフラグで切り替える必要もなくなります。ただし、15pxに当たる文字の役割はないので、役割を足すか、近いsubtitle（16px）で足りるかを担当者と決めます（「[14-5 文字の役割と色](/typography/text-roles/)」）。トップページに置いたときだけ15pxにしたいという返事だったなら、置き場所で決まる見た目なので、置く側からフラグか公開プロパティで渡します（「[10-7 置き場所と子の状態を伝える](/components/placement-and-child-states/)」）。

</details>

### 問い3

章の概要では、規約の良し悪しを、変更を受け持つ場所を予測できるか、影響範囲を確かめられるか、条件分岐が複雑になっていないかの3つで確かめると述べました。21-2から21-14の後半の変更を、この3つで振り返ってください。それぞれの変更は、部品、コンポジション、置く側のページのどこが受け持ちましたか。部品のCSSを直した変更で、ほかの置き場所に影響がないことは、何を読めば確かめられますか。表示を切り替える条件は、部品の中のどこに集まっていますか。

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えと解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

受け持つ場所は、変更の内容から予測できます。紺の面に置く（21-2）、まとまりや帯の並べ替え（21-5、21-14）、帯の外に置くお知らせ（21-6）は、置く側が受け持ち、部品は直しませんでした。置かれた幅で形を変える（21-3）、中身の量が変わる（21-4、21-10）、項目やステップが増える（21-7、21-11）は、部品の中の配置の話なので、部品が受け持ちます。そのうち21-11で直したのは、閾値の式の中の値だけでした。21-7では、ナビゲーションが溢れたこと自体を条件にしていたので、CSSを直していません。

影響範囲は、部品が外から受け取るものを2つに分けて確かめます。1つは、置く側が渡す値です。部品は外側の余白と幅を持たず、置き場所の違いは `--global-nav--stacked` のような公開プロパティか、`color-scheme` のような継承する値で受け取っています。テンプレートでその名前を検索すれば、置く側が値を渡している場所を挙げられます。もう1つは、置かれた幅と中身です。部品の中の閾値は、どれも部品のルートのコンテナを問い合わせているので、ほかの部品のコンテナの定義やビューポートの幅には依存しません。ただし、ルートの幅は置き場所で変わり、その幅で形が切り替わります。21-3のカードが狭い列と広い列で違う形になったのは、このためです。そのため、名前の検索に加えて、部品を置いたテンプレートを開き、置かれる列の幅と、中身の量や項目の数を確かめます。

切り替えの条件はフラグにまとまっていて、コンテナサイズクエリを書いたのは、各部品で `--_density` を宣言する1つのルールだけです。ヘッダーの折りたたみは、溢れを検知して立てる `--_overflowing` にまとまっています。ホバーとフォーカスは `--_hocus` か `--_has-hocus` に、画面に入ったことは `--_in-view` に集まっています。紺の面のような置き場所ごとの見た目は、部品の中に条件として書かず、配色の切り替えに任せたので、面が増えても部品の分岐は増えません（「[10-7 置き場所と子の状態を伝える](/components/placement-and-child-states/)」）。

</details>

## この節で使ったルール

- [`verify-worst-case-content`](/operations/verification/#rule-verify-worst-case-content)：実装後は、長い見出し、折り返せない文字列、読み込めない画像、0件・1件・多数の項目を入れたテストページで表示を確かめます。
- [`verify-text-resize-200`](/operations/verification/#rule-verify-text-resize-200)：ブラウザのズームと文字サイズの設定をそれぞれ200%にしても、内容が欠けず、操作できることを確かめます。
- [`verify-keyboard-and-display-settings`](/operations/verification/#rule-verify-keyboard-and-display-settings)：キーボードだけで操作し、強制カラーモード、動きを減らす設定、グレースケールの表示を再現して確かめます。
- [`review-check-order`](/operations/review/#rule-review-check-order)：レビューは、規約、トークン、ブラウザ対応、不要な記述、グローバルのCSS、内容の変化への耐性、コンポーネントの境界、レスポンシブ、コメントの順に確認します。
- [`review-reason-and-solution`](/operations/review/#rule-review-reason-and-solution)：レビューの指摘には、理由と解決策を必ずセットで書きます。
- [`review-severity-labels`](/operations/review/#rule-review-severity-labels)：レビューの指摘には `MUST`、`IMO`、`Q` のラベルを付けて、深刻度を区別します。
- [`devtools-find-winning-declaration`](/operations/devtools/#rule-devtools-find-winning-declaration)：宣言が効かないときは、詳細度を上げたり `!important` を付けたりする前に、開発者ツールで勝っている宣言と、差が付いた段階を確かめます。
- [`container-shorthand`](/responsive/container-size-queries/#rule-container-shorthand)：コンテナは `container` ショートハンドで、名前と種類をまとめて指定します。
- [`container-name-required`](/responsive/container-size-queries/#rule-container-name-required)：コンポーネントのルートをコンテナにするときは `container: --scoped / inline-size` と書き、`@container --scoped (…)` で問い合わせます。
- [`container-query-inline-size`](/responsive/container-size-queries/#rule-container-query-inline-size)：コンテナサイズクエリの条件では、`width` ではなく `inline-size` を使います。
- [`breakpoint-in-rem`](/responsive/breakpoints/#rule-breakpoint-in-rem)：ブレイクポイントはremで指定し、ピクセル値からの変換を式で書きます。
- [`threshold-as-formula`](/responsive/breakpoints/#rule-threshold-as-formula)：クエリの閾値は、レイアウトが成り立つ条件を `calc()` の式で書きます。
- [`density-via-style-query`](/components/style-queries/#rule-density-via-style-query)：同じ閾値で変わる子要素が2つ以上あるときは、コンテナサイズクエリをフラグを宣言する1つの要素のルールだけに書き、ほかの子孫はスタイルクエリで切り替えます。
- [`hover-operable-in-any-hover`](/interaction/states-and-focus/#rule-hover-operable-in-any-hover)：ホバーのスタイルは操作できる状態に限定し、`@media (any-hover)` の中に書きます。
- [`hover-with-focus-visible`](/interaction/states-and-focus/#rule-hover-with-focus-visible)：ホバーで変える見た目は、`:focus-visible` にも同じように指定します。
- [`hocus-via-style-query`](/components/style-queries/#rule-hocus-via-style-query)：ホバーとフォーカスで子要素の見た目を変えるときは、フラグを立てて `@container style()` で切り替えます。子孫の状態をほかの子孫に伝えるときは、`&:has()` で `--_has-hocus` を立てます。
- [`no-other-component-internals`](/components/boundaries/#rule-no-other-component-internals)：ほかのコンポーネントのルートや内部の要素を、セレクタで選んで見た目を上書きしません。
- [`no-important-for-specificity`](/cascade/cascade-basics/#rule-no-important-for-specificity)：詳細度や読み込み順の競争に勝つ目的で `!important` を使いません。
- [`flex-wrap-for-variable-items`](/layout-practice/defensive/#rule-flex-wrap-for-variable-items)：要素の数が変わる可能性のあるFlexboxには、`flex-wrap: wrap` を指定します。
- [`compositions-for-layout-patterns`](/components/compositions-and-utilities/#rule-compositions-for-layout-patterns)：並べて折り返すといった、コンポーネントに依存しない配置は、コンポジションで書きます。
- [`no-external-layout-on-root`](/components/boundaries/#rule-no-external-layout-on-root)：コンポーネントのルートに、外側の余白や配置の指定を書きません。
- [`prop-tag-for-public-properties`](/notation/comments/#rule-prop-tag-for-public-properties)：公開プロパティを持つファイルでは、説明ブロックの `@prop` に、型、デフォルト値、説明を書きます。
