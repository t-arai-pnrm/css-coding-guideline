レイアウトを組むときは、まず親の `grid-template` で子要素の配置と大きさを決められないかを検討します。Gridなら配置が親の指定だけで完結し、子要素の側に幅の計算や個別の指定を書かずに済みます。ただし、GridはFlexboxの上位互換ではありません。タグやメニューのように、中身の量で幅が決まる要素を並べて折り返すなら、Flexboxのほうが向いています。

配置の構造が変わるレイアウトは、`grid-template` のエリアに名前を付けて書き、条件ごとにテンプレートだけを書き換えます。並べたカードの中で見出しや本文、ボタンの位置をそろえたいときは、サブグリッドを使います。この節では、この3つを順に説明します。

## 子要素の側で配置を決めるFlexbox

カードを3列の格子状に並べるとき、Flexboxで書くと次のようになります。親で折り返しと間隔を指定し、子要素の幅は「親の幅から間隔の合計を引き、列数で割る」という計算で決めています。

```css title="🙅‍♂ Not Recommended: 格子状の並びを、子要素の幅の計算で作る"
/* 🙅‍♂ Not Recommended */
.card-list {
  display: flex;
  flex-wrap: wrap;
  gap: 16px;
}

.card-list > * {
  flex-basis: calc((100% - 16px * 2) / 3);
}
```

この書き方では、子要素が親の間隔と列数を知っている必要があります。間隔を24pxに変えたら、子要素の計算式も直さなければなりません。列数を変えるときも同じです。レイアウトを決める情報が親と子に分かれているので、どちらか一方だけを直して崩れる、という事故が起きやすくなります。

ページ全体の段組みでも、同じことが起きます。固定幅のナビゲーション、伸び縮みする本文、固定幅のサイドバーをFlexboxで並べると、1つ目と3つ目の子要素には `flex-shrink: 0` と `flex-basis` を、2つ目には `flex-grow: 1` を指定することになります。3つの子要素のCSSを読み合わせないと、全体がどういう段組みなのかが分かりません。

Gridなら、どちらの例も親の指定だけで書けます。

```css title="🙆‍♂ Recommended: 列の数と幅を親で決める"
._card-list {
  display: block grid;
  grid-template-columns: repeat(3, minmax(0, 1fr));
  gap: 16px;
}

._page {
  display: block grid;
  grid-template-columns: calc(240 / 16 * 1rem) minmax(0, 1fr) calc(320 / 16 * 1rem);
}
```

`grid-template-columns` を読めば、何列でどういう幅なのかが1行で分かります。子要素の側には、配置のための指定が何もありません。列の幅を `1fr` ではなく `minmax(0, 1fr)` と書いている理由は、「[7-3 変化に強いレイアウト](/layout/defensive/)」で説明します。

よく「1次元ならFlexbox、2次元ならGrid」と言われます。しかし、ページの段組みは横に1列並べるだけの1次元のレイアウトで、それでもGridのほうが簡潔です。次元の数ではなく、「配置と大きさを親から決めたいかどうか」で選ぶほうが実態に合っているという印象です。

## GridとFlexboxを使い分ける

私が使い分けの基準にしているのは、子要素の大きさを親が決めるのか、子要素の中身が決めるのかです。親が列の幅や数を決めたいならGridを、子要素の中身の量に合わせて並べたいならFlexboxを選びます。

| レイアウト | 選ぶもの | 理由 |
|---|---|---|
| カードを格子状に並べる | Grid | 列の数と幅を親で決められる |
| 幅によって配置の構造が変わる | Grid | エリアのテンプレートを書き換えるだけで済む |
| 要素を重ねる | Grid | 同じエリアに置けば、重ねたどの要素の高さも親に反映される |
| タグやメニューを並べて折り返す | Flexbox | 子要素の幅を決めずに、中身の量で並べられる |
| 固定幅と可変幅の2カラムを、狭いときは縦に積む | Flexbox | `flex-grow` の差で、クエリなしに折り返せる |
| 画像のまわりに文字を回り込ませる | float | 回り込みは `float` にしかできない |

タグの一覧やグローバルナビゲーションのリンクは、1つずつ文字数が違います。Gridで列を決めると、短いタグにも長いタグと同じ幅が割り当てられてしまいます。Flexboxなら、子要素の幅を決めずに並べるだけで、入りきらない要素は次の行へ回ります。この並び方は、第6章のコンポジション `cluster` として部品にしています（「[6-2 コンポジションとユーティリティ](/components/compositions-and-utilities/)」）。

固定幅のサイドと伸び縮みするメインの2カラムも、Flexboxが得意な配置です。メインの `flex-grow` をサイドよりはるかに大きくしておくと、幅に余裕があるうちは横に並び、足りなくなるとクエリなしで縦に積まれます。Gridでは、列の数を切り替えるためにクエリが必要です。この配置は、コンポジション `sidebar` として同じく第6章で紹介しています。

反対に、Gridを選ぶと効果が大きい例として、ロゴ、ナビゲーション、ボタンを左端、中央、右端に置くヘッダーがあります。`grid-template-columns: 1fr auto 1fr` と書くと、中央のリンクが増えたとき、左右の列が縮んでロゴやボタンが潰れてしまいます。左右の列の最小値を `max-content` にすれば、左右の列は中身の幅より狭くなりません。

```css title="🙆‍♂ Recommended: 左右の列が中身より狭くならないようにする"
._header {
  display: block grid;
  grid-template-columns: minmax(max-content, 1fr) auto minmax(max-content, 1fr);
  align-items: center;

  & > :last-child {
    justify-self: end;
  }
}
```

左右の列は、余裕があれば `1fr` で均等に広がるので、中央の列はヘッダーのちょうど真ん中に置かれます。ただし、3つの中身の合計より狭い画面でははみ出すので、狭い画面では別の配置に切り替える前提の書き方です。

表の最後の `float` は、古い手法だと思われがちです。しかし、画像のまわりに文字を回り込ませるという本来の用途では、今でも `float` が最適です。レイアウトのために `float` を使っていた時代のclearfixは不要で、囲む要素に `display: flow-root` を指定すれば、`float` の要素が囲む要素の中に収まります。

```css title="🙆‍♂ Recommended: 回り込みには float を使い、flow-root で内側に収める"
._description {
  display: block flow-root;
}

._figure {
  float: inline-end;
  inline-size: min(50%, calc(320 / 16 * 1rem));
  margin-inline-start: 16px;
}
```

`float` の値は、`right` ではなく `inline-end` と論理値で書きます。論理値にそろえる理由は「[5-3 モダンな記法にそろえる](/notation/modern-syntax/)」で説明しています。

## `grid-template` に配置を描く

幅によって配置の構造が変わるレイアウトは、`grid-template` のエリアに名前を付けて書きます。エリアの名前は、そのエリアに置く子要素のクラス名とそろえ、`--` で始めます。`._image` を置くエリアは `--image` です。`--` で始める理由は「[5-1 命名規則](/notation/naming/)」で説明しています。

```css title="🙆‍♂ Recommended: エリアに名前を付け、条件ごとにテンプレートだけを書き換える"
@scope (.scoped.feature-card) to (.scoped) {
  :scope {
    container: --feature-card / inline-size;
  }

  ._layout {
    display: block grid;
    grid-template:
      "--image"
      "--heading"
      "--body";
    gap: 16px;

    @container --feature-card (inline-size >= calc(560 / 16 * 1rem)) {
      grid-template:
        "--image --heading" auto
        "--image --body" 1fr
        / minmax(0, 1fr) minmax(0, 1fr);
    }

    & > ._heading {
      grid-area: --heading;
    }

    & > ._body {
      grid-area: --body;
    }

    & > ._image {
      grid-area: --image;
    }
  }
}
```

```html
<article class="scoped feature-card">
  <div class="_layout">
    <h2 class="_heading">…</h2>
    <div class="_body">…</div>
    <img class="_image" src="…" alt="" width="640" height="480">
  </div>
</article>
```

狭い場所では、画像、見出し、本文の順で縦に積みます。広い場所では、画像を左側、見出しと本文を右側へ置いています。クエリの中で書き換えているのは `grid-template` だけで、子要素の配置の指定は1か所ずつしかありません。テンプレートの文字列が、そのまま配置の図として読めるのも利点です。

子要素の `grid-area` は、親のルールの中に `& > ._heading` のようにネストして書いています。`grid-area` は、親のテンプレートとセットで初めて意味を持つ指定だからです。こうしておくと、どのグリッドに対する配置なのかが読み取れ、テンプレートを書き換えるときも一緒に直せます。ネストしてよい場面は「[5-2 ネストとプロパティの並び順](/notation/nesting-and-order/)」で説明しています。

この例では、HTMLには見出しを先に書き、見た目では画像を先に表示しています。HTMLは見た目の順番ではなく、見出しから始まる文書構造の順番で書き、見た目の順番はGridの配置で変えます。スクリーンリーダーの読み上げや、CSSが効かない環境でも、内容が意味の通る順番で伝わるからです。

ただし、リンクやボタンのようにフォーカスできる要素を並べ替えると、キーボードで移動する順番が見た目と食い違います。見た目の順番に合わせて移動させる `reading-flow` というプロパティもありますが、2026年9月の時点で対応しているのはChrome系のブラウザだけです。フォーカスできる要素は、HTMLの順番と見た目の順番をそろえておきます。

## サブグリッドでカードの中の行をそろえる

カードを横に並べると、見出しの行数や本文の長さがカードごとに違い、ボタンの位置がばらばらになります。よくある対策は、カードを `flex-direction: column` にして、本文に `flex-grow: 1` を指定する方法です。これでボタンの位置はそろいますが、見出しの高さはそろいません。そろえられるのは、伸ばした1か所だけです。

見出しに `min-height` を指定したり、JavaScriptで高さを測ってそろえたりする方法もあります。しかし、固定の高さは見出しが想定より長くなると破綻し、JavaScriptは読み込みや再計算の手間がかかります。今は、サブグリッドを使えばCSSだけですべての行をそろえられます。

<Baseline id="subgrid" />

```css title="🙆‍♂ Recommended: カードの行を、並べる側のグリッドの行に参加させる"
@scope (.scoped.card-grid) to (.scoped) {
  :scope {
    display: block grid;
    grid-template-columns: repeat(auto-fit, minmax(min(100%, calc(200 / 16 * 1rem)), 1fr));
    gap: 24px 16px;
  }

  ._card {
    display: block grid;
    grid-template-rows: subgrid;
    grid-row: span 3;
    row-gap: 8px;
  }
}
```

`grid-template-rows: subgrid` を指定したカードは、自分の行を持たず、並べる側のグリッドの行をそのまま使います。同じ行に並んだカードの見出しは、同じ高さの行に入ります。行の高さは、その行でいちばん高い見出しに合わせて決まります。本文とボタンの行も同じです。

`grid-row: span 3` は、カードが親の行を3行分使うという指定で、中の要素の数と一致させます。指定を忘れると、カードは親の1行分にしかまたがらず、見出しと本文とボタンが同じ1行に押し込まれてしまいます。サブグリッドの行の間隔は、何も指定しなければ親の `gap` を引き継ぐので、カードの中の間隔は `row-gap` で指定し直しています。

サブグリッドにした方向には、暗黙のトラックが作られません。カードに4つ目の要素を足しても、`span 3` のままでは新しい行は増えず、はみ出した要素は最後の行に重なります。要素を足したら、`span` の数も直します。また、サブグリッドの中の線の番号は、1から数え直されます。カードの中で `grid-row: 1` と書けば、カードが親のどの行に置かれていても、カードの最初の行を指します。

次のデモでは、見出しと本文の長さが違う3枚のカードを並べています。幅のボタンで768pxを選ぶと3列になり、見出し、本文、ボタンの位置が横一列にそろいます。

<Demo title="サブグリッドで、カードの見出し・本文・ボタンの位置をそろえる" html={subgridHtml} css={subgridCss} />

サブグリッドは、列をそろえるときにも使えます。日付、カテゴリ、タイトルを1行ずつ並べるニュースの一覧を考えます。列の幅を決める前に、それぞれの列が可変か不変かを考えます。日付は途中で改行されると読みにくいので、改行しない不変の列です。カテゴリは長すぎると窮屈になるので、上限を決めた可変の列にします。タイトルは、残りの幅をすべて使う可変の列です。

```css title="🙆‍♂ Recommended: 列ごとに可変か不変かを決め、項目の列をサブグリッドでそろえる"
@scope (.scoped.news-list) to (.scoped) {
  ._list {
    display: block grid;
    grid-template-columns: max-content fit-content(calc(160 / 16 * 1rem)) minmax(0, 1fr);
    column-gap: 24px;
    padding-inline: 24px;
  }

  ._item {
    display: block grid;
    grid-template-columns: subgrid;
    grid-column: 1 / -1;
    align-items: baseline;
    padding-block: 1rlh;
  }
}
```

1列目の `max-content` は、日付の幅そのものです。日付の列は、中身より狭くならず、改行もされません。2列目の `fit-content()` は、中身の幅に合わせつつ、括弧の中の値を上限にする指定です。カテゴリが短ければ短いなりの幅になり、長ければ160px相当で折り返します。3列目の `minmax(0, 1fr)` は、残りの幅をすべて受け取ります。

`<li>` にあたる `._item` は、`grid-column: 1 / -1` で親の3列すべてにまたがり、`grid-template-columns: subgrid` で親の列をそのまま使います。どの項目のカテゴリが長くても、列の幅は一覧全体で1つに決まるので、日付、カテゴリ、タイトルの開始位置がすべての行でそろいます。`align-items: baseline` は、文字の大きさが違うカテゴリとタイトルを、文字のベースラインでそろえる指定です。項目の上下の余白には、ルート要素の行の高さを単位にした `1rlh` を使っています。

<Demo title="日付・カテゴリ・タイトルの列を、サブグリッドで全項目にそろえる" html={newsHtml} css={newsCss} />

サブグリッドが効くのは、グリッドの直接の子だけです。カードを `<li>` で包んでいるなど、グリッドとカードの間に別の要素があるときは、その要素に `display: contents` を指定して箱をなくします。ただし、`display: contents` を指定した要素は、ブラウザによっては暗黙のロールを失うことがあります。ロールを持たない `<div>` なら問題はありません。`<li>` や `<section>` なら、`role` 属性でロールを明示し、スクリーンリーダーで読み上げを確かめます。

サブグリッドを使うカードは、親がグリッドであることを前提にしています。そのため、カードを並べる側のグリッドまで含めて、1つのコンポーネントとして扱います。この考え方は「[6-1 コンポーネントの境界を守る](/components/boundaries/)」で説明しています。
