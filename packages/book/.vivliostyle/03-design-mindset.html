第2章 CSS設計の考え方

この章では、CSSを書き、設計するときの判断の土台を扱います※1。第III部「設計編」（第8章から第10章）のルールは、この章の考え方を具体化したものです。

本書が最も重視するのは、保守しやすさです。Webサイトは公開した後の運用の期間のほうがずっと長く、その間も壊れにくいことをコードの短さより優先します※2。

もう1つの前提は、内容が変わることです※3。

この章で判断できるようになること

この章を読むと、共通化したカードに項目を足すような変更で、保守性、拡張性、再利用性のどれが損なわれるかを見分けられるようになります。似た記述が2か所にあるとき、すぐに共通化するか、3回目に現れるまで重複を残すかも、共通化したスタイルの影響範囲が見えにくいことを踏まえて判断できます。width: 100%、デフォルト値の指定し直し、副作用のあるショートハンドのような記述を見つけたときは、それが表示に必要なのか、消してよい不要な記述なのかを判断できます。

この章の節

この章は次の3つの節で構成しています。

  • 2-1 CSS設計のマインドセット：CSS設計が扱う範囲と、共通化したカードに項目を足す例で見る保守性、拡張性、再利用性の違い
  • 2-2 CSSで考えるための6つの視点：ボックス、カスケード、最小限の記述、境界、文脈、内容の変化という6つの視点と、それぞれを具体化した本書の章
  • 2-3 保守しやすさを最優先にする：重複を恐れず共通化は3回目から考えることと、width: 100%、デフォルト値の指定し直し、副作用のあるショートハンドといった不要な記述をしないこと

具体的なルールは、2-3のほか、第8章「リセットとベーススタイル（巻2）」、第9章「記法の規約（巻2）」、第10章「コンポーネントとカスタムプロパティ（巻2）」の各節にあります※4。

2-1 CSS設計のマインドセット

CSS設計は、クラスの命名規則やセレクタの選び方だけを指すものではありません。UIをどう部品に分けるか、コードをどう整理するか、どの技術を選ぶか、要素の見た目と振る舞いをどう書くかまでを含む、UIを作る過程全体の活動です。その目的は、作ったものを長く健全に保ち、変更へ対応しやすくすることです。

スコープを持つCSSやユーティリティファーストの手法によって、命名や詳細度の悩みは小さくなりました。しかし、命名の悩みがなくなっても、CSS設計が不要になるわけではありません。このページでは、CSS設計が扱う範囲と、設計によって高めたい3つの性質を、1つの変更の例で説明します。

命名規則はCSS設計の一部

「CSS設計」で検索すると、BEMのような命名規則や、どのセレクタを使うべきかといった話題が多く見つかります。そのためか、クラスの命名規則を決めることがCSS設計だと考えられていることがあります。命名とセレクタはCSS設計の大切な要素ですが、CSS設計のすべてではありません。

CSS設計が命名とセレクタの問題だけなら、@scope やCSS Modulesのようなスコープの仕組みや、Tailwind CSSのようなユーティリティファーストの手法で、その多くは解決します。CSS Modulesはクラス名をファイルごとの一意な名前へ変換するので、名前の衝突を防げます。@scope は名前を変換しませんが、子要素のセレクタが当たる範囲をスコープのルートの内側に限定します。どちらの仕組みでも、子要素の名前をほかの部品と重ならないように工夫する必要は減り、詳細度の争いも起きにくくなります。「クラスの命名から解放されたので、CSS設計からも解放された」と考えたくなるのは、このためです。

しかし、命名の悩みが減っても、残る判断はたくさんあります。どこまでを1つの部品にするか、部品の外側の余白を誰が決めるか、共有する値をどこにまとめるか、要素の大きさを固定値で決めるか制約で決めるか。これらは、どの命名規則を選んでも、どの道具を使っても、実装者が決めなければならないことです。

CSS設計が扱う範囲

本書では、Webページの見た目と構造を、保守しやすく、変更へ対応できる形で作るための考え方と原則の集まりを、CSS設計と呼びます。そこには、コードの書き方の取り決めだけでなく、次のような判断が含まれます。

1つ目は、UIをどう部品に分けるかです。何をコンポーネントにし、コンポーネントの責任の範囲をどこまでにするかを決めます※1。2つ目は、コードをどう整理するかです。ファイルをどう分け、カスケードレイヤーでどの順に優先するかを決めます。

3つ目は、どの技術を選ぶかです。素のCSSで書くか、Sassやユーティリティファーストの手法を使うかを、プロジェクトの文脈から選びます。4つ目は、要素の見た目と振る舞いをどう書くかです。同じ見た目でも、固定値で書くか、ブラウザに計算を任せる制約で書くかで、内容や画面の幅が変わったときの振る舞いが変わります。本書の多くのページは、この4つ目の判断を扱っています。

保守性、拡張性、再利用性

CSS設計で高めたい性質は、保守性、拡張性、再利用性の3つです。保守性は、コードを読んで理解でき、1か所を直しても別の場所が壊れにくいことです。拡張性は、新しい内容や機能を、既存のコードを大きく書き換えずに加えられることです。再利用性は、一度作ったスタイルやコンポーネントを、別の場所でも手間なく使えることです。

3つとも、変更にかかる手間と費用を減らすための性質で、違いは、どの変更を楽にするかにあります。保守性は直す変更を、拡張性は足す変更を、再利用性は同じものをもう一度作る手間を減らします。Webサイトは公開後も更新や改修が続くので、この3つが低いと、変更のたびに時間と費用がかかり、必要な変更を見送ることにもなりかねません。

共通化したカードに項目を足す例

3つの違いは、1つの変更を3つの性質から見ると分かります。サイトにお知らせの一覧とイベントの一覧があり、どちらも画像、日付、見出しを並べたカードで表示しているとします。見た目が同じなので、2つの一覧のカードを1つのコンポーネントにまとめました。公開後、イベントのカードにだけ、開催場所と申し込みの締め切りを表示することになりました。

保守性から見ると、問題は変更の影響の範囲です。イベントのために足した宣言は、同じコンポーネントを使うお知らせの一覧にも当たるので、変更のたびに両方の一覧を確かめる必要があります。イベントのときだけ表示を変える分岐が増えるほど、どの宣言がどちらの一覧のためのものかを読み取りにくくなります。

拡張性から見ると、問題は項目を足すときに書き換える量です。カードの中身を、画像、日付、見出しの3つがあるものとして、要素ごとに位置や余白を決めていれば、項目を2つ足すたびにその指定を書き直すことになります。要素の間の余白を、子に margin を書かず、親の gap でまとめて指定してあれば、項目の数が変わっても並びは保たれます※2。足す変更は、HTMLと新しい項目のスタイルだけで済みます。

再利用性から見ると、問題は何を共通にしたかです。2つの一覧が共有していたのは見た目だけで、載せる情報も、変更される理由も違いました。見た目が似ているだけで1つにまとめたことが、イベントのための変更をお知らせの一覧にまで広げています。

再利用性を高めることと、何でも共通化することは違います※3。この例のように見た目だけが似ている部品を別々のコンポーネントのままデザイントークンでそろえる方法は「10-1 何をコンポーネントにするか（巻2）」で説明しています。

CSSを書くときは、目の前のデザインを再現することに意識が向きがちです。そのときに、この書き方は後から直しやすいか、内容が増えたときに対応できるか、別の場所でも使えるかを一度考えてみると、長く使えるコードとそうでないコードの差になって表れます。

2-2 CSSで考えるための6つの視点

CSSは「壊れやすい」「思いどおりにならない」と言われがちです。しかし、その原因の多くは、CSSの欠陥ではなく、書いた宣言のほかにもブラウザの受け取る入力が多いという、CSSの性質にあります。仕様やプロパティを覚えることより、CSSの設計思想を理解し、その柔軟さを受け入れる考え方を身につけるほうが、思いどおりにならない場面は減ります。

この節では、CSSで考えるための6つの視点を示し、それぞれを本書のどの章と節が具体的なルールにしているかを対応づけます。本書を、この6つの視点から引く地図として使えます。

CSSが壊れやすいと言われる理由

C#やPythonと同じく、CSSも、入力から規則に従って結果を求める言語です。同じ入力からは、同じ結果が得られます。違うのは、入力に含まれるものの多さです。C#やPythonのプログラムでは、入力は引数やファイルのように開発者が範囲を把握できるものであることが多い一方、CSSでは、自分の書いた宣言のほかに、画面の幅、入る内容、親のレイアウト、ユーザーの設定もブラウザへの入力になります。書いた宣言だけを入力と考えていると、ほかの入力が変わって結果が変わったことを、不具合と受け取ってしまいます。

CSSは、処理の手順ではなく、どう表示されてほしいかを宣言する言語です。宣言とほかの入力から結果を求める規則が、通常フロー、Flexbox、Gridといったレイアウトのアルゴリズムです。規則を知っていれば、画面によって結果が変わった理由も説明できます※1。

壊れやすいCSSの多くは、宣言以外の入力が変わらないと決めつけた書き方から生まれます※2。入力によって結果が変わることを欠点として抑え込まず、前提として受け入れて書くことが、CSSで考えるということです。

ボックスで考える

Webページの見た目は、突き詰めれば、画面に箱を並べることでできています。見出し、段落、画像のどれも、ブラウザにとっては大きさと位置を持つ箱です。箱がどう伸び縮みし、どの向きに流れて並ぶかを理解することが、CSSで考えるための出発点になります。

本書では、箱の4つの領域（内容、padding、border、margin）と大きさの決まり方を「7-3 ボックスモデルの基礎」で説明しています※3。箱の並べ方は1種類ではなく、FlexboxやGridでは別の規則で大きさが決まります※4。

カスケードを使う

カスケードは、意図しない上書きの原因として嫌われがちです。しかし、サイト全体に効かせる基本のスタイルと、部品ごとのスタイルを適切に組み合わせれば、カスケードは記述を減らす仕組みとして働きます。全体の土台を幹、部品のスタイルを葉にたとえると、幹で決めた文字の色や行の高さは継承によって葉にも適用されるので、葉で同じ値を書き直さずに済みます。

本書は、幹と葉を名前の規則ではなく、CSSの仕組みで分けます。幹にあたるリセットCSSとベーススタイルは、カスケードレイヤーの前のほう（reset と base）に置きます。レイヤーの順番は詳細度より先に比べられるので、ベーススタイルのセレクタは素のまま書いても、コンポーネントのクラス1つで上書きできます（「8-1 壊さないリセット（巻2）」、「8-2 ベーススタイルに書くもの（巻2）」）。葉にあたるコンポーネントは @scope で範囲を閉じ込め、優先順位は詳細度の高さではなくレイヤーの順番で決めます（第4章「カスケードを制御する」）。

BEMのような命名規則が担っていた範囲の管理も、本書は @scope とカスケードレイヤーに任せます※5。

必要最小限のCSSを書く

デフォルト値と継承で足りる部分は書かず、不要な固定や上書きを避けます。ブラウザが決める幅を指定し直したり、高さを固定値で決めたりすると、その要素は内容や置き場所に合わせて変わらなくなるからです。一方で、min-inline-size で下限を示す宣言や、flex-wrap: wrap で折り返しを許す宣言のように、書き足すことで要素を柔軟にする宣言もあります。background のように、指定しなかったサブプロパティまで初期値に戻すショートハンドを、一部だけ変えたい場面で使わないことも、この視点に含まれます。

本書では、この視点を2つの節で具体化しています※6。「2-3 保守しやすさを最優先にする」では、何にでも書かれる width: 100%、デフォルト値の指定し直し、副作用のあるショートハンドを、不要な記述として扱っています。

責任の境界を決める

レイアウトとコンポーネントの関係は、弁当箱にたとえられます。弁当箱の仕切りは中に詰める料理と関係なく決まり、料理は仕切られた区画に合わせて詰められます。仕切り（レイアウト）と料理（コンポーネント）の責任を分けておけば、どちらかを変えても、もう一方に手を入れずに済みます。

本書では、margin や grid-area のような周りとの関係で決まるレイアウト（外部関連型のレイアウト）を、コンポーネントのルートに書かず、置く側に任せます※7。並べる、積む、折り返すといった配置は、コンポーネントから切り離したコンポジションが受け持ちます※8※9。

文脈を確かめる

同じ宣言でも、親がどんな環境を作っているかで結果が変わります。親がFlexboxなら子の width は縮む出発点になり、親がスタッキングコンテキストを作っていれば、子の z-index をどれだけ大きくしても、親より手前に重なっている要素の、さらに手前には出られません。要素が思いどおりにならないときは、その要素より先に親の環境を確かめるのが、解決の近道です。

本書では、要素がどの方式の中にあり、どの要素が包含ブロックとスタッキングコンテキストを作っているかを確かめる手順を、「7-1 レイアウトの基礎」で説明しています※10。重なり順の不具合をスタッキングコンテキストから調べる方法は、「11-6 重なりと全幅（巻2）」で扱います。

内容が変わる前提で書く

本書は、CMSを導入しない静的なWebサイトであっても、CMSで内容を更新するつもりで実装します。文章の長さ、項目の数、画像の有無と縦横の比率は、公開後に変わるものとして組み、カンプに入っている内容を前提にしません。

静的なサイトでも、公開後に内容は変わります。お知らせが増え、見出しの言い回しが直され、写真が差し替えられることは、HTMLを直接書き換える運用でも起こります。内容を変えるたびにCSSも直す必要があるなら、そのCSSは公開時の内容にしか対応していません。CMSがあるかどうかは、内容を誰がどう書き換えるかの違いで、内容が変わること自体は変わりません。

デザインカンプには、ちょうど良い長さの見出しと、大きさのそろった画像が入っています。実際の運用では、文章が長くなり、画像のない記事や縦長の写真が入り、要素の数も増減します。そこで、特定の内容に合わせた固定値（マジックナンバー）を避け、どうなってほしいかという意図をコードに書いて、具体的な値の計算はブラウザに任せます。

たとえば、カードを3列に並べる一覧なら、カンプの幅から逆算した304pxをカードの幅に書くのではなく、列の最小幅だけを決めて、列の数と幅は一覧の実際の幅からブラウザに計算させます。この書き方は、「12-6 grid（巻2）」でコンポジションにしています。

想定外の内容への備え方は「11-3 サイズと内容の変化に耐える（巻2）」で説明しています※11。

z-index、CSS設計、!important の扱い

6つの視点から考えると、迷いやすい3つの話題にも本書の立場が決まります。z-index は、値を大きくする前に、どのスタッキングコンテキストの中で比べられているかを確かめます（文脈を確かめる視点）※12。

CSS設計は、命名の悩みが道具で減っても部品の分け方の判断が残るので、必要だというのが本書の立場です※13。!important は、どんな上書きにも負けてはいけない場面に限ります※14。

2-3 保守しやすさを最優先にする

CSSの書き方に迷ったら、コードの短さや共通化のしやすさよりも、ほかの人が読んで安全に直せるかどうかで選びます。そのために本書では、似た記述の重複を恐れず、共通化は同じものが3回現れてから考えます。反対に、必要な理由を説明できない宣言は1つも書きません。

保守しやすさを優先し、共通化を急がない理由を先に述べます。そのあとで、保守の妨げになりやすい不要な記述として、何にでも指定される width: 100%、デフォルト値の指定し直し、副作用のあるショートハンドを取り上げます。

公開後の運用期間

Webサイトは、公開したときが始まりです。お知らせの追加、ページの増設、デザインの部分的な変更など、公開後の更新と改修の期間のほうがずっと長く続きます。しかも、更新するのは最初に書いた本人とは限りません。スキルの違う人が、時間がたってから触ることを前提に考える必要があります。

CSSは、どれだけ丁寧に組んでも、運用するたびに少しずつ劣化していきます。「ここだけ変えたい」という修正が上書きを呼び、その上書きがさらに次の上書きを呼びます。劣化を完全に止めることはできないので、最初から「崩れにくく、崩れても直しやすい」書き方を選びます。

良いCSSの条件としては「予測しやすい」「再利用しやすい」「保守しやすい」「拡張しやすい」の4つがよく挙げられます。本書はこのうち「保守しやすい」を最も重視します。短く洗練されたコードは書いた本人には気持ちの良いものですが、その短さと引き換えに、読みやすさや変更のしやすさ、不要になったときの捨てやすさを失いがちだからです。

例外は、公開後に更新する予定のない短期のキャンペーンサイトなどです。こうしたサイトなら、記述を切り詰めたコードでもかまいません。ただし、更新しない予定だったサイトに後から改修が入ることもあるので、迷ったら保守しやすいほうを選びます。

AIがコードを書いても質が要る理由

AIがCSSを書くようになり、コードを書く手間も、書き直す手間も小さくなりました。それでも、コードの質を軽く見てよいことにはなりません。AIは、プロジェクトの既存のコードを読み、その書き方に倣って次のコードを書きます。指示の文章よりも、すでにあるコードのほうが、次に書かれるコードの形を決めることが多いからです。

そのため、既存のコードの欠陥は、次のコードに複製されます。詳細度を上げて上書きした箇所が1つあれば、次の上書きも同じ形で書かれます。反対に、部品の境界と値の受け渡しが一貫していれば、AIが書く新しい部品も同じ形にそろいます。良いコードは良い模倣を生み、雑なコードは欠陥を増やします。

起こり得ない状態に備えた指定も、同じ理由で残しません。Gridで並べる子に付けた float: none や、ベーススタイルですでに0になっている余白の打ち消しは、表示を変えません。それでも、コードに残っていれば、「この指定の要る場面がある」と次の書き手に伝えてしまいます。人とAIのどちらが次に書く場合も、それを根拠に同じ指定を書き足します（ルール no-redundant-defaults）。

ここでいう不要な指定と、「11-3 サイズと内容の変化に耐える（巻2）」で勧める守りの指定は、別のものです。長い見出し、画像のない記事、増えるタグのように、運用で実際に起こる内容の変化に備える指定は要ります。区別の基準は、その状態が起こり得るかどうかです。

AIに指示すれば、既存のコード全体へ規約を一度に適用することも難しくなくなりました。ただし、そろえる先の規約がよくなければ、よくない書き方が一度に広がります。本書は規約をルールとして書き出し、IDで引けるようにしています。人とAIが同じ規約を読んで書き、同じ規約で確かめるためです（第20章「AIにコーディングさせる（巻3）」）。

共通化のタイミング

本書では、似た記述が重複することを許容します。2つのコンポーネントに同じような指定があっても、すぐには共通化しません。共通化を検討するのは、同じものが3回現れてからです。この考え方は「rule of three」と呼ばれます。

共通化を急がないのは、共通化したスタイルは影響範囲が広く、しかもその範囲が見えにくいからです。2か所で使っている共通のスタイルを、片方の都合で変えると、もう片方も一緒に変わります。それを避けるために修飾クラスや上書きを足していくと、共通化したはずのスタイルは分岐だらけになります。

とくに注意したいのが、見た目が似ているだけのものを共通化することです。商品のカードと記事のカードは、どちらも角丸の箱に画像と見出しが入っているかもしれません。しかし、載せる情報も、今後増えていく要素も、変更される理由も違います。

このように1つにまとめると、商品のカードだけを変えたいときにも、記事のカードに影響しないかを毎回確かめる必要があります。どちらかのカードが不要になっても、共通の部分と絡み合っているので、安心して消せません。

padding と border-radius は重複していますが、これは意図したものです。それぞれのカードは、相手を気にせず変更したり削除したりできます。「カード類の背景色をまとめて変えたい」といった、そろって変わるべき値だけをトークンで共有します※1。

共通化の粒度は、大きめから始めます。たとえば「左に画像、右に文章」という配置が何度か出てきたからといって、その配置だけを部品にすると、似た配置を見つけるたびに部品が増えていきます。配置の共通点は部品の境界とは限らず、部品が散らばるほど、どれをどこで使うかを把握できなくなって破綻します。共通化するなら、商品の詳細や記事の一覧のように、役割が名前で言える単位にします。

同じものが3回現れたら、それらが見た目だけでなく役割まで同じかを確かめます。役割まで同じなら、コンポーネントやコンポジションとして切り出します※2。最適化は、ひととおり書き終えてから行うくらいがちょうど良いと私は考えています。

不要な記述をしない

重複は許容しますが、不要な記述は許容しません。余計な宣言があるほど、ベーススタイル、コンポジション、コンポーネントの中の別のルールとぶつかったときに、どの値が勝つかが状況しだいになります。ぶつかった値を打ち消すために詳細度を上げる上書きが増え、修正のたびに手間が大きくなっていきます。

「なんとなく指定してみた」宣言は、設計の判断として共有されず、読む人には意図が分かりません。本書では、宣言ひとつひとつについて「なぜそれが必要か」を説明できる状態にします。以下では、とくによく見かける3種類の不要な記述を取り上げます。

何にでも width: 100% を指定しない

最もよく見かけるのが、とりあえず width: 100% を指定するものです。div や p のように、ブラウザのデフォルトスタイルで display: block になる要素は、width が初期値の auto のままで親の幅に合わせて広がります。position: absolute と inset: 0 を指定した要素も、その時点で利用できる幅いっぱいに広がります。

つまり、div が親の幅いっぱいになるのは、width: 100% と同じ指定が働いているからではありません。ブロックレベルの要素の auto は、包含ブロックの幅から自分の margin、border、padding を差し引いた残りを内容の幅にします。一方の 100% は、包含ブロックの幅をそのまま内容（border-box なら枠線まで）の幅にするので、margin があればその分だけはみ出します。見た目が同じでも、2つは別の計算です。

height: 100% は、親の高さが明示的に指定されているときにしか期待どおりに動きません。親が min-height のように最小値だけを決めている場合には成り立たず、flexやgridのアイテムであれば、指定しなくても stretch で高さいっぱいに広がります。

これらは無意味なだけでなく、ブラウザ間の挙動の違いによる不具合の原因にもなります。過去には、Safariで <summary> の子要素に width: 100% を指定すると不自然な改行が起きたり、Firefoxで height: 100% を指定したサブグリッドの要素が不自然に詰まったりする事例がありました。box-sizing を初期値に戻したときや、左右のマージンが加わったときには、はみ出しの原因にもなります。

幅を広げる指定が要るのは、display: block にしても自然には広がらない <img> のような置換要素や、<textarea> や <button> のようなフォーム部品です。行方向のフレックスアイテムと、左右の位置を片方しか決めていない絶対配置の要素も、中身の幅に縮みます。min(320px, 100%) のように、はみ出しを防ぐための 100% は問題ありません。inline-block の要素を幅いっぱいに広げたいなら、width: 100% を足す前に、外側の表示形式を block に変えられないかを検討します。そうすれば、vertical-align によって下にできる隙間もなくなります。

幅を広げる指定が本当に要る場面では、100% ではなく stretch を使います。子要素を親の高さにそろえたいだけなら、height: 100% を書かずに、親をGridにして伸ばします。どちらも、margin が加わったときや親が最小値しか決めていないときに崩れない書き方です※3。Tailwind CSSの w-full や h-full も同じで、生成AIの出力ではとくに乱用されがちです。生成されたコードにこれらがあったら、1つずつ必要かどうかを確かめます。

デフォルト値を指定し直さない

ここでいう「デフォルト値」は、CSSの初期値、ブラウザのデフォルトスタイル、リセットCSSの値、ベーススタイルの値をまとめたものです。margin: 0 や、div への display: block を場当たり的に書いていたら、設計の一貫性が崩れているサインになりやすいです。最初の要素だけ上のマージンを打ち消したいなら、全体に付けてから打ち消すのではなく、:not(:first-child) や * + * で「2つ目以降にだけ付ける」設計にします。

ブレイクポイントなどで、いったん変えた値をデフォルト値に戻したいこともあります。その場合も、値を書き写さずに、revert、revert-layer、unset、initial のキーワードで戻り先を示します。

キーワードで書けば「戻した」という意図が読み取れ、どの段階の値に戻るのかも明確になります※4。

その文脈でブラウザが無視するプロパティも、デフォルト値の指定し直しと同じく消します。たとえば、vertical-align はインラインレベルの要素とテーブルのセルにしか効かないので、ブロックレベルの要素に付けても何も起きません。フレックスアイテムやグリッドアイテムに付けた float も、同じく無視されます。こうした宣言は、ほかの人が読んだときに「何かのために必要なのだろう」と残され続けます。レイアウトの方法を変えたときに残りやすいので、表示形式を変えたら、効かなくなった宣言がないかを確かめます。

文字の色やフォント、行の高さのように :root や body で決めた値も、コンポーネントで指定し直さずに継承させます。指定し直すのは、そのコンポーネントで本当に変えたいときだけです。

副作用のあるショートハンドを乱用しない

ショートハンドは便利ですが、指定しなかったサブプロパティまで初期値に戻します。そのため、ほかの場所でロングハンドを使って積み上げた設定を、後から意図せずリセットしてしまうことがあります。

background: oklch(100% 0 0deg) は、background-color だけでなく、background-image や background-size などもまとめて初期値に戻します。別の場所で設定した背景画像があれば、それも消えます。margin: 0 auto は、左右の中央寄せのために、本来触る必要のない上下のマージンまで 0 にします。子要素の間にマージンで余白を入れるレイアウトの中に置くと、その余白を打ち消してしまいます。

次のデモでは、子要素の間に余白を入れた記事の中で、図を中央に寄せています。margin: 0 auto のほうでは、図の上の余白が消えています。もう一方の margin-inline: auto のほうでは、図の上下の余白が段落の間と同じ大きさで残っています。

デモ2-3-1　margin: 0 auto は、上下の余白の指定まで打ち消す（補足サイト）

flex のように、指定した値から別の値に置き換わるショートハンドにも注意します。flex: 1 は flex-grow: 1 と同じではなく、flex-basis を 0% にします。「flex: 1 では何が1なのか分からない」という理由で flex-grow: 1 に書き換えると、動きが変わります。font はさらに影響が大きく、line-height や font-kerning まで初期値に戻すので、リセットの目的以外では使いません。

また、flex: 1 でも、アイテムごとに padding や border が違うと列の幅はそろわないので、厳密にそろえるならGridで列を決めます（「7-7 Flexboxの基礎」の「flex: 1 でも列の幅がそろわない場合」）。

すべてのショートハンドが悪いわけではありません。inset のように、すべての辺にまとめて値を与える用途では問題になりにくく、border も、border-image を初期値に戻す点を除けば、線の太さ、種類、色をまとめて決めるだけです。ほかの設定が入り込む余地のない擬似要素なら background を使っても困りません。避けるのは、一部だけを変えたいのに、影響範囲の広いショートハンドを使うことです。
