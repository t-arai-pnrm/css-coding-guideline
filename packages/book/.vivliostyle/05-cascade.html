第4章 カスケードを制御する

この章では、同じ要素の同じプロパティに複数の値が指定されたとき、どの値が使われるかを扱います。スタイルの優先順位は、詳細度の高さで競わせず、「どのレイヤーに書くか」と「どの範囲に適用するか」で先に決めます。詳細度そのものは、できるだけ低く一定に保ちます。

私は2020年に、!important を使わずにスタイルを上書きする技として、同じクラスを連結して詳細度を上げる書き方を紹介していました。当時は、詳細度を調整する手段がセレクタしかなかったからです。いまはカスケードレイヤー、:where()、@scope がすべての主要なブラウザで使えるので、上書きの技そのものが要らない設計にできます。この章では、上書きで困ってから対処するのではなく、困らない順番と範囲を最初に決めておく設計を扱います。

ただし、新しい仕組みにも向き不向きがあります。私自身、2024年のブログではITCSSにならった7つのレイヤーを使い、2025年に公開したリセットCSSのkiso.cssでは「レイヤーに頼らなくても上書きしやすい」ことを優先しました。現在、Astroで作るサイトのテンプレートでは9つのレイヤーを使っていますが、CMSの案件ではレイヤーをやめています。こうした経験から、レイヤーを使う基準と使わない基準の両方を示します。

この章で判断できるようになること

この章を読むと、宣言が適用されないときに、レイヤー、詳細度、スコープの近接度、出現順のどれで負けているかを切り分けられるようになります。上書きが要るときは、詳細度を上げる代わりに、書くレイヤーを変えるか、@scope で範囲を絞るかを選べます。CMSのようにレイヤーに入っていない外部のCSSと共存する環境では、@layer を使わないと判断でき、!important を使ってよい場面かどうかも見分けられます。

判断の問い

この章の内容で答えられる問いを1つ置きます。答えを開く前に、どの宣言が勝つかを予想してください。

次のCSSで、<article class="card"><h2 class="title | -text-muted">…</h2></article> の見出しは何色になりますか。

答えと解説

最後の h2 の色（--foreground--danger）になります。h2 のルールはどのレイヤーにも入っていないので、すべてのレイヤーより後ろの「暗黙の最後のレイヤー」として扱われます。!important のない宣言どうしでは、レイヤーの順番が詳細度より先に比べられます。そのため、詳細度0.0.1の h2 が、0.2.0の .card .title にも、utilities の .-text-muted にも勝ちます※2。

h2 のルールを @layer base { … } に入れると、答えは --foreground--muted に変わります。3つのレイヤーのうち最も後ろにある utilities が勝つからです。ユーティリティクラスが効かないときに、まずレイヤーの書き忘れを疑うのは、このためです。

4-1 カスケード・詳細度・継承

同じ要素の同じプロパティに複数の値が指定されたとき、どの値を使うかは「カスケード」という手順で決まります。カスケードは、レイヤー、詳細度、スコープの近さ、書いた順番などを決まった順に比べ、最初に差がついたところで勝ち負けを決めます。

本書では、この仕組みのうちレイヤーと書いた順番で優先順位を設計し、詳細度はできるだけ低く一定に保ちます。!important は、詳細度の競争に勝つためには使いません。

この節のコード例は、カスケードの仕組みだけを見せるために、.button のような素のクラスで書いています※1。

詳細度で上書きを重ねると何が起きるか

ベーススタイルに、リンクの色を次のように書いたとします。一見すると問題のない指定ですが、この書き方が後の上書きを難しくします。

a:link の詳細度は、タイプセレクタ1つと擬似クラス1つで「0.1.1」になります。ボタンのクラス .button は「0.1.0」なので、リンクで作ったボタンの文字色を変えられません。そこで祖先のクラスを足して「0.2.0」にし、さらに負ける場面が出ると !important を付ける、という流れが生まれます。

こうした上書きは、1回ごとには小さな対応です。しかし、次に誰かが上書きするときには、さらに高い詳細度か !important が必要になります。上書きする側は、上書きされる側より強くなければならないので、詳細度の競争は一方向にしか進まず、最後は !important 同士の競争になります。私は、この詳細度の問題こそがCSSを破綻させるいちばんの原因だと考えています。

問題の出発点は、優先順位を詳細度の高さで決めようとしたことです。カスケードには、詳細度より先に比べられる仕組みがあります。それを使えば、詳細度を上げなくても、意図した順番でスタイルを勝たせられます。

カスケードが値を決める順番

カスケードは、次の順に宣言を比べます。上の段階で差がつけば、下の段階は比べません。

  1. オリジンと重要度：ブラウザのデフォルトスタイル、ユーザーのスタイル、作者のスタイルの区別と、!important の有無
  2. コンテキスト：Shadow DOMの内側と外側の区別
  3. style 属性：要素に直接書いたスタイル
  4. レイヤー：@layer の順番
  5. 詳細度：セレクタの強さ
  6. スコープの近さ：@scope のルートと要素との距離
  7. 出現順：後に書いた宣言が勝つ

レイヤーは、詳細度より先に比べられます。同じオリジンの、!important を付けていない宣言どうしでは、レイヤーが違えば、詳細度がどれほど高くても、後ろのレイヤーの宣言が勝ちます。!important を付けた宣言どうしでは、この順番が逆になります。詳細度は、同じレイヤーの中で初めて比べられる値です。

レイヤーに入れていないスタイルは、すべてのレイヤーより後ろにある「暗黙の最後のレイヤー」として扱われます。そのため、!important を付けていない宣言どうしでは、レイヤーの外のスタイルが常に勝ちます※2。

詳細度は、IDの数、クラス・属性・擬似クラスの数、タイプセレクタ・擬似要素の数という3つの数で表し、左の数から比べます。本書では、これを「0.1.1」のようにドットでつないで書きます。

スコープの近さは、@scope とともに加わった比べ方です。詳細度が同じ宣言どうしでは、スコープのルートが対象の要素に近いほうが勝ちます。レイヤー、詳細度、スコープの近さのすべてで差がつかなかったときに、最後に書いた宣言が勝ちます※3。

style 属性は、レイヤーと詳細度より先に比べられるので、オリジンと重要度が同じ宣言どうしなら、セレクタで書いたどのルールにも勝ちます。!important を付けていない style 属性の宣言は、作者の !important を付けた宣言には負けます。本書では、style 属性をコンポーネントの公開カスタムプロパティに値を渡す用途に限って使います※4。

優先順位はレイヤーと書く順番で決める

本書では、優先順位を次の方針で設計します。まず、スタイルの役割ごとにレイヤーを分け、「リセットよりベース、ベースよりコンポーネント、コンポーネントよりユーティリティが強い」という順番をレイヤーで決めます。同じレイヤーの中では詳細度をそろえ、書いた順番で勝ち負けが決まるようにします。

詳細度の目安は2つです。ベーススタイルは、base レイヤーに素のセレクタで書きます。後のレイヤーの指定は詳細度に関係なく勝つので、a:any-link（0.1.1）のままでも、コンポーネントのクラス1つで上書きできます。コンポーネントの中は、クラス1つ分（0.1.0）を基本にします。本書では、コンポーネントのスタイルを @scope の中に書くので、クラスを1つ書けばちょうど0.1.0になります※5※6。

リセットCSSのkiso.cssは、すべてのセレクタを :where() で包んで詳細度を0にしています。レイヤーなしで読み込まれても上書きしやすくするためです。CMSと共存する場合のようにレイヤーを使えない環境では、ベーススタイルのセレクタも同じように :where() で包みます※7。

このコードでは、ベースのリンクの色が0.1.1、ボタンの色が0.1.0です。詳細度ではリンクの色のほうが高くても、components レイヤーが base レイヤーより後ろにあるので、ボタンの色が勝ちます。レイヤーで順番を決めておけば、上書きのために詳細度を上げる工夫は要りません。

継承されるプロパティとされないプロパティ

カスケードは、「要素に当てはまる宣言のうち、どれを使うか」を決める仕組みです。当てはまる宣言がひとつもないプロパティは、継承されるプロパティなら親の値を受け継ぎ、継承されないプロパティなら初期値になります。

継承されるのは、主に文字に関わるプロパティです。color、font-family、font-size、line-height、letter-spacing などがこれに当たります。一方で、margin、padding、border、background-color、display のように、ボックスやレイアウトに関わるプロパティは継承されません。カスタムプロパティは、@property で inherits: false を指定しない限り継承されます。

継承で受け継いだ値には、詳細度がありません。要素に直接当てはまる宣言がひとつでもあれば、詳細度0の :where() の指定であっても、継承した値より優先されます。親に色を指定したのに子の色が変わらないときは、子に当てはまる宣言がどこかにないかを確認します。

継承があるので、文字の色やサイズは :root やコンポーネントのルートでまとめて指定し、子要素では継承を使います。子要素ごとに同じ値を書き直すと、ルートの値を変えたときに直す場所が増えるからです。

デモ4-1-2　継承するプロパティはルートでまとめて指定する（補足サイト）

この例では、カードの中の文章はすべてルートの色とサイズを受け継ぎ、見出しだけが違う値を持ちます。デモでは、段落と日付がルートの灰色の14pxで、見出しだけが濃い色の18pxで表示されます。本文の段落や日付にクラスを付けて、色を指定し直す必要はありません。

戻したい先をキーワードで選ぶ

指定した値を元に戻したいときは、具体的な値を書き直すより、どのプロパティにも使えるキーワードを使います。キーワードによって戻る先が違うので、意図に合うものを選びます。

  • initial：プロパティの初期値に戻す
  • inherit：親の値を受け継ぐ
  • unset：継承されるプロパティなら inherit、継承されないプロパティなら initial として働く
  • revert：サイトのCSSの指定を取り除いた値に戻す（ユーザーのスタイルがなければブラウザのデフォルトスタイル、ブラウザにも指定がなければ継承または初期値）
  • revert-layer：ひとつ前までのレイヤーで決まる値に戻す

注意したいのは initial です。display の初期値は、要素の種類に関係なく inline です。div の display を initial にすると、インライン要素になってしまいます。ブラウザのデフォルトスタイル（div なら block）に戻したいなら、revert を使います。

リセットCSSで消したものを一部の場所だけ元に戻すときにも、revert を使います。kiso.cssはリストのマーカーを list-style-type: "" で消しているので、記事の本文のようにマーカーが必要な場所では、次のように戻します。

ここで revert-layer を使うと、kiso.cssを入れた reset レイヤーの値（マーカーなし）に戻るので、マーカーは表示されません（2026年9月、Chrome 152で確認）。どちらのキーワードも「元に戻す」ものですが、戻る先が違います。次のデモでは、2つのリストの違いは list-style-type のキーワードだけです。revert のリストには項目の先頭にマーカーが表示され、revert-layer のリストにはマーカーが表示されません。

デモ4-1-3　revert はブラウザのデフォルトに、revert-layer は reset レイヤーの値に戻る（補足サイト）

これらのキーワードは、all プロパティと組み合わせると、direction、unicode-bidi、カスタムプロパティを除くすべてのプロパティをまとめて戻せます。このとき all: unset は使いません。unset は、継承されないプロパティを初期値に戻すので、display は inline になり、ブラウザのデフォルトスタイルのうち必要なもの（<ul> の余白や <button> のフォーカスリングなど）まで消えます。どのプロパティの初期値が何かを覚えていないと、何が起きるのかを予測できません。まとめて戻すなら、レイヤーを使うプロジェクトでは all: revert-layer、使わないプロジェクトでは all: revert を指定します。戻る先がひとつ前のレイヤーや（ユーザーのスタイルがなければ）ブラウザのデフォルトスタイルなので、要素が本来の表示を保ったまま、上書きだけが消えます。

!important を使ってよい場面

!important は、カスケードの最初の段階である「オリジンと重要度」の順位を変える指定です。!important が付いた宣言は、付いていない宣言に、レイヤーや詳細度に関係なく勝ちます。スタイルの宣言どうしで比べる限り、これを打ち消せるのは、同じように !important を付けた宣言だけです。例外は実行中のトランジションで、その値は !important を付けた宣言よりも優先されます（@keyframes のアニメーションは優先されません）。

さらに、!important を付けた宣言どうしでは、レイヤーの順番が逆になります。前のレイヤーの !important ほど強く、レイヤーの外の !important がいちばん弱くなります。前のレイヤーで !important を付けた指定は、後ろのレイヤーから上書きできません。

本書では、詳細度や読み込み順の競争に勝つ目的で !important を使いません。どのような上書きにも負けてはいけない指定に限って使います。代表的なのは、kiso.cssの hidden 属性の指定です。

hidden 属性を付けた要素は、どのコンポーネントが display を指定していても隠れなければなりません。kiso.cssを reset レイヤーに入れると、この !important はいちばん前のレイヤーのものになります。後ろのレイヤーで display: block !important と書いても、要素は隠れたままです（2026年9月、Chrome 152で確認）。kiso.cssは、閉じている <dialog> と開いていないポップオーバーにも、同じ理由で !important を使っています。

このほかに !important を使うのは、強制カラーモードでSVGの色をシステムカラーに固定する場合と、CMSが要素に直接出力する style 属性を打ち消す場合です。どちらも、セレクタでは勝てない相手を上書きするための例外です※8。後者の場合は、打ち消す対象と理由をコメントに残し、後から消してよいかを判断できるようにします。

以前の私は、ユーティリティクラスだけは !important を使ってよいと考えていました。いまは、ユーティリティクラスにも !important を付けません。utilities を最後のレイヤーにすれば、!important なしでコンポーネントのスタイルに勝つからです。

AIにスタイルの修正を頼むと、上書きが効かない原因を調べずに !important を足したコードが返ってくることがあります。!important が含まれていたら、詳細度やレイヤーの順番で解決できないかを先に確認してください。

4-2 セレクタで詳細度を設計する

セレクタは、要素を選ぶと同時に、そのルールの詳細度を決めます。本書では、ベーススタイルを base レイヤーに素のセレクタで書き、コンポーネントの中はクラス1つ分（0.1.0）を基本にそろえます。ベーススタイルのセレクタを :where() で包んで詳細度を0にするのは、レイヤーを使えない場合に限ります。IDセレクタと、詳細度を上げるためだけのセレクタは使いません。

:is()、:not()、:has()、of S を付けた :nth-child() は、引数によって詳細度が変わります※1。

この節のコード例も、詳細度の仕組みを見せるために素のクラスで書いています※2。

詳細度がばらばらなセレクタ

詳細度の問題は、多くの場合、上書きしたい側ではなく、上書きされる側の書き方から始まります。次の例では、フォームのボタンと見出しのスタイルを上書きしようとして、うまくいきません。

input[type="submit"] は、タイプセレクタと属性セレクタで0.1.1になります。ボタンに .submit-button を付けても、0.1.0なので背景色を変えられません。見出しの例では、IDセレクタを含む #news h2 が1.0.1になり、クラスをいくつ重ねても勝てなくなっています。

原因は、上書きされる側のセレクタが、必要以上に高い詳細度を持っていることです。上書きする側で工夫しても、さらに高い詳細度が必要になるだけです。そのため、詳細度はセレクタを書く最初の段階で低くそろえておきます。

IDセレクタと詳細度を上げる技

IDセレクタでは、スタイルを指定しません。詳細度が1.0.0になり、クラスをいくつ重ねても上書きできないからです。オリジンと重要度とレイヤーが同じなら、IDセレクタで指定したスタイルを変えられるのは、別のIDセレクタか style 属性、あるいは !important だけです。後のレイヤーに書けば詳細度に関係なく上書きできますが、IDのスタイルを変えるたびにレイヤーを分けることになります。本書のStylelintの設定では、selector-max-id でIDセレクタを検出しています。

id 属性そのものは使います。JavaScriptから要素を参照するとき、aria-labelledby などのARIAの属性から参照するとき、ページ内リンクの移動先にするときです。スタイルはクラスで指定し、id 属性はこうした用途のために残しておきます。

私は2020年に、!important を使わずに上書きする方法として、次のようなセレクタを紹介していました。同じクラスを連結する、[class] を足す、存在しないIDを :not() に入れる、といった技です。当時はセレクタのほかに詳細度を調整する手段がなく、既存のCSSを直せない場面での最終手段として使っていました。

いまは、こうした技を使いません。セレクタから意図が読み取れないうえ、次に上書きする人はさらに詳細度を上げる必要があるからです。祖先のクラスを足す書き方（.top-page .large-text）や、タイプセレクタを足す書き方（p.large-text）も同様です。どちらもHTMLの構造に依存するので、コンポーネントを別の場所で使いにくくなります。

上書きが必要になったら、先に次の手段を検討します。優先順位の問題なら、レイヤーの順番で解決します※3。上書きされる側の詳細度が高すぎるなら、:where() で下げます。親のコンポーネントから子のコンポーネントの見た目を変えたいなら、子が公開しているカスタムプロパティに値を渡します※4。

セレクタには、要素を選ぶのに必要な部分だけを書く

上書きのためでなくても、セレクタには、外しても選ぶ要素が変わらない部分を書きません。クラスで選べる要素にタイプセレクタを連結した a.nav-link（過剰修飾）や、祖先をたどって書いた .site-header .nav .nav-link が、その例です。

.nav-link がこのリンクにしか付いていないなら、ほかの部分を外しても選ぶ要素は変わりません。足した部分は、要素を選ぶ役に立たないまま、詳細度を0.3.1に上げ、HTMLの構造への依存を増やします。リンクを <button> に替えたり、ナビゲーションをヘッダーの外へ移したりすると、選ぶ要素は同じ役割のままなのに、セレクタが当たらなくなります。

セレクタの各部分は、外すと選ぶ要素が変わるかで確かめます。状態の擬似クラスや、同じクラスの要素を置き場所で区別する祖先のように、外すと意味が変わる部分は必要な部分です。本書では、コンポーネントのスタイルを @scope の中に書くので、祖先をたどって範囲を限る必要もありません※5。

ベーススタイルの詳細度と :where()

ベーススタイルのように、あらゆる場所で上書きされる前提のスタイルは、base レイヤーに素のセレクタで書きます。base レイヤーは components レイヤーより前にあるので、a:any-link（0.1.1）のように、コンポーネントのクラス（0.1.0）より詳細度の高いセレクタでも、クラス1つで上書きできます。レイヤーの順番は詳細度より先に比べられるからです。

リンクの色は、a:link, a:visited ではなく、a のルールの中に &:any-link とネストして書きます（展開すると a:any-link です）。:any-link は href 属性を持つリンクすべてに当てはまる擬似クラスで、:link と :visited をまとめて書くのと同じ意味です。リンクで作ったボタンにクラスを付ければ、components レイヤーのそのクラスだけで文字色を上書きできます。

レイヤーを使えない環境では、この前提が崩れます。CMSのテーマのCSSと共存するために自分のCSSもレイヤーなしで書く場合は、読み込む順番と詳細度だけで優先順位が決まります。このときは、ベーススタイルのセレクタを :where() で包みます。:where() は、引数にどのようなセレクタを書いても詳細度が0になる擬似クラスで、:where(a:any-link) の詳細度は0.1.1から0になります。

私が作ったリセットCSSのkiso.cssも、すべてのセレクタを :where() で書いています。kiso.cssは配布物なので、カスケードレイヤーを使えない環境でも、どのクラスやタイプセレクタからでも上書きできるようにしています。反対に、:where() を使っていないリセットCSSをレイヤーなしで読み込むと、リセットCSSのタイプセレクタの詳細度が上回り、ベーススタイルの指定を打ち消すことがあります。リセットCSSを選ぶときも、詳細度が下げられているかを確認します※6。

:where() は、コンポーネントの中でも使えます。親のルールの中にネストして直下の子を選ぶと、詳細度は0.2.0に上がります。& > :where(.contact-heading) と書けば、子を選ぶ部分の詳細度が0になり、全体は0.1.0のままです。子の要素のルールと詳細度がそろうので、書いた順番どおりに上書きが効きます。

グリッドのエリアのように、親との関係で決まるプロパティは、親のルールの中に書くと構造が読み取りやすくなります。そのときに詳細度まで上がらないようにするのが、:where() の役割です。

イレギュラーな擬似クラスの詳細度

擬似クラスの詳細度は、ふつうはクラスと同じ0.1.0です。ただし、セレクタを引数に取る擬似クラスのうち、次の5つは決まり方が違います。表の「引数の最大」は、引数に書いたセレクタのうち、いちばん詳細度の高いものの詳細度という意味です。

擬似クラス 詳細度の決まり方 例 例の詳細度
:is() 引数の最大 :is(h2, ._title) 0.1.0
:not() 引数の最大 p:not(._note) 0.1.1
:has() 引数の最大 ._card:has(> img) 0.1.1
:nth-child(An+B of S) 0.1.0に、Sの最大を足す :nth-child(2n of ._item) 0.2.0
:where() 引数に関係なく0 :where(#news h2) 0

:is()、:not()、:has() は、自分の0.1.0を持ちません。引数の最大がそのまま擬似クラス全体の詳細度になります。引数の最大は、要素に実際に一致したセレクタではなく、引数に書いたすべてのセレクタから選びます。そのため、:is(#news, ._card) は、._card に当てはまった要素でも1.0.0です。:nth-last-child() も、of S を付けたときは :nth-child() と同じく、0.1.0にSの最大を足します。of S を付けなければ、ほかの擬似クラスと同じ0.1.0です。

:not() は否定の擬似クラスですが、詳細度は引数の分だけ加わります。p:not(._note) は0.1.1で、p._note と同じ詳細度です。引数をカンマで並べると、引数の最大の1つ分だけが加わります。p:not(._note, ._lead) は0.1.1、同じ要素を選ぶ p:not(._note):not(._lead) は0.2.1です。2020年の上書きの技 :not(#_) で詳細度を上げられたのも、この決まり方によるものでした。存在しないIDを引数に書くだけで、:not() の詳細度がIDセレクタと同じ1.0.0になるからです。

次のデモの2つのカードでは、段落を灰色にするルールの後ろで、._lead を青くしています。p:not(._note) は0.1.1なので、後ろにある ._lead のルールより強くなります。同じ条件を :where() で包むと詳細度は0.0.1まで下がり、._lead の青が使われます。

デモ4-2-1　:not() は引数の分だけ詳細度が上がり、後に書いたクラスに勝つ（補足サイト）

詳細度が引数で決まるので、意味の違うセレクタが同じ詳細度になることがあります。._card:has(:not(img)) と ._card:not(:has(img)) は、意味が逆なのに、どちらも0.1.1です。詳細度の差から誤りに気づくことはできないので、入れ子の順序は意味から確かめます。

それぞれの擬似クラスの使い方と、:not() の引数の書き分けは、第5章「5-2 :is()・:where()・:not()」で説明しています※7。

引数に詳細度の高いセレクタを混ぜない

:is() は、複数のセレクタをまとめて書くための擬似クラスです。引数の最大が全体の詳細度になるので、引数にIDセレクタや長いセレクタを1つ混ぜるだけで、ほかの引数に当てはまった要素まで高い詳細度になります。

この例では、.card の中の ._title にも、1.1.0という高い詳細度が付きます。まとめるセレクタの詳細度をそろえるか、詳細度を加えたくないときは :where() を使います。:not() と :has() の引数も同じです。

詳細度が引数で決まることは、状態のスタイルを書くときには役に立ちます。画像があるときだけ2列にするカードの &:has(> img) は、:scope の0.1.0に img の0.0.1が加わり、0.1.1です。状態のスタイルは元のスタイルより詳細度が高くなるので、書く位置に関係なく元のスタイルを上書きできます。引数を短く保てば、こうした上書きの関係も読み取りやすくなります。

祖先の状態を :is() で書く

:is() が特に役立つのは、祖先の状態によって変わるスタイルを、子のルールの中に書くときです。次の例では、<details> が開いているときだけ、中のアイコンを回転させています。

&:is(.faq-item[open] *) は、「開いている .faq-item の子孫である、この要素」という意味です。.faq-item は <details class="faq-item"> で、開いているときだけ open 属性を持ちます（2026年9月、Chrome 152で確認）。アイコンのスタイルが .faq-icon のルールにまとまるので、状態による変化を探しやすくなります。@scope の中では、.faq-item[open] の代わりにスコープのルートを指す :scope[open] と書けます※8。

同じ指定は、.faq-item[open] .faq-icon という別のルールとしても書けます。しかし、.faq-icon のルールの中にネストして書くなら、ネストしたセレクタを & で始めるという本書の規約から、この形になります※9。

4-3 カスケードレイヤーで順位を決める

カスケードレイヤーを使うと、スタイルの優先順位を、詳細度ではなくレイヤーの順番で決められます。後に宣言したレイヤーのスタイルは、詳細度に関係なく、前のレイヤーのスタイルに勝ちます。詳細度を比べるのは、同じレイヤーの中だけです。

本書では、この仕組みを使って、スタイルの役割ごとに9つのレイヤーを決めています。ただし、レイヤーを選ぶのは、読み込むCSSをすべて自分で管理できる環境です。レイヤーに入っていないCSSは、詳細度に関係なくレイヤーの中のCSSに勝つので、CMSのようにレイヤーの外のCSSを避けられない環境では、レイヤーを使いません。

詳細度で役割の強さを表せるか

スタイルには、役割による強さの違いがあります。リセットCSSはベーススタイルに上書きされるべきで、コンポーネントのスタイルはユーティリティクラスに上書きされるべきです。しかし、詳細度はセレクタの形で決まる値なので、この役割の違いを表せません。

たとえば、要素を視覚的に隠すユーティリティクラス .-visually-hidden は、どのコンポーネントの要素に付けても効かなければなりません。レイヤーがなければ、ユーティリティとコンポーネントのクラスはどちらも0.1.0なので、頼れるのは書いた順番だけです。読み込む順番が変わっただけで効かなくなるので、以前はユーティリティに !important を付けるのが一般的でした。

すべての宣言に !important を付けると、このクラスを上書きできるのは、同じように !important を付けた宣言だけになります。詳細度の競争を、!important どうしの競争に持ち越しただけです。

私も2024年のブログでは、ITCSSという設計手法にならった7つのレイヤーを使っていました。全称セレクタで指定した詳細度0の文字サイズが、リセットCSSの inherit の指定に負けてしまうおそれがあり、それをレイヤーの順番で解決したのがきっかけです。詳細度の低いセレクタでも、後ろのレイヤーにあれば勝てます。レイヤーを使えば、優先順位を「役割の順番」として宣言できます。

レイヤーの仕組み

レイヤーは、@layer 文で名前と順番を宣言し、@layer 名前 { … } のブロックにスタイルを入れて使います。順番は、その名前が最初に現れた順で決まります。次の例では、components と utilities の2つのレイヤーを、この順番で宣言しています。

.notice .text の詳細度は0.2.0で、.text-muted の0.1.0より高く、ブロックも後ろに書いています。それでも、両方のクラスを持つ要素の文字色は --foreground--muted になります。カスケードはレイヤーの順番を詳細度より先に比べ、後に宣言した utilities のほうが強いからです。詳細度と書いた順番を比べるのは、同じレイヤーの中の宣言どうしだけです。

次のデモは、本書の規約に沿って書いたコンポーネントで、同じことを確かめます。デモでは、utilities レイヤーのルールを、components レイヤーのルールより前に書いています。どちらも0.1.0ですが、ユーティリティクラスを付けた2つ目の段落は灰色になります。コンポーネントの指定だけの1つ目の段落は、components レイヤーの青のままです。順番は先頭の @layer 文で決まっているので、ルールを書いた位置には左右されません。

デモ4-3-1　前に書いた utilities のクラスが、後に書いた components の指定に勝つ（補足サイト）

仕組みとして押さえておくのは、この3点です。レイヤーの順番は最初に現れた順で決まること、後のレイヤーほど強いこと、レイヤーの順番は詳細度より先に比べられることです。以降の見出しでは、この仕組みを本書でどう使うかを説明します。

本書の9つのレイヤー

ここからは、本書の規約です。本書では、すべてのCSSを自分で読み込める環境を前提に、スタイルの役割ごとに9つのレイヤーを決めています。CMSの本体やプラグインのCSSのように、レイヤーの外で読み込まれるCSSを避けられない環境では、この構成を使わず、後述の「CMSでのレイヤー」のとおり、読み込む順番で9つの分類を保ちます。

本書の基本のレイヤーは、次の9つです。前に書いたレイヤーほど弱く、後ろに書いたレイヤーほど強くなります。

  1. tokens：デザイントークン。:root のカスタムプロパティだけを置く
  2. reset：リセットCSS（kiso.css）
  3. base：HTML要素のデフォルトの見た目、@font-face、グローバルな @keyframes、@property
  4. vendors：自分で読み込むサードパーティのCSS
  5. compositions：stack、cluster、sidebarなど、レイアウトの再利用パターン
  6. pages：ページ固有のセクション
  7. components：複数の場所で使うコンポーネント
  8. patterns：静的で再利用できる見た目のパターン
  9. utilities：単機能の補助クラス

最初の3つは、すべてのページの土台です。tokens を最も弱いレイヤーにしているのは、トークンの中身がカスタムプロパティの定義だけだからです。後ろのレイヤーで同じ名前のトークンを定義し直せば、そちらが優先されます。reset の後ろに base を置くのは、kiso.cssのデフォルト（line-height: 1.5 など）をベーススタイルで上書きできるようにするためです。

vendors は、スライダーのようなサードパーティのCSSを入れるレイヤーです。自分たちのコンポジションやコンポーネントより前に置くので、サードパーティのCSSの見た目を、自分たちのCSSから上書きできます。

compositions、pages、components は、ページを組み立てるためのレイヤーです。ページ固有のセクションは pages に、複数の場所で使うコンポーネントは components に書きます。この区別は、レスポンシブ対応の手段の選び方とも対応しています。pages ではメディアクエリを、components ではコンテナサイズクエリを優先します※1※2。

components は、自分の構造とスコープと状態を持つ部品で、patterns は、それらを持たない静的な見た目の断片です。patterns は、コンポーネントの要素に重ねて使います。components より後ろにあるので、class="_label | status-badge" のようにコンポーネントの子要素に付けると、パターンの指定が勝ちます。コンポーネントの状態や @container の中の指定でも、同じプロパティは変えられません。そのため、パターンにはコンポーネントが変えないプロパティだけを書き、変える値は公開プロパティで受け取ります（「10-3 コンポジションとユーティリティ（10-3、巻2）」）。最後の utilities は、どこに付けても効かなければならない補助クラスなので、最も強いレイヤーにします。.-visually-hidden も、!important なしでコンポーネントのスタイルに勝ちます。

レイヤーの順番の宣言と @import での割り当て

レイヤーの順番は、そのレイヤーの名前が最初に現れた順で決まります。そこで、読み込むCSSの先頭で、すべてのレイヤーの順番を @layer 文で宣言します。その後ろで、各ファイルを @import … layer() の形で読み込みます。

この例では、kiso.cssを tokens のファイルより先に読み込んでいます。それでも、reset は tokens より強いレイヤーのままです。順番は先頭の @layer 文で決まっているので、@import を書く順番には左右されません。順番を宣言しなければ、先頭で読み込んだ reset が最も弱いレイヤーになってしまいます。

@import に layer() を付けると、読み込んだファイルの中身がすべてそのレイヤーに入ります。各ファイルの中で @layer base { … } のように包む必要はありません。どのファイルがどのレイヤーに入るのかを、エントリーポイントのファイルの1か所で確認できます※3。

@import は、@layer 文を除くすべてのルールより前に書く必要があります。ほかのルールの後ろに書いた @import は無視されるので、エントリーポイントのファイルには、レイヤーの宣言と @import だけを置きます。

ただし、この @import はブラウザに実行させず、ビルド時に展開します。ブラウザが @import の読み込みを始められるのは、それを書いたファイルをダウンロードして解析した後です。読み込んだファイルの中にさらに @import があれば、その分だけ待ちが重なります。CSSは読み込みが終わるまでページの描画を止めるので、この直列の待ちが、そのまま最初の表示の遅れになります。

Astro（Vite）は、ビルド時に @import の読み込み先の中身をエントリーポイントのファイルに埋め込み、layer() の指定を @layer のブロックに置き換えます（2026年10月、Vite 8で確認）。フレームワークを使わない環境では、postcss-importのようなPostCSSのプラグインで同じように展開できます。展開した後もレイヤーの順番とファイルの割り当ては変わらないので、ソースのファイルでは、上の例のように @import … layer() で書けます。CMSの案件でも、自分で書いたCSSはビルドを通してから配信します。例外は、「最小の構成で始める」のように、学習や検証のため、ビルドせずに手元で試す場合だけです。

学習用の構成から実務の配信へ移るときは、ビルドの道具を1つ通すだけで足ります。ここでは、「最小の構成で始める」のお知らせのカードを、ファイルを変えずにViteでビルドします。ファイルの配置、index.html、css/style.css とそこから読み込む4つのファイルは、そのページのとおりです。css/style.css では、9つのレイヤーの順番を宣言し、kiso.css、2つのトークンのファイル、news-card.css を @import … layer() で割り当てています。

Viteは、HTMLの <link> から読み込んだCSSも処理の対象にします。index.html のある場所で、Viteを入れてからビルドします。

ビルドすると、dist/index.html と、dist/assets/ に1つのCSSファイルができます。dist/index.html の <link> は、css/style.css ではなく、このファイルを指すように書き換わります。出力の中には @import が残らず、読み込んだ各ファイルの中身が、layer() で指定したレイヤーのブロックに入ります。次の出力は、骨組みが分かるように改行し、中身の一部を省略したものです（2026年10月、Vite 8.3で確認）。

2つのトークンのファイルは1つの :root にまとまり、中身のないレイヤーは名前の宣言だけが残ります。先頭の @layer 文は、最小化のときにこうして書き直されますが、レイヤーが最初に現れる順番は宣言のとおりなので、優先順位は変わりません。最小化では、display: block grid が display: grid に、calc(20 / 16 * 1rem) が 1.25rem になるような、意味を変えない書き換えも起きます。ビルドの後は、npx vite preview で dist/ を配信し、ソースと同じカードが表示されることを確かめます。dist/index.html はCSSを /assets/… のようにサイトのルートから参照するので、ファイルを直接ブラウザで開くとCSSが読み込まれません。そのうえで、出力のCSSに @import が残っていないことと、レイヤーの並びが宣言どおりであることを確かめます。

<head> の中の <style> のように @import で読み込まないCSSには、@layer components { … } の形でレイヤーを自分で書きます。

宣言していないレイヤー名の扱い

レイヤー名を打ち間違えても、エラーにはなりません。先頭の @layer 文にない名前は、その場で新しいレイヤーとして作られ、それまでに現れたすべてのレイヤーの後ろに加わります。次の例では、components を component と書いたことで、utilities よりも後ろの、より強いレイヤーができてしまいます。

この打ち間違いは、見た目ではすぐに気づけません。コンポーネントのスタイルはほぼ意図どおりに表示され、ユーティリティクラスを付けたときだけ効かないという形で現れます。@import url("…") layer(utility); のように、@import の layer() で打ち間違えた場合も同じです。

そのため、@layer と layer() には、先頭で宣言した9つの名前だけを使います。 この確認は、Stylelintに任せられます。Stylelintの layer-name-pattern は、@layer と @import の layer() に書いたレイヤー名を正規表現で検証するルールです。stylelint-config-standardのデフォルトは、名前がケバブケースかどうかしか調べません。本書の設定では、9つの名前を列挙した ^(tokens|reset|base|vendors|compositions|pages|components|patterns|utilities)$ のようなパターンを指定しています。これで、宣言していない名前を検出できます※4。

レイヤーの外に書いたスタイルの扱い

レイヤーを使うプロジェクトでは、すべてのスタイルをいずれかのレイヤーに入れます。レイヤーに入っていないスタイルは、すべてのレイヤーより後ろにある「暗黙の最後のレイヤー」として扱われるからです。!important を付けていない宣言どうしなら、レイヤーの外のスタイルは、詳細度に関係なくすべてのレイヤーに勝ちます。

@layer を書き忘れたスタイルは、utilities のユーティリティクラスよりも強くなります（2026年9月、Chrome 152で確認）。ユーティリティクラスを付けたのに効かないときは、レイヤーの書き忘れを疑います。1か所の書き忘れで、9つのレイヤーで決めた順番が崩れてしまいます。

次のデモの2つのカードは、同じ指定で段落を青くし、同じユーティリティクラスを付けています。違いは、2つ目のカードのルールを @layer components { … } で包み忘れたことだけです。1つ目の段落は灰色になり、2つ目の段落は青のままです。

デモ4-3-2　@layer を書き忘れたコンポーネントには、ユーティリティクラスが効かない（補足サイト）

サードパーティのCSSも同じです。<link> 要素などを使ってレイヤーの外で読み込むと、そのCSSはどのレイヤーよりも強くなり、自分のコンポーネントからは上書きできません。自分で読み込むサードパーティのCSSは、前の見出しのコード例のように @import url("…") layer(vendors); で vendors レイヤーに入れます。

この「レイヤーの外のCSSが勝つ」という性質は、自分で読み込み方を決められないCSSがある環境で、大きな問題になります。その代表がCMSです。

CMSでのレイヤー

多くのCMSでは、CMSの本体やプラグインの出力するCSSが、レイヤーに入っていない状態で読み込まれます。この環境で自分のテーマのCSSだけをレイヤーに入れると、テーマのCSSは構造的に負けます。どれほど詳細度を上げても、レイヤーの外にあるプラグインのCSSには勝てません。

次のデモでは、テーマのCSSを components レイヤーに入れ、見出しにクラスで色と大きさを指定しています。一方、プラグインを想定したCSSは、レイヤーの外にタイプセレクタ h2 で書いています。詳細度はテーマのCSSのほうが高いのに、見出しにはプラグインの色と大きさが使われます。見出しは、テーマで指定した青の20px相当ではなく、プラグインの赤の28px相当で表示されます。

デモ4-3-3　レイヤーの外のタイプセレクタが、レイヤーの中のクラスセレクタに勝つ（補足サイト）

私も、CMSの案件を始めたときは、Astroのテンプレートと同じレイヤーの構成で書き始めました。しかし、CMSの本体やプラグインのCSSとの関係でこの問題があるため、数日後にはレイヤーの使用をやめています。本書のレイヤーの構成は、すべてのCSSを自分で管理できる環境を前提にしたものです。

レイヤーを使わない環境でも、9つの分類そのものは捨てません。ディレクトリを分類ごとに分け、エントリーポイントの @import を9つの分類の順番に並べます。レイヤーがなければ、優先順位は詳細度と書いた順番で決まります。ベーススタイルを :where() で詳細度0にし、コンポーネントの中をクラス1つ分にそろえておけば、読み込む順番がレイヤーの代わりになります。この @import も、ビルド時に展開してから配信します。

CMSの本体と衝突しにくくするために、テーマのスタイルは @scope と独自のクラス名で範囲を限ります。CMSが出力するクラス名にスタイルを書く場面を減らせば、詳細度の競争に巻き込まれにくくなります※5。

例外：壊れた既存のCSSから新しいコンポーネントを守る

レイヤーを使わない環境にも、例外が1つあります。既存のCSSがIDセレクタの連結や !important で固められていて、新しく追加するコンポーネントにまでスタイルが流れ込んでくる場合です。既存のCSSを直せないなら、詳細度を上げて対抗するより、コンポーネントを外のスタイルから切り離すほうが確実です。

切り離しには、!important を付けた宣言どうしではレイヤーの順番が逆になる性質を使います※6。レイヤーの中で、コンポーネントの要素すべてに all: revert-layer !important を指定すると、この宣言はレイヤーの外のスタイルに、!important の付いたものも含めて勝ちます。revert-layer の戻り先はひとつ前のレイヤーなので、同じレイヤーの中に入れ子の無名レイヤーを作り、コンポーネント自身のスタイルはそこに書きます。

コンポーネントの要素の値は、入れ子のレイヤーに書いた値か、それがなければブラウザのデフォルトスタイルになります。既存のCSSが #page#page p のような詳細度で color や padding !important を指定していても、コンポーネントの中には当たりません（2026年10月、Chrome 152で確認）。all は継承を止めないので、文字の色やフォントのように指定しなかった値は、親から受け継ぎます。@scope の to (.scoped) があるので、中に置いた子のコンポーネントは切り離しの対象外です。

遮断できないものもあります。all が戻すのは、カスタムプロパティと direction、unicode-bidi を除くプロパティです。既存のCSSが :root のトークンやコンポーネントの公開プロパティの値を書き換えていると、その値はそのまま届きます。また、:scope と * は擬似要素を選ばないので、既存のCSSが ::before や ::after に付けた装飾は残ります。擬似要素も遮断するならセレクタに *::before, *::after を加え、トークンの値を守りたいなら、コンポーネントの入れ子のレイヤーで使う値を定義し直します。

この書き方は、!important を例外に限る本書の方針の中でも、さらに例外の位置づけです。後ろのレイヤーやユーティリティクラスも同じように遮断されるので、コンポーネントの見た目はすべて入れ子のレイヤーの中で完結させる必要があります。style 属性に !important を付けた指定だけは、レイヤーの中の宣言より強いので防げません。既存のCSSを直せる見込みがあるなら、そちらを先に検討します。

レイヤーを使うかどうかの判断基準

レイヤーを使うかどうかは、「レイヤーに入っていない外部のCSSがあるか」と「そのCSSを自分でレイヤーに入れられるか」の2点で判断します。

  • すべてのCSSを自分で書くか、サードパーティのCSSも自分で @import できる：レイヤーを使い、サードパーティのCSSは vendors に入れる
  • CMSの本体やプラグインのように、外部のCSSがレイヤーの外で出力され、読み込み方を変えられない：レイヤーを使わず、読み込む順番で9つの分類を保つ

AstroのようにすべてのCSSを自分で管理できる静的サイトは、前者に当たります。CMSのテーマやプラグインは、後者に当たります。迷ったときは、ブラウザの開発者ツールでページに読み込まれているCSSを確認し、自分が書いていないCSSがレイヤーの外にあるかどうかを調べます。

レイヤーは優先順位を宣言する便利な仕組みですが、詳細度を低くそろえる設計ができていれば、読み込む順番でも同じ結果を得られます。kiso.cssを :where() で書き、「レイヤーに頼らなくても上書きしやすい」ことを重視したのも、レイヤーを導入しにくい環境があるからです。

補足と注意点

9つのレイヤーを採用すると、CSSを書く人は、新しいスタイルをどのレイヤーに入れるかを毎回判断することになります。compositions と components、components と patterns の線引きは、名前だけでは決まらないので、慣れるまで迷いやすいところです。詳細度と書いた順番で優先順位を考えてきた人は、まずレイヤーの順番で勝ち負けを読み、同じレイヤーの中でだけ詳細度を比べる読み方に切り替える必要があります。

ある宣言がどのレイヤーにあるかは、エントリーポイントのファイルの @import … layer() の一覧で確かめます。レイヤーはファイル単位で割り当てているので、ファイルの置き場所が分かればレイヤーも決まります。<style> の中などに直接書いたレイヤーは、@layer で検索して探します。ブラウザの開発者ツールでは、スタイルの欄で、各ルールの上に、そのルールの属するレイヤーの名前が表示されます。意図しない宣言が勝っているときは、そのルールのレイヤーと、レイヤーの外に書かれていないかを先に確かめます。

レイヤーを使わないほうがよいのは、前の見出しの判断基準のとおり、レイヤーの外で出力される外部のCSSと読み込み方を変えられない場合です。サイトが小さく、9つのうち使わないレイヤーがあっても、スタイルを持たないレイヤーは優先順位に影響しないので、先頭の @layer 文から外す必要はありません。

新しいプロジェクトでは、最初にレイヤーの導入を検討します。既存のプロジェクトに入れるときは、一部のCSSだけをレイヤーに入れると、残りのレイヤーの外のCSSにすべて負けます。そこで、最初の段階で既存のCSSを含むすべてのファイルをいずれかのレイヤーに割り当て、Stylelintの layer-name-pattern を有効にします。components と patterns のような細かい線引きは、そのあとでファイルを移しながらそろえます。

4-4 @scopeでスタイルを閉じ込める

@scope は、セレクタが当たる範囲を、スコープのルートから下限までの間に限る仕組みです。@scope (.media-card) to (.author-note) と書くと、スタイルは .media-card の中に当たり、入れ子にした .author-note の手前で止まります。この形を「ドーナツスコープ」と呼びます。

本書では、この仕組みを @scope (.scoped.<名前>) to (.scoped) の形で使います。すべてのコンポーネントのルートに scoped のクラスを付けておけば、下限に .scoped と書くだけで、何を入れ子にしてもスコープが止まるからです。この規約は、仕組みを説明したあとの「本書の書き方：下限を .scoped にする」で示します。

この節では、@scope の仕様上の動作を説明します。下限の有無による違い、ネストや :where() との比較、詳細度が同じときに勝つ側を決める「スコープの近接度」、<style> 要素に書く前置きのない @scope、@scope が防がないものを順に扱います※1。

クラス名の工夫で範囲を限る従来の方法

CSSのセレクタは、ページ全体のどの要素にも当てはまる可能性があります。そのため、コンポーネントのスタイルがほかのコンポーネントに漏れないように、これまではクラス名を工夫してきました。代表的なのが、BEMのようにコンポーネント名を接頭辞にする命名です。

子孫セレクタで範囲を限ろうとすると、カードの中に置いた別のコンポーネントの .title にもスタイルが当たります。詳細度も0.2.0に上がります。BEMのように .news-card__title と名前で区別すれば漏れは防げますが、名前が長くなり、すべての子要素に同じ接頭辞を付け続ける必要があります。

@scope は、この問題をセレクタが当てはまる範囲そのもので解決します。スコープのルートと下限を指定すれば、その間にある要素にだけスタイルが当たります。ほかのコンポーネントもすべて @scope の中に書かれているなら、子要素のクラス名がほかのコンポーネントと同じでも、スタイルはぶつかりません。この条件が成り立たない場合は、「外から入ってくるスタイルは防げない」で説明します。

@scope の基本形

@scope の後ろの括弧に、スコープのルートを書きます。下限は to の後ろの括弧に書きますが、次の見出しで説明します。

@scope の中のセレクタは、先頭に「:scope と子孫結合子」が省略されたものとして扱われます。h2 は :scope h2 と同じ意味で、スコープのルートの子孫にだけ当てはまります。スコープのルートそのものを選ぶときは、:scope と書きます。

詳細度の数え方は、ネストと違います。@scope の括弧の中のセレクタは、中のルールの詳細度に加わりません。h2 は0.0.1、._main-link のような子クラスは0.1.0のままです。:scope は擬似クラス1つ分の0.1.0です。@scope の直下に書いた & もルートを選びますが、仕様では :where(:scope) と同じ扱いで、詳細度は0になります※2。

ドーナツスコープで入れ子のコンポーネントを除く

to の後ろの括弧に書くのは、スコープの下限です。ルートの子孫のうち、下限のセレクタに当てはまる要素とその中身は、スコープから外れます。下限の要素そのものも、スコープの外です。ルートから下限までの間だけにスタイルが当たるので、穴の開いたドーナツにたとえて「ドーナツスコープ」と呼ばれます。

この例では、.media-card の中の p が青くなり、入れ子にした .author-note の中の p は青くなりません。タイプセレクタで選んだスタイルも、下限で止まります。

本書の書き方：下限を .scoped にする

ここからは、本書の規約です。下限に入れ子のコンポーネントの名前を並べると、カードの中に置く部品が増えるたびに、外側の @scope を書き直すことになります。そこで本書では、すべてのコンポーネントのルートに scoped のクラスを付け、@scope (.scoped.<名前>) to (.scoped) と書きます。下限の .scoped は、ルートの内側にある別のコンポーネントのルートすべてに当てはまるので、何を入れ子にしても、外側のスタイルはそこで止まります。

この書き方で範囲が閉じるのは、入れ子にするコンポーネントのルートにも scoped が付いているときです。既存のサイトに @scope を少しずつ入れる段階では、scoped の付いていない古い部品の中まで外側のスタイルが届きます※3。ルートを .scoped.<名前> とクラス2つで選ぶ理由と、:scope と & の使い分けは、第9章「9-3 @scopeとネストの使い分け（巻2）」で説明します。

次のデモでは、本書の書き方で、.media-card の中に別のコンポーネントの .author-note を入れ子にしています。どちらのコンポーネントにも、段落の p があります。外側のスコープでは p を大きな青い文字にしていますが、入れ子のコンポーネントの段落には届いていません。タイプセレクタで選んだスタイルも、下限で止まります。

デモ4-4-1　to (.scoped) があるので、入れ子のコンポーネントの p に外側のスタイルが届かない（補足サイト）

下限を書かなかった場合と比べてみます。次のデモは、外側の @scope から to (.scoped) を消しただけのものです。入れ子のコンポーネントの段落も、青い文字になります。

デモ4-4-2　to (.scoped) がないと、入れ子のコンポーネントの p にも外側のスタイルが届く（補足サイト）

このデモでは、文字の大きさにだけ入れ子のコンポーネントの指定が使われています。どちらの p のルールも詳細度は0.0.1なので、この節の後半で説明するスコープの近接度によって、ルートに近い入れ子のコンポーネントの指定が勝つからです。しかし、入れ子のコンポーネントが指定していない色には、外側のスタイルがそのまま当たります。

下限のない @scope とネストの違い

下限のない @scope が当てはまる範囲は、ネストで書いた子孫セレクタと変わりません。次の3つのルールは、どれも .section の子孫のすべての p に当たり、入れ子になった別のコンポーネントの p も除きません。

違いは、まず詳細度です。ネストでは、p は .section p として扱われ、親のクラスの分だけ詳細度が上がります。@scope ではルートのセレクタが詳細度に加わらないので、p の0.0.1のままです。この差は、ネストの親を :where() で包めば再現できます。反対に、.section { :where(p) { … } } と書けば、親のクラスだけが残って0.1.0になります。

もうひとつの違いは、@scope の中のルールにだけ、次に説明するスコープの近接度が働くことです。ただし、近接度が働くのは、同じ要素の同じプロパティに、詳細度の同じ宣言が複数あるときだけです。上のデモで外側の色が入れ子のコンポーネントに届いたように、入れ子のコンポーネントが指定していないプロパティには、外側の指定がそのまま当たります。範囲を閉じ込めるという @scope の目的は、下限を書いて初めて果たせます。

スコープの近接度

スコープの近接度は、CSS Cascading and Inheritance Level 6で、カスケードの比較の段階に加わった基準です。カスケードは、オリジンと重要度、コンテキスト、style 属性、レイヤー、詳細度、スコープの近接度、出現順の順に比べ、先の段階で決まらなかったときだけ次の段階に進みます。近接度は、詳細度の後、出現順の前です。

近接度で比べるのは、スコープのルートから、スタイルが当たる要素までの距離です。仕様は、ルートが違う宣言どうしでは、要素からルートまでの世代や兄弟の数（ホップ数）の少ないほうが勝つと定めています。近接度は詳細度の後に比べるので、詳細度の高いルールは、ルートが遠くても勝ちます。近接度が順位を決めるのは、詳細度が同じときだけです。

次の例では、ライトとダークの配色を入れ子にしています。どちらのルールも詳細度は0.0.1なので、近接度で比べます。

リンクから見ると、ダークのルートは1つ上、ライトのルートは2つ上にあります。ダークのルールは先に書かれていますが、ルートが近いので勝ち、リンクは明るい色になります。出現順で決まるなら、後に書いたライトの色になるところです（2026年10月、Chrome 152で確認）。

次のデモは、この例に背景色と余白を足したものです。ダークの中のリンクは、後に書いたライトの濃い青ではなく、ダークの明るい青になります。

デモ4-4-3　詳細度が同じなら、ルートに近い @scope の指定が勝つ（補足サイト）

@scope の外に書いたルールは、近接度が無限大として扱われます。そのため、詳細度が同じなら、@scope の中のルールが、後に書いた @scope の外のルールにも勝ちます。@scope (.s) { :scope { … } } と、その後ろに書いた .s { … } は、どちらも0.1.0ですが、:scope の側が勝ちます（2026年10月、Chrome 152で確認）。

<style> に前置きのない @scope を書く

@scope は、ルートのセレクタ（前置き）を省いて書くこともできます。仕様では、前置きのない @scope のルートは、そのスタイルシートを持つ要素の親要素になります。<style> 要素の中に書けば、<style> を置いた親要素がスコープのルートです。

この例では、<section> がルートになり、p のスタイルはこの <section> の中にだけ当たります（2026年10月、Chrome 152で確認）。ルートを選ぶクラス名が要らないので、テンプレートの中にその場限りのスタイルを書く用途を想定した仕組みです。

次のデモでは、2つの <section> のうち、1つ目にだけ <style> を置いています。2つ目の段落は、同じ p でも青くなりません。デモのCSSのタブは枠線を付けるためのもので、前置きのない @scope はHTMLのタブにあります。

デモ4-4-4　前置きのない @scope は、style 要素を置いた section の中にだけ当たる（補足サイト）

本書では、この書き方を規約として勧めません。コンポーネントのスタイルがテンプレートのHTMLに散らばると、コンポーネントごとのCSSファイルにまとまらず、Stylelintでも検証できなくなります。同じコンポーネントをページに3つ置けば、同じ内容の <style> も3つ出力されます。本書は、コンポーネントのCSSをファイルに分け、ルートに付けたクラスでスコープを作ります。

外から入ってくるスタイルは防げない

@scope が制限するのは、@scope の中に書いたルールが当たる範囲です。スコープの中のスタイルが外へ漏れることは防げますが、@scope の外に書かれたルールがスコープの中の要素に当たることは防げません。

この違いは、自分で書いていないCSSと共存するときに表れます。CMSが本文エリアに .entry-content h2 { border-inline-start: 4px solid; } のようなスタイルを出力していると、本文エリアに置いたコンポーネントの h2 にも枠線が付きます。ライブラリのCSSが .title のような汎用的なクラス名にスタイルを指定していれば、同じ名前の子クラスにも当たります。子要素のクラス名がほかのコンポーネントと同じでもかまわないのは、ページのCSSがすべて @scope で範囲を閉じているときに限ります。

外から入ってくるスタイルへの対処は、レイヤーとCSSの読み込み方の問題です。外部のCSSを自分で読み込めるなら、vendors レイヤーに入れ、コンポーネントの指定が勝つようにします※4。ただし、レイヤーで決まるのは同じプロパティを指定したときの優劣なので、コンポーネントが指定していないプロパティには、外部のCSSが当たり続けます。CMSの本文エリアのように読み込み方を変えられないCSSがある環境では、レイヤーを使わず、読み込む順番で優先順位を保ちます。その判断の基準も4-3で説明しています。

次のデモでは、本文エリアのCSSを vendors レイヤーに入れ、.entry-content h2 に色と線を指定しています。コンポーネントが指定した color はレイヤーの順番で勝ちますが、指定していない border-inline-start と padding-inline-start は、スコープの中の見出しにも当たります。

デモ4-4-5　@scope の中の見出しにも、外に書いたルールが当たる（補足サイト）

値の継承も、スコープの境界を越えます。@scope が制限するのはセレクタの適用範囲なので、外側の要素に指定した color や font-size、カスタムプロパティの値は、下限の内側にも継承されます※5。

外のスタイルを境界で止める仕組みには、Shadow DOMがあります。@scope はLight DOM（ページの通常のDOMツリー）の中で自分のルールが当たる範囲を区切るだけなので、外に書いたルールと継承する値の両方が中に届きます。一方、Shadow DOMでは、境界の外に書いた通常のセレクタは内側の要素に当たりません。届くのは、color やカスタムプロパティのような継承する値と、部品が part 属性で公開した要素に ::part() で指定するスタイルです。本書では、::part() による公開を基本の設計には使いません。その代わり、ページのリセットCSS（kiso.css）やユーティリティクラスも内側には届きません。本書では、カスタム要素で部品を作るときもLight DOMのまま @scope で書くのを基本にし、ページから子要素を受け取らず、中身をすべて自分で描く部品に限ってShadow DOMを使います※6。

このため、@scope (.scoped.<名前>) to (.scoped) の形には、本書の中で3つの例外があります。1つ目は、カスタム要素で作る部品です。名前のクラスを付けず、要素名を前置きにして @scope (<要素名>.scoped) to (.scoped) と書きます。2つ目は、Shadow DOMの中のCSSで、境界がすでにあるので @scope を使いません※7。3つ目は、CMSのWYSIWYGが出力する本文エリアです。編集者は scoped のクラスを付けられないので、@scope (.wysiwyg) をルートにし、独自のブロックの手前を下限にします※8。どの例外も、下のガイドラインのルールの補足から、該当するルールをたどれます。

4-5 CSSネストの基礎

CSSのネストは、スタイルのルールの中に別のルールを書き、親のセレクタを & で参照する仕組みです。見た目はSassのネストと似ていますが、セレクタを文字列としてつなげる機能ではありません。& は、親のセレクタを :is() で包んだものとして要素に一致し、詳細度もそれに従って決まります。

@scope とネストは、どちらもコンポーネントのスタイルをまとめる道具ですが、得意なことが違います。@scope はBEMにおけるblockとelementの関係を、ネストはelementとmodifierの関係を表すのに向いています※1。

Sassのネストと同じだと考えて書く問題

ネストは、長くSassやLessのようなプリプロセッサーの機能でした。プリプロセッサーは、ネストしたセレクタを親のセレクタと文字列としてつなげ、普通のCSSに展開します。.card { &__title { … } } から .card__title を作れるのも、文字列の展開だからです。

素のCSSのネストは、この展開をしません。ブラウザは、ネストしたルールを親のルールとの関係として解釈し、& を「親のセレクタに一致する要素」として扱います。そのため、Sassと同じ形で書いても、無効になるものや、当たる要素と詳細度の変わるものがあります。

次のデモでは、1つ目の見出しをSassと同じ &__title で、2つ目の見出しを & ._title で指定しています。&__title のルールは無効なので捨てられ、1つ目の見出しには、色と大きさのどちらの指定も当たりません。

デモ4-5-1　Sass の &__title は、素の CSS では無効なルールになる（補足サイト）

この違いは、書いた人が気づきにくい形で表れます。&__title は無効なセレクタなので、ルールごと無視されますが、エラーは表示されません。詳細度や当たる要素の違いは、多くの場合は見た目に差が出ず、別のスタイルとぶつかったときに初めて表れます。Sassの書き方に慣れていると、素のCSSのネストも展開後のセレクタを想像して読んでしまい、こうした違いを見落とします。AIが生成するコードでも、&__title のようなSassの書き方を見かけます。

ネストの基本の書き方

ネストしたルールのセレクタは、親のセレクタとの関係を表す「相対セレクタ」です。& を書けば、その位置に親のセレクタが入ります。& を書かなければ、先頭に & と子孫結合子が省略されたものとして扱われます。

& は、複合セレクタのどの位置にも書けます。&[open] と [open]& は同じ要素に一致します。ただし、タイプセレクタは複合セレクタの先頭に書くという決まりがあるので、&div は無効で、div& と書く必要があります。

& を省いた書き方は、2023年12月より前の実装では使えませんでした。Chrome 112〜119とSafari 16.5〜17.1では、ネストしたセレクタを & や .、> のような記号で始める必要があり、h2 のようにタイプセレクタで始めると無効になりました。

本書では、どのセレクタも & で始めます。現在の仕様では、& を省いた .card { ._title { … } } は、先頭に & と子孫結合子を補った .card ._title として扱われます。省いても動きますが、先頭に & があれば、ネストしたセレクタが親とどういう関係にあるのか（&:hover なら自身の状態、& > img なら直下の子、& ._title なら子孫）を、セレクタの先頭を見ただけで読み取れます。ネストが長くなって親のルールの先頭が画面から外れても、& が親を指していることは変わらないので、どのセレクタが親との関係を表しているのかを読み違えにくくなります※2。

& は :is() と同じように働く

仕様は、& の詳細度を、親のセレクタリストの中でいちばん高い詳細度と定めています。これは、親のセレクタリストを :is() で包んだときと同じ決まり方です。親が1つのセレクタなら、展開した結果と詳細度は変わりません。違いが出るのは、親がセレクタリストのときです。

Sassなら、このルールは .news ._title, #pickup ._title に展開され、.news の中の ._title は0.2.0のままです。素のCSSでは、.news の中の ._title にも1.1.0が付きます。Chrome 152で、このルールと後ろに書いた .news ._title を比べると、このルールが勝ちました（2026年10月確認）。次のデモでは、ネストしたルールで文字を灰色に、後ろのルールで青くしています。見出しは灰色になり、後ろのルールからは、ネストしたルールが指定していない文字の大きさだけが使われます。

デモ4-5-2　セレクタリストの中にネストすると、.news の中の見出しにも 1.1.0 が付く（補足サイト）

詳細度の違うセレクタリストの中にネストしない規約は、第9章のルール no-nesting-under-selector-list です。

当たる要素が変わるのは、& を後ろに置いて祖先を足すときです。.a .b { .c & { … } } の & は :is(.a .b) になるので、全体は .c :is(.a .b) です。これは「.c の子孫で、かつ .a の子孫である .b」を意味し、.c と .a の上下を問いません。Sassの展開した .c .a .b と違い、.a の中に .c がある .a .c .b の並びにも当てはまります（2026年10月、Chrome 152で確認）。

& は、:is() と同じく擬似要素を表せません。._link::after { &[aria-current] { … } } のように、擬似要素のルールの中にネストしたルールは、どの要素にも当たりません（2026年10月、Chrome 152で確認）。擬似要素を選ぶときは、要素のルールの中で &::after や &[aria-current]::after のように、& の後ろに書きます。

& に文字をつなげる書き方は、どの位置でも使えません。仕様は、ネストを構文の変換ではなく、親のセレクタに実際に一致する要素にもとづく仕組みとして定めています。.card { &__title { … } } は無効なルールとして取り除かれ、Chrome 152では中身のない .card { } だけが残りました（2026年10月確認）。

条件付きのアットルールをネストする

@media、@container、@supports は、スタイルのルールの中にも書けます。中に直接書いた宣言は、親のセレクタに当たります。条件を満たしたときの指定を、元の要素のルールの中に置けるので、ひとつの要素のスタイルが1か所にまとまります。次のデモで幅のボタンの320pxを選ぶと、画像の下に本文が並び、見出しは18pxです。480pxと768pxでは、カードの内側の幅が400px以上になるので、画像と本文が横に並び、見出しが24pxに大きくなります。

デモ4-5-3　条件付きのアットルールを、要素のルールの中に書く（補足サイト）

._layout は、カードの幅をコンテナサイズクエリで問い合わせ、広いときにフラグ --_density を --spacious に切り替えます。子孫の ._title は、そのフラグをスタイルクエリで読みます。どちらの @container も、スタイルを変える要素のルールの中に書いています（フラグの仕組みは「10-6 スタイルクエリで状態を伝える（巻2）」で説明します）。

ネストした @container の中の宣言は、._layout と同じ詳細度の0.1.0で、元の宣言より後ろにあります。そのため、条件を満たすと、出現順で元の宣言を上書きします。@media や @container をセレクタの外にまとめて先に書くと、後ろに来た元のルールが同じ詳細度で勝ち、条件の側の指定は使われなくなります。条件付きのアットルールを各セレクタの中に書く規約は、第9章のルール conditions-inside-rules です。

条件付きのアットルールの中には、宣言のほかに、ネストしたルールも書けます。._layout の中の @container に & > img { … } を書けば、条件を満たしたときだけ直下の画像に当たります。アットルールの中に書いたルールの & も、外側のスタイルのルール（ここでは ._layout）を指します。アットルールはセレクタではないので、& が指す要素と詳細度を変えません。

ネストしたルールの後ろに書いた宣言

ネストしたルールの後ろにも、宣言を書けます。現在の仕様では、ネストしたルールの間に続く宣言は、親と同じ要素に同じ詳細度で当たる「ネストした宣言のルール」としてまとめられ、書いた位置の順番を保ちます。JavaScriptからは CSSNestedDeclarations として見えます。

この動作は、2024年12月にすべての主要なブラウザが対応した、比較的新しいものです。それより前の実装（Chrome 129以前、Firefox 131以前、Safari 18.1以前）では、後ろに書いた宣言も親のルールの先頭に移されたものとして扱われ、上の例では red が勝ちました。Chrome 152では green になることを確かめました（2026年10月確認）。次のデモは、同じ順番で赤と緑を指定したものです。本書の並び順の規約には反する書き方なので、悪い例として示します。新しい動作に対応したブラウザでは段落の文字が緑になり、古い実装では赤になります。

@scope とネストの役割の違い

@scope とネストは、BEMの3つの単位のうち、違う関係を表します。BEMのblockは独立したコンポーネント、elementはその部品、modifierはblockやelementの状態や種類です。@scope は、ルートと下限でblockの範囲を区切り、その中の部品（element）を短いセレクタで選ぶ仕組みです。ネストは、ひとつの要素のルールの中に、その要素自身の状態や種類（modifier）を & でまとめる仕組みです。次のデモでは、2枚のカードのうち data-variant="featured" を付けた2枚目だけが、ネストした指定によって青い2pxの枠線と24pxの見出しになります。

デモ4-5-5　@scope で部品を、ネストで状態や種類を表す（補足サイト）

BEMで書けば、.news-card、.news-card__title、.news-card--featured に当たる3つの関係が、それぞれ @scope のルート、スコープの中の h2、& を使ったネストで表されます。ネストで部品の階層をたどる書き方（:scope { h2 { … } }）もできますが、@scope があれば、部品はスコープの直下に並べられます※3。@scope の仕様は「4-4 @scopeでスタイルを閉じ込める」で説明しています。
